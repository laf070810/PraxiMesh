# RFC-031：GPU 源码发送前的通道检查点

日期：2026-11-15。状态：已实施，268 项组件与本地管道、41 项真实 CPU 容器检查通过；GPU 回归待执行，决策见 [ADR-085](../adr/085-gpu-preparation-checkpoints.md)。

## 问题

冻结版本 `4380a19` 在临时站点通过完整 GPU 启动、候选队列和向量题的六项正常 API 检查。随后矩阵参考解的 Run 返回 `time_limit`，尚未记录编译初始化完成。原任务保留为 `30ca2fe5-0f0f-4a62-a68b-704abb280a5f`。

原数据库记录显示，预约于 04:41:22.886839 UTC 开始，执行标记于 04:41:49.689473 写入。90 秒预约依次预留外层停止 5 秒、协议完成 5 秒、独立恢复 35 秒和内层清理 10 秒，实际执行截止为预约开始后 35 秒。执行标记之后最多只剩约 8.20 秒，且发送源码前仍有完整环境和设备检查；编译本身的 15 秒上限尚未到达。失败不能据此归为矩阵实现错误，也不能删除原结果重发来宣称通过。

调用路径在连接构造器已执行完整检查的前方又检查一次，并在准备响应、开始回调和通道发送之间重复执行检查。外层手动调用没有更新通道自己的 250 ms 心跳时钟，因此通道在紧邻的发送中再次查询设备。

## 调整

为原 `Channel.check` 增加强制检查选项：忽略下次心跳时刻立即调用原检查，完成后按原规则安排下一次检查。开始回调返回后，调用该检查点，再经原通道发送源码。原容器 ID、启动实例、journal、数据库租约、配置、完整 NVIDIA 来源和截止时间仍由原回调核对。检查失败、取消或超时不得发送源码；部分写入与背压仍按原周期复查。

连接构造器自身负责建立连接前的完整检查；准备响应核对后直接执行开始回调，再执行上述强制检查。删除紧邻且覆盖同一阶段的手动检查，不缓存跨阶段就绪、不重用其他实例的观察、不改变 90/180 秒预约或恢复余量。开始回调中的环境复核和完成后的独立清理、设备空闲检查保持原义。

## 验证

用真实本地 socket 验证强制检查可打断尚未到期的心跳缓存、检查耗时计入原期限、紧邻发送不重复回调、背压仍复查；模型验证开始回调改变身份或取消时源码不能发送。固定 CPU 容器检查覆盖通信、内核调用及故障恢复，但不计作 GPU 通过。

新冻结四镜像须重放无设备入口和 CPU 应用，再通过正常协调器启动、普通 HTTPS API 的参考解/错解/恢复，以及真实 GPU 的时间和清理证据。原失败及原版本的成功证据分别保留；若仍耗尽预算，继续诊断而不缩小恢复余量。
