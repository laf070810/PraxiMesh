# RFC-023：恢复时重建无状态 Web 容器

日期：2026-11-01。状态：已实施，真实复验待完成。对应 PRD R-09、AC-07；延续 [RFC-005](005-deployment-coordination.md)。决策见 [ADR-060](../adr/060-web-container-recovery.md)，检查范围见 [G44](../acceptance-g44.md)。

## 已复现的问题

[G43](../acceptance-g43.md) 的四代 CPU 发布在曝光后恢复时遇到 RootlessKit 端口占用。独立固定 CPU HTTP 服务进一步复现：释放冲突端口后重新 `docker start`，同一容器可以显示运行，却没有实际端口映射、无法访问。重复启动不构成恢复成功。

## 决定

在原恢复流程的维护、排空、停止和数据库冻结/解冻之后，重建该代无状态 Web 容器。仍使用原发布镜像、原数据库、原配置和原逻辑容器名，重新分配回环端口。worker 保留原生命周期与完整启动检查；不改变曝光边界，不把已曝光数据库回退到旧快照。

重建前核对实际代理处于维护状态，确认容器已经停止。校验站点、代、角色、镜像、容器 ID、命令、环境、只读根、资源约束、网络、权限及挂载；只接受协调器管理的无持久挂载 Web。旧日志首次恢复可以按这些明确契约建立 ID 记录；已有记录不得按同名或当前 UID 重新认领未知对象。

先在私有部署 journal 保存重建意图，包括原 ID 和配置摘要、目标随机标记、代、数据库与镜像。移除只使用已再次核对的完整 ID，不使用 force 或 volumes。随后单独 create，保存新 ID 后再 start；实际回环映射和后续 HTTP、worker 就绪、可信正确/错误程序检查全部通过，才允许重新开放代理。

重建记录跨发布操作保留。进程中断后，仅接受原 ID/配置，或精确匹配持久意图标记和运行契约的新对象。创建后尚未记下 ID 的对象也必须完整核对。已经尝试启动的新对象若在下一次恢复时停止，则另存新意图后重新创建，避免重用失败的网络状态。未知替换、挂载、配置变化、端口异常或创建失败均保留维护状态与原数据库；不修改共享 daemon。

## 验证范围

控制流检查覆盖曝光前回到上一代、曝光后保留当前代，以及移除前、移除后、创建后、ID 保存后和启动后的中断重试、同名替换与持久数据拒绝。实际容器检查用自有固定 CPU HTTP 服务和占端口 socket，验证故障、重新创建、HTTP 和清理；明确不证明数据库或真实评测。

完整 CPU 验收继续使用未改写的可信旧发布包、实际 PostgreSQL/HTTPS/WASI，重放四代切换、真实进程中断、数据保留、删除不复活和新提交。GPU 激活与真实硬件验证仍独立待完成；本修复不触碰设备。
