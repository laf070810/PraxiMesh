# RFC-024：本地 CUDA 练习工具

日期：2026-11-02。状态：无设备编译已实现，完整本地 GPU 运行仍实施中。编译决策见 [ADR-073](../adr/073-local-device-free-cuda-compilation.md)。对应 PRD R-15、R-16、§8.5；沿用 [RFC-007](007-b2-practice-and-sharing.md) 的公开包/正式成绩边界，以及 [RFC-021](021-gpu-container-supervision.md) 的容器监督、隔离编译与持久恢复。

## 问题与完整目标

CLI 已支持 CUDA 公开包下载、编辑和远程 Run/Submit，但本地 `test` 只支持 WASI。维护者当前要求不访问 GPU；已有无设备 NVRTC 编译能力仅供内部验收工具调用。完整本地 CUDA 练习仍需要经过验证的设备环境、公开样例执行、可信比较、独占与资源控制、取消及恢复，不能以编译成功替代这些要求。

先将已具备的真实隔离编译接入本地工具，给用户提供编写 CUDA 时的编译反馈，并保持后续完整公开测试的目标。此增量不开放本地 GPU 执行、不生成成绩或就绪凭证；公开样例仍通过已验收服务器的 `submit --mode run` 执行。

## 用户入口与执行边界

- 新增 `compile` 子命令，读取既有 `exercise.json` 与 `solution.cu`，复用严格的公开包校验。只接受 CUDA 契约；公开包不能指定镜像、宿主路径、设备或执行命令。
- 操作者显式提供私有状态目录、rootless Docker socket、不可变编译镜像 ID 和计算架构。计算架构只作为 NVRTC 目标，不查询 GPU。构建入口封装已有固定归档与编译镜像构建器，不下载执行公共包中的脚本。
- 复用 `CompilationTask`、`CompilerContainerService` 和既有无设备 gVisor guest。保留 0.5 CPU、512 MiB、零 swap、256 PID、绝对期限、只读根、断网、固定 seccomp，以及无 GPU/驱动的实际握手；源码仅在身份及开始回调通过后经有界管道发送。
- 结果只返回编译状态、源码摘要、公开版本身份及受限编译元数据，明确 `formal_result: false`、`executed: false`。可编译的语义错解同样可能返回 `compiled`，不能使用 Accepted 或通过样例数。
- `recover-compiler` 只清理该状态目录登记的原编译任务，不重新编译、不执行旧镜像、不操作按名称发现的替代容器。正常编译前若存在未完成记录，拒绝新任务并要求先恢复。

## 私有状态与中断

状态目录必须由当前非 root 操作者拥有、权限 0700，并绑定原目录、锁目录、journal inode 和安装身份。只为原本不存在的目录初始化标记；不接管未标记的现有目录。复用锁与 journal 的格式时，使用由本地状态身份派生的逻辑 UUID；它不代表物理 GPU，也不能用于设备准入。

每次操作先确认标记、原安装记录及同一 daemon，再获取原锁；不能通过删除记录、改换状态目录或重建命名空间来绕过待清理任务。运行中持续核对原身份。SIGINT/SIGTERM 仅设置取消标志，由正常控制路径停止与核对原任务；SIGKILL 后保留原记录，由显式恢复继续处理。初始化在任何任务创建前完成；部分或损坏的初始化保留现场并拒绝接管。

## 完整公开样例执行的下一步

现有 `execute` 请求要求同时包含公开和受保护测试；下载包无法使用这一请求，也不能通过伪造受保护样例满足校验。为本地执行增加独立 `execute-public` 请求，仅接受既有六个执行字段和全部为公开的测试，模式固定为 `run`。原正式任务、正式内容和 Submit 的校验保持原义。

公开任务复用可信比较函数、原 GPU 任务与容器执行链，不增加宿主执行或任意命令入口。源码仍在环境握手和开始回调之后发送；公共预期值留在可信控制器，guest 只接收编译源码和输入。完成响应必须带 `formal_result: false`，不带性能分数，并等待原 guest 停止、新正确恢复、外层任务删除与空闲观察。公开完成响应不能作为正式任务完成响应接收。

先实现这一执行协议及适配器接口，并用固定 CPU/runsc 协议夹具验证控制器比较、失败分类、取消和清理；夹具不编译或执行学员源码，不证明 CUDA 正确性。完整本地命令仍须接入原物理设备锁、持久本地任务身份、完整二十四阶段启动、过期/取消处理及硬件验收，不能因协议检查通过而开放入口。相关源码变更需核对策略及配套镜像身份，旧编译镜像也不得在契约变化后继续使用。

## 共用完整容器启动流程

服务端当前把容器启动检查和数据库预约/凭证发布放在同一函数中。本地执行需要前者，但不能借用服务端账号、队列或学习数据库。将完整容器检查次序整理到无 Django/数据库依赖的 `judge/container_startup_suite.py`，由服务端继续调用同一实现，避免另建一套较弱的本地检查。

共用流程必须核验调用者已完成的原任务恢复报告，再依次运行资源、十九项内核和三项控制器故障检查。它接受原适配器、维护任务身份、总期限和所有权/取消回调；只返回完整且逐阶段校验的证据，不写 receipt、不确认数据库预约，也不发布 ready。任一错误、取消、环境变化或清理未完成均扣留总结果。

服务端继续负责原数据库预约、凭证撤销/发布和最后的行锁核对；阶段进度仍在校验后通知。本地调用者后续还须有原物理锁、私有持久身份和恢复流程。此重构先通过无数据库的执行模型、既有服务端检查、真实 PostgreSQL 竞争，以及实际无设备 worker 镜像预检；这些检查不替代完整 GPU 硬件启动。

## 本地物理状态与完整执行生命周期

本地执行复用操作者明确准备的原 v4 控制器状态、物理 UUID 锁和 journal，不从练习包建立另一套设备锁目录。首次本地绑定只接受未使用的准备状态；存在 worker 配置、发布协调标记、receipt、旧任务或未知文件时拒绝认领。绑定保存原目录/锁 inode、mounts 摘要和安装/daemon 身份。反向地，worker 配置、读取和协调器首次认领也须拒绝本地状态，不能在无数据库核对时清理服务端预约。

每次公开执行先持久登记新的本地操作与任务/预约 UUID，再执行真实初始正确恢复、共用二十四阶段启动和公开任务；结果必须晚于完整原任务清理、最后的原身份核对和操作终态持久化。所有权/取消回调贯穿启动、发送源码前和结果返回前。已有未完成操作时不自动重跑；显式恢复只按保存的操作/设备/镜像/固定命令清理原容器，不执行旧镜像、不发布 ready，之后的新执行仍重跑完整启动。

本地状态与执行组件均不得依赖 Django、应用账号或学习数据库。先验证完整组件调用链、真实文件/锁与进程中断，以及与 worker/协调器互斥；GPU 方法的模型不证明硬件可用。外部 CLI、固定控制镜像/通信及真实 GPU 验收仍须接入同一生命周期，不能绕过它另行执行公开包。

## 备选方案与取舍

宿主 `nvcc`、NVRTC 或普通容器会增加一条没有既有隔离验证的源码处理路径，故不采用。复用正式 Web 队列建立临时账号并导入下载包会混淆内容发布、公开测试与正式版本，也不作为本地编译的实现。新增命令使用现有可信编译执行链，保持应用、数据库 schema 和正式 GPU 执行协议不变。

## 验证与交付

验证公开包拒绝、私有文件与实际文件锁、状态替换、镜像错配、取消前不发送源码、错误分类和待恢复记录保留；协议模型不作为执行证据。随后使用真实无设备编译镜像重放正确程序、可编译错解、编译错误、未知架构、并发拒绝、控制进程中断和原任务恢复，再核对现有服务及测试资源。

源码发布须包含新 CLI 模块和构建入口，同时继续接受旧冻结包。操作集中到 `docs/deployment/`，使用方法放在[本地练习指南](../local-practice.md)。真实 GPU 公开样例、本地运行的完整启动门槛、硬件故障恢复及正式 GPU 产品验收仍作为后续独立交付项保留。
