# RFC-040：首次 GPU 发布曝光后的确认丢失

日期：2026-11-15。状态：实现与 91 项组件检查通过，实际 GPU 中断仍待验收。决定见 [ADR-094](../adr/094-initial-gpu-exposure-acknowledgement.md)，延续 [RFC-022](022-gpu-release-coordination.md) 和 [ADR-072](../adr/072-coordinated-gpu-release-recovery.md)。

## 已复现的问题

首次 `apply_coordinated` 已持久化候选 GPU 库及曝光决定、开放路由，调用者在外部健康确认前消失。`recover_coordinated` 新建恢复记录时无条件从 maintenance 开始，随后停止仍在运行的原 worker 并重新执行完整启动。既有不重启检查仅覆盖恢复记录已经处于 expose_target 的第二次调用，漏掉首次发布的同一边界。CPU→GPU 和 GPU→GPU 两个模型均观察到启动次数从一变为二；这不是硬件验收。

## 有限恢复入口

仅当首次发布记录和外层操作均停在 exposing、当前库及曝光目标均为原 GPU 候选，并且尚无恢复尝试时，新恢复记录从 expose_target 开始。此前持久化的曝光决定、轮次、配置、原容器及启动时间仍须通过现有 GPUExposure 的全部核对；不创建新准备轮次或补写曝光证据。

保存恢复意图后先核对原 worker。原实例仍存活时继续原曝光协议，逐次检查新鲜心跳、正式准入、原环境和实际路由；已开放后的合法任务保持正常。原实例确已退出时回到 maintenance，沿同一数据库进行停止核对、新预检、完整启动与新候选轮次。配置、对象、归档或路由未知时保留现场，不以一次重启掩盖身份错误。

该入口不改变已完成发布上的显式 recover，也不改变已捕获健康失败后的 needs_recovery、曝光前失败、GPU→CPU 或 CPU 原路径。再次暂停、撤回已确认路由或新启动仍遵循既有完整恢复规则。原日志 schema 不变，只使用已有 expose_target 恢复阶段；已交付记录不改写。

## 验证与交付

先在隔离工作区复现两个失败，覆盖首次安装、CPU/GPU 前代、原 worker 退出、身份改变、缺失曝光记录、未知路由、已完成发布与已捕获失败。真实文件/进程检查在持久曝光后终止原协调器，再核对恢复前后的 worker 启动次数和新写入。

变更纳入新的冻结源码包，不能修改当前正在验收的制品。最终还须在原自有临时站点进行真正的 GPU 候选曝光中断、普通新提交及原实例恢复；模型通过不解除公共 GPU 激活门槛。
