# RFC-021：GPU 容器部署的独立任务监督

日期：2026-10-31。状态：分阶段实施；尚不开放 GPU 容器评测。

## 问题与最终边界

GPU 宿主 worker 依靠用户 systemd 服务、持久设备锁、私有通信和独立硬期限。把该命令直接放进现有 Web 镜像无法保留服务身份、cgroup、路径和崩溃接管语义。完整交付仍须包括 Compose/发布协调、固定运行制品、当前启动凭证、GPU 隔离与独占检查、真实队列及异常恢复，不能用容器内有 Python 或能看到显卡代替。

继续保持 Web 不接触 Docker socket；GPU 可信控制器与学员 guest 分开。普通 OCI 容器只承载可信监督代码，学员代码必须进入另行验证的 gVisor 环境。现有宿主路径在新路径全部验收前保持可用；不把开发组件接入提交准入或签发凭证。

## 方案比较

- 向控制器容器暴露宿主用户总线并继续启动宿主命令，需要跨容器匹配解释器、挂载、PID 和 UID；仍依赖宿主 Python，不能作为完整容器交付。
- 在容器内运行完整 systemd/嵌套 daemon 增加权限和运维面。Docker 的 rootless 嵌套示例仍要求 privileged，不能据此推断适合本项目。[Docker rootless 指南](https://docs.docker.com/engine/security/rootless/tips/)
- 候选方案是专用 rootless Docker 上的可信监督容器：控制器按不可变镜像和持久预约身份创建任务容器，容器 PID 1 独立维护绝对截止时间。设备隔离、guest 运行时与容器化控制器的身份映射另行接入和实测。

本阶段先实现第三种方案的监督基础，真实验证父控制器退出、整棵任务进程树、独立期限、停止与重启接管。它是完整部署所需的组件，不是新的学员执行器。

## 监督契约

客户端只连接明确选择、由当前用户拥有的本机 Unix socket，并核对 rootless、cgroup v2 和限额能力。使用空白 Docker 客户端配置，避免代理或身份配置进入容器；不改 daemon、用户服务或驱动。

每个任务由设备锁、任务 UUID、预约 UUID 和用途确定名称与标签；绑定实际容器 ID 后不能因同名替换而继续操作。镜像必须是本机已经存在的完整 SHA-256 ID，不自动拉取或接受浮动标签。创建与启动分开，启动前核对完整配置。命令仅来自可信控制器，不接受学员命令、源码或数据库凭证。

监督容器采用独立 PID/cgroup 命名空间、无网络、只读根、无额外能力、no-new-privileges、固定非 root 用户和有界私有 tmpfs；不挂宿主目录、socket 或 GPU。CPU、内存、swap 和进程数量必须在容器内读取实际 cgroup 文件核对，不能仅信任 Docker 参数。此阶段的固定 CPU 探针不代表 GPU guest 隔离。

PID 1 在绝对启动期限后拒绝启动；终止期限不因重连、观察超时或恢复而延长。仅监督器生成有限的私有状态，子进程输出丢弃，Docker 日志关闭。PID 1 退出结束该 PID 命名空间的进程树；上层仍须确认容器实际停止，再删除自己的容器。API 超时、配置不符、替换或无法确认停止均保留待恢复状态，不能据此释放设备预约。Docker 的 init、PID namespace、资源和停止选项以[官方运行文档](https://docs.docker.com/reference/cli/docker/container/run/)为依据，并以实际故障检查核验。

## 后续集成与发布门槛

### 容器内 runsc 可行性验证

2026-10-31 的固定 CPU 前提检查确认：当前监督容器内 `unshare(CLONE_NEWUSER)` 返回 EPERM，cgroup 为只读。现有依赖 RootlessKit、Podman 及可写子 cgroup 的宿主运行时不能原样搬入。原始结果在 `test-results/g22-namespace-prerequisite.json`；没有修改主机服务或执行 GPU。

下一步以独立、未接入正式评测的实验镜像验证直接 OCI runsc：固定完整运行时归档，构建只读 guest 根目录；仅对可信外层程序提供经过审阅的命名空间系统调用配置，继续使用 rootless、无额外能力、无宿主挂载、无网络和无设备。不能使用 privileged 或 unconfined 代替确定所需权限。gVisor 的[无特权嵌套运行说明](https://gvisor.dev/docs/user_guide/rootless/)和 [OCI 入口](https://gvisor.dev/docs/user_guide/quick_start/oci/)提供机制依据，实际可用性仍以本机探针为准；外层 syscall 配置参照 [Docker seccomp 说明](https://docs.docker.com/engine/security/seccomp/)。

实验必须明确资源属于哪一层：外层现有 2 CPU、2 GiB、512 任务上限覆盖监督器和所有 guest；这不能冒充宿主路径独立的 0.5 CPU、512 MiB guest 配额。接入正式评测前须选定并版本化资源契约、证明内存/进程/CPU 故障和独立期限，重新验证执行环境及凭证。外层期限必须仍覆盖 runsc、gofer、Sentry 和脱离父进程的后代，不能仅终止附着 CLI。CPU 探针只能证明所执行的基础路径，不能启用 GPU、正式成绩或普通容器回退。

必须解决并验证：容器化 worker 与既有设备锁/UID/主机身份兼容；持久保存并恢复旧镜像和容器身份；可信通信、取消和租约；gVisor/NVIDIA 单卡注入、PID 对应和持续占用检测；完整启动与资源/内核/故障探针；Compose 数据库初始化与发布协调器的排空、升级和回退。GPU 驱动仍在信任边界内，Docker GPU 选项不能替代 [gVisor GPU 检查](https://gvisor.dev/docs/user_guide/gpu/)。

### 受信控制连接

G22 已实际验证容器内 CPU guest，但只从固定探针文件收集结果，尚不能传送任务。下一步复用有界 `Channel` 协议，通过不可变容器 ID 的 `docker exec --interactive` 启动镜像内固定桥接程序；禁用 TTY，不把任务放进命令行、环境或 Docker 日志，不向任务容器挂载宿主通信目录。Docker 对 exec 生命周期与环境继承的说明见[官方接口](https://docs.docker.com/reference/cli/docker/container/exec/)，是否正确传递 EOF、背压与故障须实际验证。

桥接程序只连接容器私有 tmpfs 中的固定 Unix socket。双方核对内核对端 UID/PID；桥接端必须连接监督状态指定的主控制器，控制器只接受固定桥接入口。宿主先核对已持锁的容器 ID、启动实例和完整运行配置，再校验原启动 nonce、子进程身份及绝对期限，完成确认后才传任务。每个调用只允许一个连接；断连不能重连继续旧任务，也不能延长原期限。

本地连接与字节转发分别受期限、累计字节数及固定缓冲区限制。关闭连接、终止 Docker CLI 和确认 guest/整个容器退出是不同动作；取消或租约失效先停止发送，再沿原容器身份回收。应真实验证大消息、guest 不可见通信端点、运行中断连/取消、额外输入和硬期限，并核对新的独立调用可以恢复。此路径仍不处理设备注入、不生成 GPU 凭证、不直接替换宿主通信。

### 持久身份与升级后的清理

现有开发服务的名称包含当前进程 UID，运行配置又按当前源码计算。容器化 worker 的 UID 视图可能不同，代码更新也会改变契约摘要；不能要求新控制器使用当前镜像来冒认或重新运行旧任务。下一步增加独立的持久服务身份：私有安装 UUID、Docker daemon ID、同一设备锁目录的文件系统身份、设备和任务预约共同确定范围，不以进程 UID 作为跨重启名称来源。

每卡持锁后，先将固定启动意图持久化，再创建容器；实际容器 ID 在启动前落盘，启动实例在确认就绪后追加。原镜像 ID、参数 nonce、完整标签、镜像环境及已审阅 seccomp 配置随记录保存。写入采用私有文件、原子替换和目录同步；记录不包含学员源码或应用凭证。不同锁目录、daemon、未知记录格式或仍有未恢复调用均拒绝新任务。

恢复不需要执行旧镜像内的程序。独立的仅清理接口按已保存的 v1 监督契约验证实际容器，再停止、确认退出并删除；已绑定 ID 或启动实例不能被同名新对象替代。创建成功但尚未来得及记录 ID 的窗口，只能按原意图的名称、随机 nonce、镜像和完整配置找回。确认消失后归档记录，再允许新调用；这仍不证明 GPU 空闲或正确性恢复，不能释放数据库预约或生成就绪凭证。

需实际验证创建前、创建后、启动后中断、新进程接管、旧镜像契约与当前源码不一致时的清理、同名替换拒绝及新调用恢复。跨 UID/命名空间映射、真实 worker 容器与数据库连接、设备注入及完整发布仍需分别验收。

### 容器化控制端与宿主文件身份

下一阶段先交付不使用 GPU 的可信控制端镜像及实际接管检查。控制端连接指定的 rootless daemon，镜像内 UID/GID 0 必须实际映射到启动它的非 root 操作者；读取内核映射并核对宿主准备的私有挂载清单，不通过放宽 0700/0600 权限或改写文件拥有者解决映射问题。镜像固定 Docker CLI 制品、源码和入口，不依赖宿主 Python、Docker 配置或用户总线。

控制端具有该 daemon 的完整控制权，必须属于可信执行平面，不能承载 Web 或学员代码。它只挂载精确的 socket 文件和专用持久目录；不挂整个用户运行目录、项目目录或 GPU。只读根、无额外能力、no-new-privileges、独立 PID/cgroup、限额、无网络仍需实际核对。socket 文件使用只读挂载并不限制 Docker API 权限；安全边界是可信代码和专用 rootless daemon。[Docker rootless 机制](https://docs.docker.com/engine/security/rootless/)、[bind mount 语义](https://docs.docker.com/engine/storage/bind-mounts/)。

宿主清单固定目录和 socket 的 dev/inode、daemon ID、操作者 UID/GID，容器入口在打开任务记录前验证；共用原设备锁 inode 和 journal，不创建第二套独占机制。必须验证宿主持锁时容器拒绝、容器持锁时宿主及另一容器拒绝、映射错误和挂载替换拒绝、控制容器退出后原任务清理，以及新容器/宿主之间双向接管。任务容器仍由原独立 PID 1 期限管理，控制容器被杀不能自动视为任务完成。此阶段使用固定 CPU guest；数据库、GPU 设备/占用监测、资源契约及 Compose/发布仍为后续独立门槛。

### 数据库预约与持久容器恢复

G25 已验证跨宿主/容器的同一锁和 journal，但尚未把恢复与数据库预约绑定。下一步将其接入现有 worker 的启动、凭证续检和取消恢复，并作为后续容器 worker 复用的核心恢复组件。显式配置同一 rootless socket 和已初始化的 journal；默认宿主路径保持原行为。配置不能选择不存在的新目录来掩盖旧任务。

恢复先在有界事务中接管并隔离设备，保留原任务/预约。终止已确认属于本安装的原容器与已知宿主服务，不让数据库锁等待或失败阻止原对象终止；终止并不移除活动记录或释放预约。缺失 ID 的创建窗口仍须先核对并持久保存找回的完整 ID，再停止。任何身份替换仍拒绝操作未知对象。

归档与移除前必须在短事务中确认同一设备拥有者、隔离状态和原预约。容器记录只允许对应原任务/预约或每卡固定的启动维护身份；错配时保留记录与数据库预约，不能借用新的预约清理或释放旧对象。账户删除后设备行中保留的 UUID 仍是恢复依据，不要求用户或提交记录继续存在。清理后再次核对数据库身份；并发变化、归档故障或数据库不可用均不产生就绪、成绩或释放动作。

宿主 worker 只在上述清理完成后继续原有独立 GPU 正确性恢复和完整启动检查。新增容器清理结果本身始终 `ready: false`，不是 receipt。须在实际 PostgreSQL 和固定 CPU 容器中验证创建/运行中断、预约错配、删除账号、数据库行锁、归档中断与重试；另验证旧宿主生命周期和默认命令兼容。正式 GPU 执行策略摘要应覆盖新恢复代码与所依赖的容器身份检查；这一步不代替容器 GPU 执行、设备监测或完整 Compose 发布。

### 固定 CUDA 编译器与无设备验证

容器运行镜像下一步加入经过归档及逐库摘要校验的 NVRTC 13.1.115，复用正式 `gpu_runtime.py` 的编译参数、PTX 上限和错误分类。将编译函数从 CUDA context 初始化中分离；正式 GPU 路径仍先确定实际设备架构，再调用同一函数。独立编译检查只在 gVisor guest 中接收源码，不允许在宿主或可信外层容器中编译学员输入。

NVRTC 官方说明其可在无 GPU 的系统运行，见 [NVRTC 文档](https://docs.nvidia.com/cuda/nvrtc/index.html)。此开发检查使用明确的目标架构，不连接设备、不装载 CUDA 驱动，固定 Python guest 根也不包含驱动库。编译器及 harness 通过镜像只读复制进入 guest；受保护答案、Docker socket、数据库凭据、宿主目录和控制连接不进入 guest。现有外层 CPU/内存/PID/临时存储总上限和独立期限继续生效；该证据不等同于生产 guest 子配额。

编译镜像使用独立源码契约，包含固定归档、库、guest harness、可信通信入口及构建描述。基础 CPU 镜像不隐式携带编译器。沿用 journal 的 v1 标签形状和按保存契约清理语义，不改写旧记录。源码只经现有有界通信传入，输出仅为编译状态及有限 PTX 元数据，不输出 PTX、原始诊断或正式 verdict；断连、取消或超时必须核对原 guest 和容器清理，并通过新调用复验。

实际验证包括两道 CUDA 候选的参考实现、六份可编译但语义错误的变体、编译错误、非法输入及平台配置错误。编译成功仅证明能生成 PTX，不能证明入口可加载、答案正确、设备恢复或性能，不能生成 GPU receipt、开放网站提交或发布候选题目。正式 GPU 策略覆盖共用编译逻辑变化，旧 receipt 失效；CPU/WASI 策略保持不变。

设备允许列表、默认题库和现有服务继续保留；不占用 GPU，不设置 privileged，不以普通容器运行学员代码。后续任何需要放宽监督容器权限的方案必须重新记录取舍和验证，不能悄悄扩大此契约。

### 容器任务的版本化总预算

G27 已在现有开发总上限内验证实际 NVRTC 编译，但没有交付正式资源契约。下一步增加明确的 `container-workload-v1`：一个任务容器内的监督器、可信通信、runsc 和 guest 共同使用 0.5 CPU、512 MiB、无 swap、256 个宿主任务的总预算。它不宣称存在独立 guest 子 cgroup，也不与原宿主路径的子组计量混同；后续执行环境必须记录新的预算标识与计量范围。原 2 CPU/2 GiB/512 PID 开发配置保留为 `container-supervision-v1`，不改写旧记录的含义。

由可信服务显式选择两个固定配置之一，不接收学员提供的资源数值。Docker 元数据、PID 1 实读 cgroup 和运行时必须一致；私有只读 cgroup 继续由外层 daemon 设置，不授予写宿主 cgroup、privileged 或新的设备权限。监督启动参数绑定预算标识，journal 新记录使用 v2 保存该标识；v1 仍按原固定上限核对并清理，新控制器不能用当前预算重新解释旧对象。

实际 CPU 探针须验证节流、受控内存超限、固定可信宿主 fork 的 PID 上限、guest 临时存储上限和原进程树清理，并在故障后以新的容器重新编译。内存结果须有内核 OOM 计数或 Docker 原实例 OOM 状态支持，单独的退出码不能作为内存超限证据。任务总上限含运行时开销；若所需固定编译在此预算内不可行，应保留失败证据并重新审议版本化预算，不能悄悄放宽限制或延长期限。

机制依据为 [Docker 资源限制](https://docs.docker.com/engine/containers/resource_constraints/)和 [Linux cgroup v2](https://docs.kernel.org/admin-guide/cgroup-v2.html)，以本机真实探针为验收依据。此阶段不占 GPU、不更新历史成绩或签发新凭证；设备注入与监测、容器 worker、正式环境身份和 Compose 发布仍须继续接通和验收。

### 容器控制端的实际编译调用

G28 的任务预算与恢复已通过，但编译调用仍由宿主程序发起。复查控制镜像原构建副本发现，它只能导入编译服务类，计算 `compiler_digest()` 时缺少 `gpu_runtime.py` 等源码，不能在镜像内验证和启动编译任务。继续依赖宿主计算并传入“可信摘要”会削弱固定制品核对，也无法完成后续容器 worker 的交付。

控制镜像应包含编译服务契约的完整源码闭包，由镜像内代码重新计算摘要；不能执行缺失时跳过校验，或从宿主 Python 借用模块。新增可信编译调用封装，连接原 journal、固定编译镜像、`container-workload-v1`、原启动握手和有界协议。校验请求后才创建任务，开始回调成功后才发送源码；错误、取消或正常结果都须完成原 guest/任务容器清理与 journal 归档，无法确认时保留记录并传播故障。一个调用实例只执行一次，不把旧 nonce 或连接用于下一任务。

调用只返回受约束的编译状态、PTX 大小/摘要及实际镜像/预算身份，不返回 PTX、原始诊断、正式成绩或就绪。它与正式 GPU 环境身份分开；后续 GPU 运行仍须设备注入、持续占用监测、完整启动与凭证，不将无设备编译产物注册为 GPU 执行后端。

真实验收从受限控制容器发起编译，在不同任务容器的 gVisor guest 中运行 NVRTC，覆盖两份候选参考解、语法/配置错误、请求前拒绝、开始前取消、编译后取消、控制器退出和原记录接管，故障后用新实例重新编译。输入只通过测试自有私有目录交给可信控制端，再走现有通信；不得放入命令行或普通日志。最后重放原控制端 UID、共享锁与跨版本接管检查，保留失败和清理证据。现有宿主编译入口、历史制品和 CPU/WASI 策略不变。
### 本地驱动制品与无设备检查（G30）

容器化编译已接通，但编译镜像有意不包含 CUDA 驱动。下一步建立独立的驱动制品：从本机已安装且不可由普通用户改写的 x86_64 驱动文件生成私有构建快照，固定内核报告的驱动版本、每个库的大小、SHA-256 与 SONAME。初始 CUDA/PTX 配置包含 `libcuda`、PTX JIT、NVVM 和 GPU compiler 四个库；缺少库、架构/SONAME 不符或快照期间发生升级时拒绝构建。不要从客户端或学员提交选择文件，不安装或修改宿主驱动，不发布本机驱动二进制。

新镜像使用独立源码摘要与驱动清单摘要，不能作为原来的无驱动编译镜像使用。镜像内固定 runsc 必须报告支持该精确版本；不使用覆盖 ABI 或允许不支持驱动的选项。依据见 [gVisor 驱动兼容与设备范围](https://gvisor.dev/docs/user_guide/gpu/)及 [NVIDIA compute 库清单](https://github.com/NVIDIA/libnvidia-container/blob/main/src/nvc_info.c)。初始清单是当前 PTX 路径的候选依赖集合；无设备加载通过不能证明实际 CUDA JIT 的依赖完备。

本阶段的真实检查始终沿用没有设备、挂载或网络的既有监督契约，在 gVisor guest 中核对清单、库摘要和动态依赖，重放固定正确/语法错误源码的 NVRTC 编译，并检查新会话恢复与完整清理。不能在宿主加载 CUDA 库，不能调用 CUDA 初始化或创建上下文，也不能将动态加载或 PTX 编译标记为硬件执行成功。旧 journal 的恢复规则不变。

设备注入仍须后续独立版本契约：仅选定 UUID 对应的 `/dev/nvidiaN`、`/dev/nvidiactl`、`/dev/nvidia-uvm`，并验证内外设备身份、持续占用、PID 对应、完整启动和任务清理。驱动升级后必须重新生成制品和完整环境凭证；本阶段不接入正式提交、就绪凭证或 Compose GPU worker。
### 控制容器中的宿主进程归属（G31）

单卡执行前必须连接持续占用监测。现有宿主监测使用 NVIDIA 返回的宿主 PID 和 `/proc/PID/cgroup`；控制容器保留私有 PID/cgroup 命名空间，不能将该 PID 直接解释为容器内 PID。[Linux PID 命名空间说明](https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)规定 procfs 的 PID 视图由其挂载所属命名空间决定；[内核 cgroup v2 文档](https://www.kernel.org/doc/html/latest/admin-guide/cgroup-v2.html)说明 cgroup 路径还相对于读取者的命名空间，因此不能把相对路径当作宿主绝对路径解析。

采用显式的控制端挂载契约 v2：在原 socket、锁和 journal 身份之外，绑定宿主 procfs 的 dev/inode 和 boot ID，以 `bind-recursive=readonly,bind-propagation=rprivate` 挂到固定位置，并核对所有子挂载实际只读且私有。保留原 v1 无此挂载的语义。控制端仍使用私有 PID/cgroup、无额外能力和只读根；不加入 host PID 模式，不让任务容器或 guest 看到该挂载。

固定 CPU 前提检查发现非递归 bind 返回 EINVAL；保留并递归只读挂载成功，真实记录在 `test-results/g31-proc-rprivate-prerequisite.json`，包括挂载身份、私有 PID 1、不同宿主 PID 及 `/../docker-….scope` cgroup。原失败和 Docker 要求显式 rprivate 的拒绝也已保留。较低权限 mount namespace 不能分离继承的锁定子挂载，[Linux mount 文档](https://man7.org/linux/man-pages/man7/mount_namespaces.7.html)与 [Docker 递归只读选项](https://docs.docker.com/engine/storage/bind-mounts/)解释此约束；不通过增加能力或改 daemon 绕过。

该挂载只属于可信执行平面：procfs 可能暴露操作者可读的进程元数据，且只读挂载本身不能约束所有 proc 魔术链接的目标。拥有 Docker socket 的可信控制端已有该操作者权限；观察接口仅打开固定的 `stat`、`status`、`cgroup` 字段，不读取命令行、环境、内存、fd 或 root，不接受客户端路径或在观察中发送信号。

任务归属同时依赖原设备锁、安装/journal、不可变容器 ID、启动实例、经过完整配置核对的 PID 1、进程出生时间和相同实际 cgroup。路径只作不透明身份比较，禁止借助 `..` 访问其他文件系统位置。记录替换、进程退出/复用、容器重启、挂载/boot 身份变化或读取失败时均拒绝，不能认为设备空闲或清空预约。独立原记录恢复继续负责终止，而观察器不停止未知 PID。

先用真实 CPU 任务和外部固定进程验证两个 PID 视图、任务成员/外部成员、退出和接管边界，再连接 NVIDIA 库与单卡执行。此阶段不查询或占用 GPU、不签发 receipt；真实设备 PID 来源和 CUDA 清理仍须后续硬件验证。

### 容器内 NVIDIA 上下文观察（G32）

下一步将管理查询与 G31 的原任务归属连接。采用独立的本地 NVML 库快照，只包含与内核驱动匹配且经过静态 ELF/SONAME、大小和 SHA-256 校验的管理库，不把 CUDA 计算库加入可信控制端。固定查询子进程直接调用已审阅的 NVML v3 计算、图形和 MPS 进程接口，以取得宿主 PID；不依赖容器私有 `/proc` 中的进程名称，不接受命令或任意 NVML 方法。所有类别均须成功，未知、权限不足、不支持、列表超限和超时都不能视为空闲。

控制端挂载契约显式升级为 v3，绑定准确 GPU UUID、型号、驱动、计算能力、管理库清单及选定字符设备的主次编号。仅映射该卡的 `/dev/nvidiaN` 与 `/dev/nvidiactl`，不映射 UVM 或其他卡；保持原私有 PID/cgroup、只读 procfs、无能力、无网络和资源限制。管理接口需要设备句柄，其权限不是只能查询；约束来自固定可信代码和原执行平面，不能把设备映射或 NVML 查询称为学员隔离证明。

实际前提检查发现 NVML 590.48.01 查询时会在控制容器私有 `/dev` 中创建空的 `nvidia-caps` 目录。v3 明确允许该目录，但必须与 `/dev` 同文件系统、归当前用户所有、不可由组或其他用户写入、不是符号链接且始终为空；不能因此允许任何额外 capability 节点。原拒绝与成功查询数据保留，不新增能力或挂载来绕过此边界。

读取前后核对原控制端与设备身份；任务监测保存同一个 G31 归属对象，不能每次观察都重新认领 PID 1。空列表仍须核对原任务，任何外部占用都停止本次评测，不停止外部 PID。子进程有独立时间/输出上限，异常不产生就绪或清空预约。v1/v2 控制端和无设备任务保持原语义。

验证先对维护者选定的 GPU 0 作管理查询：比较宿主与私有 PID 容器中的身份及进程列表，并验证真实外部占用拒绝、错误设备/库/版本拒绝和原控制端兼容。仅作 NVML 元数据读取，不初始化 CUDA、不创建计算上下文、不运行内核；若当前没有外部占用，不人为启动 GPU 程序来补造此证据。真实 CUDA 进程归属和持续故障恢复仍须独占验收。

接口依据为 [NVIDIA 管理功能说明](https://docs.nvidia.com/datacenter/cloud-native/container-toolkit/latest/docker-specialized.html)与 [NVML 官方头文件](https://github.com/NVIDIA/go-nvml/blob/main/pkg/nvml/nvml.h)，实际绑定同时核对本机 CUDA 附带的 `nvml.h`。NVML 与 `nvidia-smi` 的输出稳定性区别见 [NVIDIA 查询说明](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

完整镜像重放已有十七项管理/CPU/兼容场景通过；当前没有实际外部 GPU 进程，因此未验证非空 CUDA PID 来源。另经文档复核，NVIDIA 还定义了 `O` 类及无需上下文的资源占用，不能从三个上下文列表推出穷尽空闲。该来源或等价的可靠限制必须在正式容器准入前补齐；本阶段是观察组件，不是完整占用凭证。结果和决定见 [G32](../acceptance-g32.md)、[ADR-048](../adr/048-container-nvml-observation.md)。

### 完整进程查询来源（G33）

G32 的三个上下文 API 不替代 NVIDIA 文档定义的完整 `Processes` 列表。本阶段新增独立管理制品 v2，静态复制同一安装的 `/usr/bin/nvidia-smi` 与 NVML 库，绑定各自大小、摘要、库 SONAME 和驱动版本。采用显式控制端挂载契约 v4；旧 v3 仍只允许原来的上下文观察，不能以旧清单自动获得完整占用语义。

可信控制端在同一个有界观察期限内执行固定 NVML 子程序、固定 `--version` 和指定 UUID 的 `--query --xml-format`。SMI 只使用清单内 NVML；不接受调用者参数、继承环境或任意查询工具路径。所有命令结束并通过身份校验后才返回经过投影的 PID 列表；进程名称、命令行、显存和其他原始 XML 信息不写普通日志。完整列表不按 `C/G/M/O` 过滤，未来或组合类型同样作为占用；缺失、N/A、重复字段、重复 PID、畸形数据和上限错误均拒绝。

三类 NVML PID 必须是完整列表的子集，否则认为来源不一致并关闭本次观察。不同时间采样允许出现短暂不一致，但不能据此重试为“空闲”。完整列表中的每个 PID 都沿用 G31 的原任务归属核对，包括没有传统上下文的进程。此查询不授予排他访问；其他账号仍能启动任务，正式执行必须持续监测并在干扰时丢弃结果。

只读实测比较宿主与私有 PID 控制容器的版本、设备和完整列表，验证损坏工具/库/契约拒绝、空列表下原任务核对及 v1/v2/v3 兼容。没有真实其他/无上下文进程时明确保留硬件证据缺口，不通过创建 CUDA 上下文补造数据；仍不签发就绪凭证。依据为 [NVIDIA 进程类型及 XML 查询说明](https://docs.nvidia.com/deploy/nvidia-smi/index.html)。

十九项真实镜像场景、实际 v3 查询兼容和 475 项组件检查通过；管理镜像 `CUDA Version: N/A` 的真实失败与修正、空列表范围和最终清理见 [G33](../acceptance-g33.md)，决定见 [ADR-049](../adr/049-container-full-device-inventory.md)。

### 单卡任务设备与原记录恢复（G34）

下一步把选定设备接到已有驱动任务镜像和嵌套 runsc。新增固定单卡配置，只允许所选 `/dev/nvidiaN`、`/dev/nvidiactl` 与 `/dev/nvidia-uvm`；minor 来自已核对的 GPU 身份，UVM major 来自内核注册表而非硬编码。宿主与可信控制端核对同一设备配置，任务启动后再次检查实际节点；不允许 `--gpus=all`、通配 cgroup 规则、其他卡、capability 设备或主机目录。

持久任务记录新增显式 v3，保存单卡配置和原任务总预算；v1/v2 仍表示无设备任务。恢复只按保存配置核对原容器 ID、实例、命令及 Docker 设备映射后停止/移除，不重新执行旧镜像，也不依赖当前驱动制品才能清理旧对象。新执行使用独立源码/驱动清单身份，不能借用原无设备镜像标签。

内层 OCI 只从该配置生成三个字符设备与对应规则，显式开启 nvproxy、限制驱动能力并禁止 legacy 自动注入；不强制覆盖驱动 ABI 或放宽 seccomp。原 CPU `ContainerRuntime` 不获得 GPU 配置。选定 UUID 与完整管理来源核对、原任务进程归属、开始执行登记和正确性/恢复仍是后续正式执行的共同门槛。

当前授权仅允许不占 GPU 的开发。先实现并验证记录/设备拒绝边界，再用固定 CPU 程序检查真实任务和 guest 的设备元信息、无额外卡与原记录清理；不调用 CUDA 初始化、创建上下文或运行内核。该检查不证明 CUDA 可执行、nvproxy ioctl 隔离或设备已恢复，不生成正式凭证。设备范围依据见 [gVisor GPU 文档](https://gvisor.dev/docs/user_guide/gpu/)。

实际推进中进一步明确：固定 CPU 程序的设备映射本身也需要明确授权，不能从“不占 GPU”推定允许。首次检查在只读挂载目标创建时失败；镜像预建空普通文件的修复已实现，保持运行时只读根，待授权后重放设备检查。当前结论与原始失败见 [G34](../acceptance-g34.md)。

### 容器任务的完整内核调用（G35）

在单卡任务与原记录基础上连接完整执行协议。复用已有题目/结果校验、控制器数值比较和批次计时；抽取无宿主运行依赖的消息校验与固定恢复内核供两种运行方式共用，不改写旧会话配置或历史成绩。外层可信任务接收受保护题目，guest 只得到源码、操作与输入；预期值、正式结果和数据库凭证不进入 guest。

可信控制容器先按同一 v4 管理来源确认空闲、启动受监督任务并绑定原 PID，再通过原私有连接核对准备身份。调用者的开始回调与租约复核成功后才发送源码。任务使用嵌套单卡运行时执行编译、正确性及必要的批次计时；错误后的 guest 必须停止，随后在新的 guest 中运行固定正确内核并核对答案。完整清理完成才发送结果，控制端还须按原 journal 停止/移除外层任务并重新观察空闲；任一失败保留设备隔离，不返回可结算成绩。

新协议区分任务与维护恢复，不提供任意命令、测试模式或普通容器执行回退。准备和结果绑定所选设备、驱动清单、任务预算及独立源码契约。当前步骤返回组件结果与制品信息，不伪造正式环境或启动凭证；接入 worker 时仍须版本化环境、完整启动、资源/故障探针与真实 GPU 验收。

在真实设备授权仍待确认期间，用独立无设备镜像中的固定 CPU 协议夹具验证同一可信执行流程、保护答案、取消、错误分类、恢复失败和结果扣留。夹具不编译或执行学员源码，使用独立入口与无设备服务，不能作为 GPU 镜像或正式成绩来源。物理设备映射、CUDA 与性能继续保持未验证，不能以这些 CPU 结果关闭 G34 的失败。

### 容器环境与正式任务结算（G36）

容器路径使用独立的 `gvisor-gpu-container` 环境，不套用宿主 Podman 身份。环境固定单卡配置、任务镜像、驱动及完整管理清单、控制器与任务源码、Docker 引擎/内核、编译器/运行时、会话计时规则及整任务预算；资源范围明确包括外层监督器。旧宿主环境继续按原 schema 解释，历史环境只校验保存字段与摘要，不要求其源码摘要等于当前代码。

执行适配器只接受原可信控制容器，创建 G35 的原 `KernelTask`，在开始事务后发送源码；独立恢复、清理、空闲观察和环境复核全部通过后，才将结果交给原 `GPUJobControl` 结算。失败清理必须沿同一任务对象执行，不能为了停止而重新认领 journal，数据库失败也不能把任务结果写成正式通过。容器与宿主的完整环境摘要不同，成绩不能混榜。

本步连接环境与正式执行事务，但完整启动、资源/故障探针和 worker 命令尚需后续接通。现有 receipt 严格入口继续拒绝容器适配器，网页准入也保持拒绝尚未交付的容器环境；不能通过手工导入报告或放宽类型绕过。非 GPU 验证覆盖历史成绩、精确原任务结算、实际 PostgreSQL 和控制镜像内完整策略源码绑定，不证明 CUDA 或签发运行凭证。

### 容器内固定 CUDA 启动检查（G37）

将已有十九项固定 CUDA 检查接入容器维护任务。请求只含审阅过的检查名与随机挑战，源码和预期结果由可信任务端从现有目录生成；普通提交不能传入替代源码或将检查请求混入 task 目的。复用正确性、边界、错误分类和编译后中断规则，但保留独立的容器清理报告：内层 runsc 使用私有标签，与宿主 Podman 的完整容器 ID 不同，不能改写成虚构的宿主身份来复用报告校验。

嵌套运行时在原 guest 清理期间记录清理前运行状态、原附着进程返回码、原进程树消失及状态移除。保留最初成功清理的证据，重复清理不得将其覆盖为另一次空状态观察。模块内存错误仍要求原驱动返回码 4。取消和附着退出在触发前核对原 guest 仍运行、原附着进程仍活跃；触发后必须完成实际清理，不能仅凭客户端退出通过。真实 runsc 检查发现附着进程关闭后的 guest 可能已经停止，因此清理时状态不能替代中断前观察；原宿主报告仍保留其“清理前活跃”的要求。报告必须匹配请求挑战，并等待新的正确内核恢复、完整清理和外层原记录移除后返回。任何缺项、未完成编译或恢复失败都不构成通过。

沿用无设备 CPU 验收入口，新增固定维护请求、编译后取消、附着进程退出、错误结果和恢复失败场景；CPU guest 仅处理固定向量数据，不编译或执行收到的源码。该证据验证控制路径，十九项 CUDA 的真实结果仍需明确授权的独占卡。完成此接口不开放 receipt、网页准入或 worker；完整资源、整控制器故障和部署生命周期继续单独接通。

### 容器资源与隔离启动检查（G38）

维护协议增加固定资源检查，请求只含随机挑战，不接收端口、路径、命令或预算。可信任务创建私有 canary 与本容器回环监听器，固定 guest 检查只读根、私有文件不可见、网络隔离、零能力和最小环境；GPU 路径另核对所选物理设备节点和 CUDA 枚举的唯一 UUID、型号、架构。CUDA API 签名以 [NVIDIA 设备管理文档](https://docs.nvidia.com/cuda/archive/12.8.2/cuda-driver-api/group__CUDA__DEVICE.html)为准；CPU 验收入口不加载驱动、不映射设备。

资源报告使用独立 schema，覆盖身份、输出、超时、取消、附着进程退出、CPU 节流、临时存储、实际 OOM 与进程上限。配额始终是包括监督器的整任务 0.5 CPU、512 MiB、禁用 swap、256 个任务，不声称 guest 独享，也不等同显存。进程上限沿用固定可信 fork 探针，在自有私有任务 cgroup 内运行并恢复原任务数；其他探针在嵌套 runsc 内运行。每项之后创建新的固定身份 guest，共保留十七个原 guest 清理记录；报告严格检查测量值、挑战、原设备及记录顺序。

沿用原绝对期限，预留独立正确内核恢复和清理时间。取消及附着退出在注入前记录原 guest 活跃，注入后必须完整清理；任何检查、恢复或原记录移除失败都扣留报告，不生成 receipt。无设备镜像重放同一资源控制器与固定 CPU 恢复，验证实际限制和错误后的恢复链；不把它记作 CUDA、显存或正式 GPU worker 验收。完整控制器故障、启动发布和部署入口继续接通。

### 容器控制器故障与新实例恢复（G39）

补齐控制器退出、通信断开和独立监督期限三种固定维护检查。共用固定名称/挑战/触发协议，不允许任意命令或故障注入到普通提交。可信任务先在活跃 guest 中运行固定正确内核，由控制器比较答案，并核对原 guest 与附着进程活跃，再确认已准备故障；收到匹配挑战才触发。CPU 验收采用同一流程及固定向量夹具，不加载 CUDA。

容器报告独立绑定外层实例 ID、启动 nonce、实际监督期限和原 journal 清理。监督器将子控制器异常退出映射为 70，独立期限映射为 124；不得把任何断连当作成功。通信断开后须观察到原容器仍存活，再按原记录停止；独立退出和超时则只观察原对象自行停止，不能通过手动停止来证明计时器。允许在原监督期限后短暂观察退出，仅用于已握手的固定故障，仍核对同一实例与原参数，不延长实际任务期限或放宽普通会话。

总维护预算拆为最多 90 秒故障及 90 秒新正确恢复。故障任务完成原记录清理与空闲观察后，才能在同一锁、任务与预约下创建新的维护实例；新容器 ID 和 nonce 必须不同，恢复失败不返回通过报告。保留环境复核、数据库回调、来源身份和租约边界，不签发 GPU 凭证；完整启动发布与容器 worker/Compose 继续接通。真实 CPU 验收须在故障已准备时记录原完整进程树，验证停止、目录与实例清理、新恢复以及后续正常调用。

### 容器完整启动与就绪发布（G40）

沿用 `core/gpu_readiness.py` 的完整顺序、租约短事务、凭证原子写入与最后就绪事务，按精确适配器类型选择宿主或容器实现。容器初始恢复只能操作原控制端的 journal，在 DB 异常时仍停止原对象、保留记录和预约；禁止用容器接口接管仍未恢复的宿主任务。新的维护实例使用固定启动身份；清理和完整空闲观察后运行正确恢复，整个启动通过前不释放旧预约。

容器报告按已有独立协议验证，不能套用宿主 unit/cgroup 或资源报告格式。资源阶段保留原随机挑战，十九项内核及三项控制器故障按固定顺序执行；每个任务在原记录移除、正确恢复和环境复核后才计入完整证据。初始恢复、新实例清理、任一步报告、续检或发布失败时都保持隔离，不能从旧文件或部分通过报告续跑。

容器私有凭证使用新 schema 和套件身份，额外绑定原控制端挂载、安装/daemon/锁目录、真实宿主 boot ID 与映射操作者。宿主凭证保持原含义；不能把容器内 UID 0 视作宿主 root，或把保存的成绩环境当成当前启动通过。两种模式共用私有文件与时效检查，重新取得锁、改换挂载/安装身份或更新制品后旧凭证失效。

成功发布后的心跳和领取再次检查当前凭证、原控制端与完整设备空闲观察。Web 只读已发布环境及新鲜设备状态，不读取私有凭证、持锁或访问 Docker socket。验证使用合成 GPU 身份、一次性数据库和明确的运行时替身测试事务与拒绝边界；实际 CPU 容器仅证明依赖和清理，不签发可用于运行站点的 GPU 凭证。GPU 硬件、容器 worker 命令、Compose 与发布升级仍须分别验收。

### 容器 worker 入口与数据库部署（G41）

在既有 `ContainerController`、`ContainerGPUAdapter` 和共同 `run_worker` 上提供专用 Django 命令。正常入口只接受完整 v4 管理配置、不可变任务镜像和原驱动清单，使用同一状态目录的 locks、journal 和 receipts；不提供导入收据、跳过完整启动或 CPU 模拟执行选项。停止信号仍先进入共同取消/隔离流程，退出前保留原锁。

单独构建包含锁定 Django/psycopg 依赖的可信 worker 镜像，保留开发控制夹具的原入口。镜像携带固定 Docker CLI、完整管理制品、应用源码及源码身份；不带数据库密钥或当前状态。依赖使用现有带哈希的 `requirements.lock`。容器内核对源码与原控制器契约后才启动应用，旧控制端和原 journal 语义保持兼容。

Web 基础镜像同样携带完整执行摘要所需的脚本，在构建时进行纯文件检查，并在默认 Compose 首次启动和重建后比较 Web/CPU worker 的摘要。该检查不访问设备，也不改变 CPU 沙箱策略；避免源码环境通过而镜像部署后 GPU 准入始终关闭。

数据库配置从原私有状态目录的有界、无链接、0600 配置读取，不把连接字符串放进 CLI、Compose 展开结果或错误日志。该入口使用 PostgreSQL 与已有 worker 最小权限，不自动迁移、创建数据库或导入题库。独立的只读配置/数据库检查不访问 GPU、不签发 receipt、不发布 ready；它只证明部署依赖、连接、当前列结构和权限可用。

提供独立 Compose worker 文件，连接维护者已准备的应用 PostgreSQL 网络。默认 SQLite 单机 Compose 的数据不能直接混用。可信控制器保留只读根、rootless 映射、原 socket/状态/procfs 挂载和 1 CPU/512 MiB/128 PID 限额；只控制端获得数据库网络和私有凭据。任务/guest 的无网络、无数据库和无 Docker socket 边界继续由原契约验证。原挂载或设备条件不满足时关闭启动，不增加宽松回退。

本批先验证命令的完整生命周期及失败拒绝、实际 PostgreSQL 最小权限、真实无设备镜像中的应用启动与数据库连接，并保留原控制端跨进程恢复检查。GPU 执行方法在组件测试中仍是明确替身；无设备镜像/Compose 配置通过不能替代完整硬件启动、性能、队列或升级验收。实际设备映射与常驻 GPU 服务启动继续等待授权和独占条件。

专用入口、联合镜像构建及上述非 GPU 验证已完成；Web 打包遗漏的修复前后实测与默认 Compose 重放见 [G41 验收](../acceptance-g41.md)。完整设备运行和升级范围仍单独保留。

### GPU 镜像进入不可变发布包（G42）

现有 format 1 只绑定 Web 和 CPU/WASI worker；G41 的本机构建目录还不能作为跨主机、可审查的升级制品。扩展同一发布流程为可选 format 2，包含同一冻结源码产生的 Web、CPU worker、可信 GPU worker 与单卡任务四个不可变镜像，以及驱动、完整管理制品和各自的源码契约。默认 CPU 发布继续生成 format 1，新控制器仍验证旧包，不改写旧制品或把新增文档变成其必填文件。

不采用独立、可随意组合的 GPU 附加包，避免升级时将不同策略的 Web 和 worker 混装。构建从一次捕获的源码执行固定构建器；GPU 构建只读取受信库文件，不查询设备或运行 CUDA。发布包不包含 GPU UUID、数据库凭据、状态目录、锁、journal 或 receipt。四镜像共享原三文件目录结构，既有摘要信任入口保持不变。

归档验证在任何 Docker 导入之前完成，检查完整层内容、角色、平台、用户、入口及契约标签。GPU 元数据保存有序源码范围，并从归档字节重新计算摘要，不执行归档里的 Python，也不使用当前工作树替代旧源码。worker 的 UID 0 只适用于其受验证的 rootless 映射；任务仍为原非 root 配置，不能将这一例外扩散到 Web/CPU worker。

制品层先完成真实四镜像构建、导出/导入、无设备应用预检与原 CPU 评测。现有协调器在尚未接入 GPU 生命周期时明确拒绝该格式的激活，不允许悄悄只启动其中两个服务。后续协调升级仍须关闭入口、排空全部物理预约、停止原 GPU 控制器、保留原锁/journal/安装身份，并对候选数据库执行新的完整启动；开放前后的恢复分别沿原部署决策，不能把本批制品验证当作 GPU 或升级验收。

上述制品与非 GPU 验证已完成，实际归档、旧 F 包兼容、导入后的九项 worker 检查及完整 CPU/浏览器结果见 [G42 验收](../acceptance-g42.md)。冻结源码逐文件对应实现提交，验收记录目录的原始失败和最终修正也一并保留。
