# RFC-037：控制器退出观察共享检查时钟

日期：2026-11-15。状态：原代码复现、修复、371 项相关检查及五组实际 CPU/runsc 故障检查通过；新双镜像完整 GPU 重放待完成，见 [ADR-091](../adr/091-controller-fault-observation-checkpoints.md)。

`62eb989` 沿原本地 GPU 状态运行 1126.844 秒，未再出现进程归属失败，但最后的 service-deadline 检查在 EOF 后的 `state()` 超过原观察期限。原维护容器 `bd38ec07…` 的 Docker `die` 事件为 11:32:44.054974 UTC、退出码 124；原硬期限约 11:32:43.379107，观察期限约 11:32:48.379107。墙钟换算是事后对同一单调时钟的估计，不代替执行时的原绝对期限。原正常恢复完成、GPU 0 空闲；原记录在 `test-results/namespace-handles-local-diagnostic-2026-11-15/observation-1/`。

`Channel.expect_eof()` 周期性执行完整状态/租约/设备检查；返回 EOF 后，故障观察又立即执行同一完整回调。完整来源观察比原受限 PID 视野更昂贵，两次相邻完整回调可能耗尽原五秒结束窗口。不能增加期限、容差、通过事后 Docker 事件补签成功，或主动停止容器来证明独立监督。

修复复用 `Channel.check()` 的现有 0.25 秒检查时钟：EOF 后及等待终止时先核对该时钟，再读取新的原容器状态并检查原绝对期限。刚完成的完整回调不重复执行，时钟到期则仍执行完整回调。最终状态不能从上次回调缓存取得，仍核对原 ID、完整监督参数、OOM 状态、锁、socket 和实际退出；清理及新正确恢复照常执行。

先用明确耗时的检查回调复现原失败，验证新的状态读取、过期回调、替换/错误退出及边界时间仍失败，再重放实际 CPU 控制器故障与新匹配镜像的完整 CUDA 启动。模型、CPU 或历史退出事件都不算完整 GPU 成功。
