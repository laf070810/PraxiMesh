# RFC-022：GPU 发布协调与原数据库恢复

日期：2026-11-01。状态：实施中。对应 PRD R-09、R-16；延续 [RFC-005](005-deployment-coordination.md)、[RFC-021](021-gpu-container-supervision.md) 与 [ADR-058](../adr/058-gpu-release-artifacts.md)。完整 GPU 激活、真实队列和升级验收尚未完成。

节点绑定决策已采用，见 [ADR-059](../adr/059-gpu-deployment-attachment.md)；当前实现与验证范围见 [G43](../acceptance-g43.md)。

## 问题

四镜像制品已绑定同一冻结源码，但当前协调器只管理 Web 和 CPU worker。GPU 控制器的锁、安装身份和活动容器记录跨容器持久存在；数据库中的设备预约也不能因为任务结束、数据库克隆或容器停止而自动清空。候选代执行失败后，拿旧代数据库恢复候选任务，会丢失原预约的对应关系。

目标是在同一发布操作中协调 Web、CPU worker、GPU worker 和任务镜像，继续保留排空、维护页、最小数据库权限、曝光意图先落盘和已曝光后保留当前数据库的规则。不能通过允许普通容器执行学员代码、导入旧 receipt 或省略启动检查实现升级。

## 一次性节点绑定

部署配置可显式增加 `gpu`，只包含原私有状态绝对路径 `state`、本地 rootless `docker_socket` 和完整规范 UUID `device`。默认 CPU 配置不变。`attach-gpu` 是独立的绑定动作，不启动 worker、不查询设备、不发布就绪，也不修改数据库或代理。

已运行的 CPU 站点只允许通过此命令增加 `gpu` 字段；其余配置的摘要必须仍与原记录一致。不能用这个入口顺便更改密码、数据库、网络或代理。新站点可以在 `init` 后显式绑定。未完成绑定时拒绝发布和恢复等变更，原站点仍可提供读取。

首次绑定只接受为本次新安装准备、尚无 worker 配置和执行记录的 v4 状态。准备工具增加 `--prepare-only --initialize`：读取已获授权设备的元数据并建立原身份，暂不写数据库连接。这个初始化仍需要设备授权；不能把它当作无设备检查，更不能为已有控制器创建第二套锁。

协调器核对同一操作者、目录/socket/锁 inode、rootless daemon、宿主 procfs/boot 身份和完整观察清单，并持有原设备文件锁。认领记录同时绑定部署站点 ID 与部署状态目录身份。先在部署日志保存认领意图，再原子创建节点侧私有记录，最后确认配置摘要；重复或中断恢复只能接受相同意图和相同身份。其他站点、无对应意图的记录、旧 worker 配置、活动或历史任务记录均不能自动认领。已有 GPU 安装的迁移须另行验证原数据库和恢复状态，不通过删除记录来适配首次绑定。

## 代际配置与运行

### 配置读取与发布身份

沿用现有 `worker.json` 格式，在已经绑定协调器的原私有目录增加 `deployment-generation.json`。记录绑定完整原 owner 的规范摘要、站点、发布代、数据库、发布包摘要、worker 镜像及源码契约，以及完整 worker 配置的规范摘要。节点绑定文件存在时，缺失或不匹配的代际记录不能按独立 worker 配置继续运行；未绑定的独立部署保留原行为。

读取时只核对原私有文件、目录/锁 inode、安装身份和 mounts 摘要，不查询设备。记录的数据库和 worker ID 必须来自同一实例/代，数据库登录必须是该实例的 worker 角色。实际 worker 镜像校验返回其源码契约，随后与代际记录核对；不能用另一个发布代的配置启动当前镜像。

worker 在取得原设备锁后再次读取并比较完整配置和代际记录，关闭 Django 初始化、配置读取与持锁之间的变更窗口。元数据与配置过渡中不一致时失败关闭；协调器的持久切换须在原锁、实际停止和原数据库无预约的检查下完成，再启动新 worker。生成配置前要求冻结发布包的 execution/controller/worker 源码范围包含此绑定协议；旧四镜像包仍可校验，但不能为不识别该协议的旧 worker 生成协调器配置。身份检查不提供激活命令；内部写入事务与 worker 生命周期见下文，实际数据库、容器运行和完整部署仍待验证，四镜像发布拒绝继续保留。

GPU 代保存实际 worker 容器名/ID、发布摘要、所选节点与 worker 配置摘要；任务镜像和驱动/管理清单来自已验证发布包，不能独立替换浮动标签。数据库连接由协调器的当前代 worker 角色派生，仅写入原私有 `worker.json`，不进入容器参数或日志。

配置切换必须持原设备锁，并保存原摘要、目标摘要、所属代和数据库的持久意图。只允许恢复意图中的前后两个精确状态，遇到未知文件内容立即停止。切换前须确认原 worker 停止、原活动 journal 清理完成，以及原数据库不存在设备预约；停止容器本身不证明这些条件。

### 双文件配置的持久切换

切换由协调器内部入口执行，仍不提供绕过完整 GPU 发布的 CLI。持原协调器锁和设备锁，实际代理须处于维护状态；已登记 GPU 容器须为同一完整 ID/镜像且已停止、禁止自动重启，未登记对象拒绝处理。原任务 journal 不能含活动记录或未知残留。原配置所属库和目标库都须保持本次暂停 token、无排队/运行任务和无物理预约，检查不因任务已经结束或删除而省略预约。数据库操作锁、设备表写锁及队列行锁贯穿文件切换，不给 Web/worker 增加权限。

部署日志先保存原/目标的非敏感发布上下文、配置摘要、两个文件的字节摘要及固定意图 ID，数据库凭证仍仅写 `worker.json`。节点随后建立私有 `deployment-config-transition.json`；其存在即阻止 worker 配置读取，包括尚未写完整的标记。然后依次原子替换 `worker.json` 和代际记录，确认两个目标文件后先持久保存新的活动配置，再移除并 fsync 节点标记，最后确认部署日志。各临时文件只属于原意图；重试只可处理匹配的完整内容或其已写前缀，不能清理未知文件。

恢复只接受“原/原、目标配置/原记录、目标/目标”三种顺序状态，不允许倒序组合或缺失发布中标记的部分结果。必须使用原操作 token、原绑定及完全相同的目标；不能中途换库、换发布或旋转凭证。先完成原意图，另一次经过原库清理的事务才能恢复上一代。此状态机不自行决定曝光前后回退方向。

新四镜像包显式声明 `worker_configuration: generation-pair-v1`，用于确认 worker 会拒绝发布中的私有配置；旧包保持只读校验兼容，但不能进入新的配置发布。仍须完成真实 PostgreSQL、镜像、运行中排空与整个 GPU 升级矩阵，才能开放激活。

### worker 容器的持久生命周期

无设备预检与正式 worker 使用同一固定镜像和资源契约，分别记录容器。预检仅只读挂载原状态及连接内部数据库网络；不挂 socket、宿主 procfs 或设备。正式 worker 复用原状态/socket/procfs 与既定单卡管理映射。数据库凭证不进入 CLI 或容器环境，禁止继承操作者 Docker 客户端配置的代理设置。

创建前持久保存原发布、配置记录、网络 ID、固定镜像配置摘要、专用意图标签和参数。创建后先验证完整运行契约、持久登记完整容器 ID，再允许启动。创建结果未确认时只可找回同一意图且从未启动的对象；缺失的已登记对象、未知同名对象或变更的运行契约均保留并拒绝，不能按名称重新认领。

启动先在原设备锁下确认完整配置与预检结果并记录意图，再释放设备锁，允许正式 worker 自己取得同一把锁。协调器继续持部署和数据库操作锁；记录启动前时间，启动结果仅接受同一容器的新启动实例。进程在确认前退出时保留失败，不能把容器退出当成预检成功或 GPU 就绪。无设备预检的通过必须来自固定 `--check` 容器正常退出，并绑定本代完整配置。

停止不抢占正在运行的 worker 所持设备锁。先记录原 ID、运行契约和启动时间，再只停止该对象，最后确认同一实例已退出；中断后仍沿原意图继续。停止本身不删除任务 journal、释放数据库预约、确认设备空闲或自动切换配置。后续配置发布必须确认生命周期处于已创建未启动、已停止或预检完成状态，未确认的创建/启动/停止不能被绕过。

容器沿用专用 Compose 的只读根、最小权限、私有命名空间、资源上限和固定挂载。创建前保存意图，启动前保存实际 ID，检查时核对同一启动实例。禁止自动重启旧代后读取新配置。无设备 `--check` 先验证实际 PostgreSQL 角色和表列；正式启动必须完成原二十四阶段，不提供 CPU 替身或跳过选项。

就绪须同时验证实际容器、当前代 worker ID、启动后的新鲜设备行、完整发布环境和无残余预约。等待预算覆盖完整 GPU 启动；不能复用 CPU 的短等待。Web 仅获得该代设备名单和只读发布状态，不获得 socket、设备或私有 receipt。

### 发布前的就绪观察

内部就绪检查读取原代数据库，每次快照由单条只读查询同时观察暂停归属、设备、全部物理预约和待执行队列，不持设备或队列行锁等待启动。设备须属于本代 worker、处于无预约的 ready 状态，时间不早于当前容器启动且仍新鲜；查询前后重新核对原容器、启动实例、配置与维护路由。环境核验后再确认心跳及容器，并取得最终快照；所有者、环境或预约变化不能沿用先前观察。就绪不是 Docker running，也不是旧日志中的一次成功。

冻结发布包须先完整核验。运行时源码范围及固定 runsc、NVRTC、Docker CLI 常量从归档字节的字面量读取，禁止执行归档 Python 或借当前工作树补全。发布的完整环境沿既有版本验证器检查，并与原节点、实际 daemon、冻结源码契约、驱动/管理清单及任务镜像匹配。观察不签发或读取私有 receipt，不写设备状态；正式 worker 继续独占真实启动、凭证与清理权限。

等待从原容器启动时间计算完整启动预算，协调器重试不重置期限；超时保留同一容器、任务和预约，不自动重启。成功观察只供本次协调流程判断，不能持久缓存为后续曝光凭据；曝光前仍须重新观察。此内部组件通过不解除完整 GPU 激活门槛。

## 升级与恢复顺序

### 冻结原库之前的排空保护

排空完成后，不能释放所有保护再直接调用 CPU 数据库冻结。GPU 路径先在本操作的维护路由、原配置和暂停下确认全部任务及预约为空，再停止原 GPU worker；等待停止期间不持设备或队列行锁。随后取得原设备锁，复查全部已登记容器、原启动实例与空闲 journal，再停止 Web/CPU worker。

数据库冻结在设备表写锁、设备行锁和队列行锁内撤销 runtime 的 CONNECT，并终止原 Web/worker 连接。只暂时保留本次持锁检查所用的精确 owner 后端；其他 owner 或未知连接仍然拒绝冻结。检查事务结束后必须确认没有任何目标库连接、runtime 不能重连，且没有 prepared transaction。不能把持锁 owner 连接错误地当作外部连接，也不能为此容许所有 owner 连接。

此步骤沿用 worker 已有停止意图和数据库持久 CONNECT 权限，不引入可缓存的“已排空”凭据。中断或响应丢失后，重试仍重新检查原 worker、配置、暂停、journal、全部队列与预约；不能因先前冻结成功而跳过。失败不自动 thaw、重启、取消任务或清空预约。该内部边界先接入协调器的停止/冻结调用位置；公共 GPU 激活门槛仍保留，整体发布与实际 PostgreSQL/GPU 验收另外完成。

### 候选代的真实队列检查

同一操作中的原 worker 完成恢复后，需要对新启动重新验证。检查协议增加独立 UUID 轮次；原操作 token 仍控制暂停，轮次只标识测试账号、题目和提交。轮次在入队前持久保存，重复调用继续原轮次；同一启动不能换轮次刷新期限。新启动只有在前一轮完成验证/清理后才能创建新轮次。恢复后的清理使用原轮次与新鲜设备 owner，不会误认新轮次的记录；旧轮次结果不能为新启动背书。冻结包须声明支持相同协议，旧包只读核验仍兼容。

候选验证在维护路由和本次暂停 token 下，经普通 `enqueue` 提交固定正确、错误 CUDA 程序。检查绑定本代 CPU/GPU worker、原 GPU 容器启动、设备拥有者及冻结环境指纹；只创建本操作专属的无密码账号、临时题目版本和两个正式 Submit。暂停在同一队列锁事务内暂时打开并重新关闭，其他提交者不能观察到开放窗口；不设置绕过准入、预约或真实 worker 的选项。

结果须经过现有正式成绩校验，且来源、版本、预算、时间及完整环境与本次输入一致。检查等待不持数据库行锁。超时或进程中断保留原提交、内容及物理预约，重试只继续相同提交，观察期限以最早提交时间为基准，不能刷新预算。成功前还须确认原设备恢复 ready、所有队列和全部设备预约为空；完成记录不能代替曝光前的新鲜就绪观察。

成绩通过后仍保留测试记录，协调器须先持久保存验证响应，再执行独立清理，并保存清理响应。验证确认丢失时重读原提交；清理响应丢失时仅重试幂等清理，不能重新提交或刷新原观察期限。

失败后的清理是独立动作，仅允许删除精确识别的合成账号/版本/两条终态任务。任务仍待执行、存在任何物理预约、暂停归属变化或出现其他关联数据时保留现场；不能清空预约、代 worker 执行恢复或删除真实用户数据。原 worker 重启后，先在原数据库完成恢复，再按新鲜身份执行清理；不能拿失败候选的成绩当作新启动的验证证据。

### 原数据库上的 worker 恢复

候选失败或原 worker 异常退出后，恢复必须绑定仍在私有配置中的原发布代和数据库。内部恢复流程保存原容器 ID/契约、配置摘要、操作 token 与阶段，依次停止原 worker、重新执行本代无设备预检、启动同一容器、等待完整启动和排空。中断后沿原记录继续；不能先改配置、冻结或删除任务所属数据库，再用另一个库解释残余预约。

正式 worker 每次新启动均要求当前操作的预检，且该预检开始不早于上一 worker 的实际退出时间；旧成功不能跨操作或跨停止重用。恢复流程只在原实例确认停止后重跑预检，不删除或重建同名容器。仍在启动的实例继续等待原期限；已确认退出的本次启动可在下一次恢复调用中开始新尝试，保留前次记录，不能在同一次失败调用中无限重启。成功仍须重新观察，不能把持久阶段当成就绪凭据。

曝光前只恢复当前私有配置所指向的原库，确认物理恢复和排空后才能切换；曝光意图存在时，只能恢复已曝光的当前代。未完成完整 GPU 协调的公共 CPU 发布/恢复入口也必须拒绝 GPU→CPU 或绕过 GPU 原库恢复，不能因为新包只有 CPU 镜像而忽略原 GPU 状态。

1. 校验四镜像包、绑定节点和同一 daemon，随后排空 CPU/GPU 队列与全部物理预约。
2. 进入维护模式，停止原 GPU worker；在原锁下确认原 journal 和数据库预约已清理，再停止 Web/CPU worker、冻结和复制数据库。
3. 迁移候选库并按原最小权限授权，暂停准入；写入候选私有配置，执行无设备数据库预检，再启动候选服务。
4. 等待两类 worker 的真实新鲜就绪。在暂停对外提交时，通过正常队列验证候选代的固定正确/错误 CPU 和 GPU 程序及可信成绩证据，完成测试账号、任务与物理预约清理。
5. 再次检查就绪，保存曝光意图后切换代理并验证外部健康。

曝光前失败时，先在候选任务所属的候选数据库上完成原任务恢复，才允许重写私有配置并回到上一代。数据库故障、未知容器或无法确认物理清理时，保留候选库、原配置、journal 和预约，保持维护模式，供相同操作重试。不能为了恢复旧页面而丢弃候选预约。曝光后始终保留当前代数据库；不切回曝光前快照。GPU→CPU 也必须先清理原 GPU 身份和预约，不因新包没有 GPU 镜像而忽略它们。

## 验证与交付边界

分别验证严格配置、真实文件锁、所有权竞争、每个落盘阶段的中断重试、错误代/未知记录拒绝；这些状态检查不证明 GPU 成功。无设备检查使用自有临时状态、实际 rootless daemon 和专用 worker 的 PostgreSQL 预检，不执行元数据查询或映射节点。重放旧 CPU 协调器与旧发布制品读取，不能改写旧归档。

真实验收仍须在获授权且独占的 GPU 上完成完整启动、正确/错误队列提交、迁移、运行中排空、控制器中断、候选失败回滚与曝光后恢复。只有完整生命周期接通后，才移除协调器现有的四镜像激活拒绝；组件、绑定或无设备预检成功都不能替代这道门槛。
