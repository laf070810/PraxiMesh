# RFC-022：GPU 发布协调与原数据库恢复

日期：2026-11-01。状态：实施中。对应 PRD R-09、R-16；延续 [RFC-005](005-deployment-coordination.md)、[RFC-021](021-gpu-container-supervision.md) 与 [ADR-058](../adr/058-gpu-release-artifacts.md)。完整 GPU 激活、真实队列和升级验收尚未完成。

节点绑定决策已采用，见 [ADR-059](../adr/059-gpu-deployment-attachment.md)；当前实现与验证范围见 [G43](../acceptance-g43.md)。

## 问题

四镜像制品已绑定同一冻结源码，但当前协调器只管理 Web 和 CPU worker。GPU 控制器的锁、安装身份和活动容器记录跨容器持久存在；数据库中的设备预约也不能因为任务结束、数据库克隆或容器停止而自动清空。候选代执行失败后，拿旧代数据库恢复候选任务，会丢失原预约的对应关系。

目标是在同一发布操作中协调 Web、CPU worker、GPU worker 和任务镜像，继续保留排空、维护页、最小数据库权限、曝光意图先落盘和已曝光后保留当前数据库的规则。不能通过允许普通容器执行学员代码、导入旧 receipt 或省略启动检查实现升级。

## 一次性节点绑定

部署配置可显式增加 `gpu`，只包含原私有状态绝对路径 `state`、本地 rootless `docker_socket` 和完整规范 UUID `device`。默认 CPU 配置不变。`attach-gpu` 是独立的绑定动作，不启动 worker、不查询设备、不发布就绪，也不修改数据库或代理。

已运行的 CPU 站点只允许通过此命令增加 `gpu` 字段；其余配置的摘要必须仍与原记录一致。不能用这个入口顺便更改密码、数据库、网络或代理。新站点可以在 `init` 后显式绑定。未完成绑定时拒绝发布和恢复等变更，原站点仍可提供读取。

首次绑定只接受为本次新安装准备、尚无 worker 配置和执行记录的 v4 状态。准备工具增加 `--prepare-only --initialize`：读取已获授权设备的元数据并建立原身份，暂不写数据库连接。这个初始化仍需要设备授权；不能把它当作无设备检查，更不能为已有控制器创建第二套锁。

协调器核对同一操作者、目录/socket/锁 inode、rootless daemon、宿主 procfs/boot 身份和完整观察清单，并持有原设备文件锁。认领记录同时绑定部署站点 ID 与部署状态目录身份。先在部署日志保存认领意图，再原子创建节点侧私有记录，最后确认配置摘要；重复或中断恢复只能接受相同意图和相同身份。其他站点、无对应意图的记录、旧 worker 配置、活动或历史任务记录均不能自动认领。已有 GPU 安装的迁移须另行验证原数据库和恢复状态，不通过删除记录来适配首次绑定。

## 代际配置与运行

GPU 代保存实际 worker 容器名/ID、发布摘要、所选节点与 worker 配置摘要；任务镜像和驱动/管理清单来自已验证发布包，不能独立替换浮动标签。数据库连接由协调器的当前代 worker 角色派生，仅写入原私有 `worker.json`，不进入容器参数或日志。

配置切换必须持原设备锁，并保存原摘要、目标摘要、所属代和数据库的持久意图。只允许恢复意图中的前后两个精确状态，遇到未知文件内容立即停止。切换前须确认原 worker 停止、原活动 journal 清理完成，以及原数据库不存在设备预约；停止容器本身不证明这些条件。

容器沿用专用 Compose 的只读根、最小权限、私有命名空间、资源上限和固定挂载。创建前保存意图，启动前保存实际 ID，检查时核对同一启动实例。禁止自动重启旧代后读取新配置。无设备 `--check` 先验证实际 PostgreSQL 角色和表列；正式启动必须完成原二十四阶段，不提供 CPU 替身或跳过选项。

就绪须同时验证实际容器、当前代 worker ID、启动后的新鲜设备行、完整发布环境和无残余预约。等待预算覆盖完整 GPU 启动；不能复用 CPU 的短等待。Web 仅获得该代设备名单和只读发布状态，不获得 socket、设备或私有 receipt。

## 升级与恢复顺序

1. 校验四镜像包、绑定节点和同一 daemon，随后排空 CPU/GPU 队列与全部物理预约。
2. 进入维护模式，停止原 GPU worker；在原锁下确认原 journal 和数据库预约已清理，再停止 Web/CPU worker、冻结和复制数据库。
3. 迁移候选库并按原最小权限授权，暂停准入；写入候选私有配置，执行无设备数据库预检，再启动候选服务。
4. 等待两类 worker 的真实新鲜就绪。在暂停对外提交时，通过正常队列验证候选代的固定正确/错误 CPU 和 GPU 程序及可信成绩证据，完成测试账号、任务与物理预约清理。
5. 再次检查就绪，保存曝光意图后切换代理并验证外部健康。

曝光前失败时，先在候选任务所属的候选数据库上完成原任务恢复，才允许重写私有配置并回到上一代。数据库故障、未知容器或无法确认物理清理时，保留候选库、原配置、journal 和预约，保持维护模式，供相同操作重试。不能为了恢复旧页面而丢弃候选预约。曝光后始终保留当前代数据库；不切回曝光前快照。GPU→CPU 也必须先清理原 GPU 身份和预约，不因新包没有 GPU 镜像而忽略它们。

## 验证与交付边界

分别验证严格配置、真实文件锁、所有权竞争、每个落盘阶段的中断重试、错误代/未知记录拒绝；这些状态检查不证明 GPU 成功。无设备检查使用自有临时状态、实际 rootless daemon 和专用 worker 的 PostgreSQL 预检，不执行元数据查询或映射节点。重放旧 CPU 协调器与旧发布制品读取，不能改写旧归档。

真实验收仍须在获授权且独占的 GPU 上完成完整启动、正确/错误队列提交、迁移、运行中排空、控制器中断、候选失败回滚与曝光后恢复。只有完整生命周期接通后，才移除协调器现有的四镜像激活拒绝；组件、绑定或无设备预检成功都不能替代这道门槛。
