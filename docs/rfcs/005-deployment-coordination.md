# RFC-005：发布期间的任务排空与版本协调

状态：接受；队列协议、真实五代发布、失败迁移及中断恢复验收通过。日期：2026-10-23。关联：PRD R-09、AC-04、AC-07；前置 [RFC-004](004-release-artifacts.md)，决策见 [ADR-007](../adr/007-admission-coordination.md)、[ADR-008](../adr/008-deployment-generations.md)。

## 问题与选择

固定镜像保证了一个进程的身份，却不能阻止旧 worker 从共享队列取到新 Web 的任务。目前新任务依赖匹配的健康心跳入队，worker 取任务时没有再次核对策略。直接切换环境变量也无法原子地关闭所有 Web 进程的入口。

为每个新任务记录入队时的评测指纹：backend、解释器制品与评测策略的摘要。worker 只领取与自身启动配置一致的任务。历史任务保留原记录；没有指纹的历史待处理任务不会猜测其环境或重新执行，按已有超时规则结束为平台故障。

沿用现有单行队列锁，增加持久的暂停 token 和时间。暂停与入队使用同一个事务锁：暂停返回后，不会再有并发请求越过入口；已经提交的事务仍是有效任务。暂停只影响 Run/Submit，阅读、登录、私有草稿和已入队任务继续工作。没有自动到期解锁，部署进程退出不能意外重新开放执行。

管理命令提供 status、pause、drain、resume。调用方提供 UUID token；另一部署不能覆盖或解除当前暂停。drain 先暂停入口，再等待所有排队与执行任务结束，有明确期限；超时或中断保留暂停，不删除任务、伪造完成或杀死正常执行。resume 要求相同 token、显式开启评测、匹配且新鲜的健康 worker，以及没有其他策略的待处理任务。命令通过受限的维护通道运行，不提供网页管理接口或让学习者接触 token。

## 服务切换与边界

单主机部署协调器校验发布包、记录持久部署状态、暂停并排空、停止旧 worker，然后安排迁移、启动候选版本、检查真实隔离与核心功能，再激活代理和恢复入口。不能同时让两个策略争抢没有身份边界的队列。

数据库变更需要独立备份与恢复验证。候选 schema 必须在隔离副本验证；恢复旧镜像不等于数据库逆向迁移。恢复旧库应限制在外部流量仍被维护页隔离的阶段；新版本开始接收用户写入后，不能把旧数据库快照自动切回而丢失数据。此边界由协调器和恢复 journal 执行，单独的队列命令不代表完整发布成功。

### 协调器实施方案（2026-10-23）

采用有维护窗口的单主机发布，不承诺零停机。操作者提供专属 PostgreSQL 容器、内部数据库网络、Web 入口网络和私有站点配置；工具只管理带本实例标记的资源，Caddy 使用本实例的私有 Unix 管理 socket。数据库 owner 只进入可信迁移/维护命令，Web 与 worker 保持不同最小权限角色。发布包必须先通过可信 manifest 与镜像校验。

`init` 建立私有状态目录及维护代理配置；`apply` 记录 journal → 暂停/排空 → 代理维护页 → 停旧 Web/worker → 撤销运行角色连接并确认没有其他数据库会话 → 完整备份/恢复至独立候选库 → 核对恢复内容 → 候选迁移 → 最小权限 → 清除复制的旧健康记录 → 启动候选 → 核对该命名 worker 的新心跳及真实正确/错误任务 → 恢复入口 → 持久记录 exposure intent → 开放代理。初次安装单独指定导入初始内容；升级不自动覆盖运营内容。

状态文件使用 0600、原子替换、文件和目录 fsync；同一状态目录有独占锁。维护配置也持久保存，主机重启不能自动绕过它。一次性管理容器有整体期限，超时先删除所属容器，再核对持久状态，避免后台事务迟到提交。排空失败保持暂停，不取消用户任务。

`recover` 处理同一 journal。开放候选之前的备份、恢复、迁移或启动失败，可停止候选、恢复旧库连接、重新启动并实测旧 worker 后恢复旧站。必须在任何可能把代理配置写成候选上游的动作之前写 exposure intent；此后即使 reload 返回不确定或最终完成记录未落盘，也只允许维护模式下保留候选库并前向恢复。不会自动删除旧数据库或备份，也不对已开放版本执行数据库快照回退。维护者需配置独立备份、保留政策和目标主机服务监管。

验收包含正常升级保留私有数据、失败迁移恢复旧站、协调器被杀后的同操作恢复，以及候选开放后新增草稿/删除账号仍能在恢复中保留。测试只使用隔离的合成站点。

没有使用进程内开关或各 Web 容器逐个改环境，因为它们无法定义明确的并发边界；没有使用会到期的暂停租约，因为失联的部署不应重新打开入口。选择短暂停止新评测而不是取消在途任务，保留用户已经发起的工作。

## 迁移与验证

此次 schema 增加可空暂停状态和任务指纹；旧 Web/worker 不理解这两项保护，首次引入必须先停旧应用与 worker、确认队列状态，再执行迁移并启动新版本。之后才可使用在线排空命令。现有未公开实例不自动启动或执行迁移。

验证同 token 重试、异 token 拒绝、失联/错误策略拒绝恢复、超时后仍关闭、阅读/草稿继续、运行中任务正常结束；在真实 PostgreSQL 上让入队和暂停互相竞争，证明暂停事务返回后的新调用均被拒绝，并证明不同策略 worker 不会领取同一任务。真实 WASI 演练验证暂停中已有任务完成、恢复后新任务实际通过。

### F 到当前 CPU 版本的整站验收补充（2026-11-11）

现有 `--upgrade-only` 分派只覆盖 A→B1、B1→B2、B2→C、C→D 和 D/E→F；两个已验证的 F/当前制品仍会因“前代必须早于 F”而被拒绝。历史 schema 的独立复制检查也没有运行旧应用，不能代替这条整站路径。

在同一入口增加专用 F→当前 CPU 分支。前代必须匹配已冻结的 F 迁移清单；目标只接受保留全部历史迁移并新增当前三项迁移的 format 1 双镜像制品。未知迁移组合、相同镜像、GPU 制品和改写历史均在导入镜像前拒绝；不将入口放宽为任意版本升级。

真实验收先运行原 F 应用和 worker，通过 HTTPS 建立账号、草稿、正式成绩、CPU 预约、私有版本反馈、课程/计划、令牌与主动公开的成绩。经正常协调器复制、迁移和切换后，比较原记录、版本目录、序列和权限；只对新增 `metric_kind` 作显式投影，并另验它仍为 `sequential-v1`。保留原会话、令牌幂等请求和分享范围，再验证新提交、浏览器及账号删除。新增 GPU 表必须为空，Web 保持只读；测试不查询或使用 GPU。

清单校验、投影和权限的组件结果与真正运行原镜像的整站结果分别记录。旧 F 缓存导入仍受先前审批限制；完成验收工具或当前目标制品不能解除这项限制，也不能提前宣布升级通过。

## 官方依据

- [Django migrations](https://docs.djangoproject.com/en/5.2/topics/migrations/)：PostgreSQL 支持 DDL 事务，但多次迁移和非原子迁移仍需独立恢复设计。
- [PostgreSQL pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html)：在线一致备份并不停止其他写入，不能据此假设切回旧快照不会丢数据。
- [Caddy reload](https://caddyserver.com/docs/command-line#caddy-reload)：支持运行时配置切换；代理切换与数据库状态仍需应用自己的协调。
