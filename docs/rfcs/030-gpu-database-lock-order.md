# RFC-030：GPU 控制事务与部署检查的表锁顺序

日期：2026-11-15。状态：已实施，真实 PostgreSQL 复现及修复验证通过；原站点恢复及新版本候选队列已通过，决策见 [ADR-084](../adr/084-gpu-control-table-lock-order.md)。

## 问题

`9cc50bc` 的原临时 GPU worker 完成全部 24 阶段并发布就绪后，在首次候选队列检查期间于心跳 UPDATE 退出。原 PostgreSQL 日志确认锁等待超时；源码路径为 `core/gpu_resources.py:133`。候选检查已留下原轮次和两个测试提交，不能丢弃它们或复用旧就绪证明。

控制事务先以 SELECT FOR UPDATE 取得设备行锁和 ROW SHARE 表锁，之后 UPDATE 需要 ROW EXCLUSIVE。候选检查的 SHARE ROW EXCLUSIVE 与前者兼容、与后者冲突：它可以先取得表锁再等待设备行，阻塞原心跳的锁升级。须用两个真实 PostgreSQL 事务复现，不能仅按错误文本推定全部原因。

## 调整

`bounded_database` 在设置原局部超时后、读取任何设备行之前，先取得 ROW EXCLUSIVE 表锁。该模式不阻止普通查询；同类控制事务仍可并行，具体设备与任务仍按原行锁顺序串行。部署检查保持原完整设备清单锁。现有 GPU worker 已有该表所需 UPDATE 权限，不扩大任何表、列、序列或转授权限，不延长 250 ms 锁等待及 1 s 单语句期限。

历史 worker 的在途恢复继续使用原镜像、原启动和原轮次。若需清理已终态的旧候选，可只对已经核验的旧控制源与命令源，使用其原 CLI 已支持的较短数据库等待；清理失败保留原任务，不重建轮次、不刷新验证期限、不释放未确认的物理预约。该兼容只用于清理，不把旧制品当成已修复的正常发布版本。

## 验证

真实 PostgreSQL 复现表锁升级冲突，再证明新事务在取得行锁前已持有更新所需表锁；重放原超时、最小权限、设备/队列顺序与候选检查。原站点恢复后再用新冻结包完成 GPU 启动、候选检查和普通 API；已有完整启动只证明对应原镜像实例，不证明队列及升级通过。
