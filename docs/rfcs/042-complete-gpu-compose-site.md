# RFC-042：独立 PostgreSQL/GPU Compose 站点

日期：2026-11-16。状态：分批实施中，完整方案尚未验收。目标来自维护者此前要求的完整 Compose 支持；与 [RFC-041](041-public-gpu-deployment-entry.md) 的发布协调器入口分别交付。

## 交付目标

提供一个包含 PostgreSQL、Web、CPU/WASI worker 和独立 GPU worker 的 Compose 方案，可叠加本地 CPU AI。完成明确的单卡和冻结制品准备后，用统一 Compose 命令启动完整站点。默认创建独立 PostgreSQL 数据，不改写现有 SQLite 站点；两种方案的选择、数据位置、启停和维护集中在 `docs/deployment/`。

沿用同一应用、用户、知识和题目版本、队列、成绩证据及隐私规则。Web 不获得 Docker socket、设备或所有者凭据；CPU worker 只连接数据库并使用原 WASI 隔离。只有原可信 GPU worker 获得既有单卡管理、私有 socket 和只读 procfs 挂载，学员任务仍通过原隔离执行。

## 准备与运行边界

准备入口接受完整核验的冻结发布包、明确 GPU UUID、原 rootless daemon 和新的私有安装目录。保存安装意图与实际资源身份，失败继续原目录，不借用新状态跳过未完成任务。数据库、网络、卷、凭据、源版本和 GPU 状态必须归属同一安装；未知现有资源拒绝认领。只允许新空库初始导入目录，不自动覆盖现有内容。

数据库所有者只用于受控迁移、角色配置和维护。授权定义复用 `scripts/deploy_database.py`，保持列权限和拒绝转授；应用不因初始化方便而使用所有者或超级用户。固定镜像的管理命令执行迁移，不能执行归档代码或借当前不匹配源码替代冻结应用。

GPU 私有配置保持独立 Compose 与协调器两种归属的区别。完整站点所需的安装/过渡记录应有明确版本，并在 Django 初始化、原锁获取和配置复读中一起核对。旧无绑定配置仍按原范围兼容；不让旧镜像误接受新协议，也不把独立 Compose 状态交给协调器接管。

同版本启停继续原配置、数据库、锁及任务历史，每次 GPU 启动执行全部检查。版本维护必须先正常暂停和排空、确认原 worker 停止、journal 及物理预约清理，再处理数据库和配置；失败保留原资源、备份和意图。不能在 `compose up` 时对仍有工作或来源不明的库自动迁移，不能删除锁或修改历史记录来通过检查。

## 实施前需要确定的复用点

- 复用现有数据库角色、冻结和恢复代码，明确初始化容器与宿主准备工具各自负责的步骤，避免另写宽泛授权 SQL。
- 核对独立 worker 配置的旧写入兼容与完整快照范围；如新增安装协议，先形成 ADR，补齐真实文件、进程和 PostgreSQL 保护检查。
- 明确 Compose 启停与版本维护的资源归属，覆盖同名替换、配置响应丢失、未完成 GPU 任务和数据库失败；不能将协调器的测试直接算作该方案通过。

## 必须完成的验收

已实现独立 PostgreSQL 应用入口、持久数据库初始化与宿主安装标记，以及冻结包准备和四种服务组合。原初始化增量 `7e1aff0` 已通过冻结镜像构建、十项无设备 worker 与完整 CPU 应用；新增宿主标记另有 27 项真实 PostgreSQL 与 46 项文件/配置检查通过。后续整站 Compose、GPU 和版本维护仍按下列范围分别验证，操作入口集中在[PostgreSQL Compose 指南](../deployment/compose-postgres.md)。

先验证配置、归档和权限拒绝，以及无设备初始化、同版本重启、完整 PostgreSQL schema、最小角色、目录和数据保留；随后在明确授权的独占卡上运行真实 Compose GPU worker、完整启动、两题参考解/错解 API、正常停止与原状态恢复。AI 叠加、Web/worker 挂载边界和实际页面也须覆盖。

初始化通过不等于 GPU 就绪，队列和成绩不能使用替身。版本维护与失败恢复须另行实测；未完成前不把本 RFC 或生成的 Compose 文件标成全功能交付。当前运行中的临时站点和公共 CLI 候选不因该设计而改变。
