# RFC-019：共享学习体系中的 CUDA 内核评测

状态：实施中，尚未开放提交。日期：2026-10-30。对应 PRD §2.2 C、§4.2/4.4、§8、R-16 和 AC-04/08。基础环境证据见 [RFC-018](018-gpu-environment-probe.md)。

## 契约与可信结果

新增 `cuda-kernel-v1`，语言为 CUDA C++，首先覆盖 float32 向量加法和行主序矩阵乘法，提供基础实现与优化练习。题意明确内核参数、网格/线程块、数组边界、浮点容差与资源预算。内容仍使用现有不可变题目版本、知识关系、Run/Submit、私有源码和学习进度。

学员只提交设备内核源码。固定 NVRTC 在 gVisor 内将其编译为 PTX，固定 Driver API 驱动加载内核；不链接或运行学员的宿主 C++ 程序。编译选项、入口和驱动代码由平台固定，内容不能提供 checker 或可执行插件。输入允许进入 guest，预期结果和容差比较留在可信控制器。编译、执行和错误变体都必须经过相同隔离，不允许宿主编译学员源码或普通容器回退。

所有值、形状、网格、输出、源码、编译和执行时间都有独立上限。错误区分语法/编译错误、答案错误、运行失败、时间或内存超限以及平台故障。隐藏用例不返回名称、数据、原始编译日志、异常、输出或中间缓冲区。公开 Run 不能生成正式学习证据。

## 性能与可比性

正式性能使用可信控制器测量的固定批次执行墙钟时间；编译和初始化耗时单独报告。采样包括预热、重复批次及中位数，明确它包含控制通信和同步成本，不称为纯 kernel 时间。guest 自报耗时或分数不作为正式证据。

性能记录绑定题目版本、测试/基准版本、样本量与重复次数、硬件型号和设备 UUID、驱动、编译器、编译选项、运行时/制品/策略摘要及资源配置。只在相同可比性键内排序，正确性不通过不获得性能成绩。沿用自愿公开、撤回与账号隐私规则，不并入 CPU 的统一通过数/速度榜。

执行会话采用逐条请求/应答协议。控制器先发送源码并等待固定编译完成帧，再逐个发送输入，答案不进入 guest。单次请求、协议帧、累计输出、编译和整个会话分别受限，等待时持续调用取消/租约检查。客户端进程退出不能代替容器终止；会话清理始终检查自有容器状态，必要时终止并等待实际退出，失败则保持设备停用。

第一版性能配置固定选用正式测试中工作量最大的一个输入（向量元素数或矩阵乘加项数，同量取最先出现者），只在全部正确性检查通过后采样。预热 2 批，测量 5 批，每批在固定输入上重复执行 16 次，控制器从发送批次请求到收齐输出帧计墙钟并取中位数。每次内核调用前重置输出缓冲区，并同步执行；每批仍返回输出供控制器比较。结果明确为含通信、缓冲区分配和同步成本的批次时间，不称为纯内核耗时；编译/初始化单列。固定输入的缓存优化属于此基准条件，不外推为其他输入或规模的速度。

初始会话上限为 Run 60 秒、Submit 120 秒，编译 15 秒、每次请求 5 秒，余下预约用于环境准备与清理；这些值须通过真实设备样例和超限用例验证后才能用于正式 worker。正式会话不启用包含源码或原始日志的诊断环境变量。组件探针复用同一会话实现，继续与正式启动 receipt 和网站准入分开。

### 自愿公开的 GPU 计时榜补充（2026-10-31）

GPU 成绩复用现有公开主页、`SharedResult`、确认预览、撤回和导出。共享记录新增固定的指标范围：旧记录和旧客户端写入默认为顺序测试进度，只有新的明确确认才能记录 GPU 计时分享。新增字段保留数据库默认值，防止旧 CPU 写入因为新增非空列失败；此兼容检查不等于整站回退验收。新增记录类型必须同步经过公开预览、权限和成绩验证，不能把旧分享自动扩大为公开计时。

GPU 分享仅接受 `verified_evidence` 校验过的完整正确 Submit，另核对不可变题目快照摘要；Run、错误解、重复批次错误、平台故障、缺失或矛盾采样均拒绝。每次公开读取重新校验，记录损坏后从详情、主页和榜单消失。仅公开正确性计数、批次中位数、预热/采样/重复数量、版本与不透明环境指纹；不公开设备 UUID、型号/驱动、原始环境、样本数组、编译耗时、源码或测试。

榜单使用 `(题目版本 ID, 完整执行环境指纹)` 分组，GPU 指纹已包含设备身份、编译器、驱动、制品、评测协议和资源条件；不与 CPU 进度排序合并。为使显示与并列规则一致，GPU 中位数按十进制四舍五入至 0.001 ms，值越小越好，同值同名次。每位参与者只取自己主动分享的最好成绩；相同成绩用分享身份稳定选择一条代表记录，不使用私有提交替换。统计范围为所有仍公开的记录，撤回后立即重新计算。

说明明确计时包含控制通信、缓冲区处理和同步，不能视为纯内核时间或跨设备加速比。固定输入、最佳公开尝试、主机负载及设备状态会影响可观察结果，不将榜单当作掌握程度或严格基准认证。中英预览和榜单在窄屏与键盘下检查。当前不占 GPU，只能使用明确的临时库合成成绩验证消费者、权限和布局；不生成真实公开成绩或硬件通过声明。

## 执行池、预算与回收

保留现有 CPU/WASI worker，GPU 使用独立路由、就绪状态和执行指纹，不能由 CPU worker 领取。初期明确分配 GPU 0，每卡一次一个任务，数据库预约和主机设备锁同时保护重复 worker。GPU 每日时间预算独立于现有 CPU 调用单位，不能混记或在重复幂等请求中重复扣额。

资源预约涵盖编译、正确性检查和性能采样。继承已实测的用户 cgroup 命名空间与可信父 cgroup 限额；固定工作负载预算必须通过实际限额及超限探针。显存预算包括输入、输出、驱动和编译开销；设备代码不得借 CPU 宿主代码访问额外分配 API。还需验证设备端分配、越界、显存耗尽与长运行内核的边界，不能仅凭正常样例推断这些限制成立。

worker 在各阶段续租并检查取消。租约失效只终止自己的任务；任务结束或服务退出必须回收专属容器/cgroup，确认设备无本任务残留，再执行设备恢复检查。未知执行状态、失联或恢复失败将设备隔离停用，预约不得因数据库超时就直接交给下一任务。不能重置共享 GPU 或终止未知进程。

主机文件锁只协调本平台控制器，不能阻止其他账号使用显卡。正式 worker 须在任务前后及运行期间检查设备占用；出现不属于自有工作负载的计算进程时停止自有任务、丢弃性能结果并保持停用。共享主机上的专用设备仍需要维护者协调独占窗口；不能把低利用率或空闲 CUDA 上下文视为无人占用。

资源实现使用同一 `Submission` 的独立 `gpu-slot-seconds-v1` 预约策略，按 Run 90 秒、Submit 180 秒保守预约整卡时段，不能与 CPU 调用单位相加。它是执行上限的预约，不冒充实测 GPU 时间；执行后不因语法错误、取消或用户错误退回额度。具体执行器的编译、运行和清理总上限不得超过预约。

设备表保存 UUID、执行指纹、worker 所有权令牌、当前任务 UUID 和租约令牌，状态分为隔离停用、可用、已预约。当前任务只保存不含用户内容的运行身份，不通过外键随账号删除而释放设备。主机使用私有目录中的每卡 `flock`，所有副本必须共用该目录，锁文件关闭后保留；新控制器取得主机锁后也先进入隔离停用，不能仅凭旧心跳过期恢复可用。数据库内所有设备操作按设备行、任务行的顺序加锁，旧所有权/租约令牌不能续租、写成绩或释放新预约。

Web 对设备表只读，worker 仅有读取、插入和更新权限。部署控制器按实际迁移是否存在授予新表权限，旧发布包保持兼容。调度层只能记录受信控制器已经完成恢复这一事实；正式 worker 必须在真实设备检查后调用恢复转换，不能把调度单元测试当作硬件验收或伪造启动 receipt。

### 网页准入与部署排空

网站用 `JUDGE_GPU_DEVICES` 显式列出允许接收任务的完整设备 UUID，默认空列表。CPU/WASI 的配置、健康及调用单位保持独立。GPU 准入要求总评测开关开启、设备位于允许列表、完整启动发布的环境与设备指纹一致、执行策略等于当前源码、心跳新鲜，且设备空闲或持有仍有效的原任务预约。旧迁移记录没有环境信息时拒绝准入；配置设备名单或单独恢复设备不能代替完整启动检查。

完整启动在同一数据库事务内发布环境和 ready 状态，设备换所有者时清空发布信息。网页只读取设备表，不读取私有运行凭证、获取设备行写锁或操作 GPU。队列在现有全局锁下检查版本、待处理数量与独立 GPU 日额度，再从健康设备中按未完成任务数选定最少负载的执行指纹；已排队任务不自动改投其他设备或环境。检查后设备失联的任务保持原指纹，不能回退 CPU。

部署暂停覆盖两类新提交。状态检查分别识别 CPU 和 GPU 策略，排空还必须等待所有设备的持久预约释放，即使关联任务已经结束或账号被删除。取消和超时仍不能自动释放物理预约。恢复准入需当前 CPU worker、已配置 GPU 池的健康设备，以及全部待处理任务和设备预约的兼容性；不通过改配置隐藏旧预约。新增状态字段不改变原 CPU 字段语义。

此增量先做数据库、最小角色权限、HTTP/API 与故障关闭验证。测试允许在一次性数据库使用明确合成设备状态，不运行 CUDA、不生成硬件凭证、不修改部署环境中的允许列表。正式 GPU 内容、浏览器 CUDA 编辑功能、真实硬件及容器化部署仍须各自完成验收。

### 任务服务与控制回调

每个正式任务使用独立的临时用户服务承载可信控制器和其整个隔离进程树。服务名与描述绑定设备 UUID、任务 UUID、预约令牌及操作 UID；控制器重启后可以凭保留的预约定位旧服务，但必须核对描述、临时服务属性、cgroup 与调用身份。未知同名服务不能停止或替换。服务使用 `Type=exec`、整 cgroup 终止、禁止自动重启、明确启动/停止期限和运行硬期限；准备、执行、恢复与清理共享同一预约截止时间，不能因重试获得新时段。服务仅启动固定可信入口，学员源码不进入命令行或日志。

运行时限由用户服务管理器执行，不依赖 Python 心跳或数据库回调及时返回。任务结束后检查服务停止及 cgroup 没有剩余进程，不能将启动客户端退出、一次 `stop` 返回或数据库租约到期作为已清理证明。该检查仍不替代设备空闲与真实 CUDA 恢复探针。组件阶段使用固定 CPU 进程树验证超时、父进程退出及重启后的定向清理，不访问 GPU。

GPU 控制回调使用单独、短事务：PostgreSQL 单次语句上限 1 秒、锁等待 250 毫秒；SQLite 连接在事务前临时使用 250 毫秒 busy timeout，并在退出后恢复。每次进入和退出检查设备锁、任务截止时间与租约；等待失败只会中止自有任务，不能续活过期预约。数据库服务端超时不保证网络故障时调用及时返回，因此任务服务硬期限仍是独立必要条件。新回调和服务组件在实际 GPU worker 接入前不打开提交入口。

### 受信运行适配器

外层 worker 保留数据库凭据，持有设备锁、任务预约和服务实例；临时服务中的可信控制器复用固定 RootlessKit/Podman/runsc 环境，在其内运行 guest 编译/驱动。两者通过私有目录中的 Unix socket 传递有界消息，外层用 `SO_PEERCRED` 核对操作 UID 与所属任务 cgroup。只有完整制品身份和环境准备通过后才发送源码与受保护测试；不将这些数据写入命令行、环境变量、日志或任务文件。guest 仍只收到源码和输入，预期答案留在可信控制器。

外层在等待各阶段时持续检查数据库租约和宿主设备占用；占用查询包括计算与图形进程，无法识别 PID 或所属 cgroup 时拒绝继续。服务内所有隔离进程须属于同一任务 cgroup；出现外部进程时仅终止自有服务，不杀未知 PID、不重置 GPU。结果只有在 guest 清理、独立正确解恢复、整个任务服务退出以及宿主设备空闲均确认后才交还 worker 结算。

适配器绑定完整离线制品、单卡身份、会话策略和控制器源码摘要；数据库任务指纹必须与此身份匹配。控制通道按连接、准备、执行、恢复、完成的固定顺序交互；只有运行时回报的制品身份匹配、外层再次检查租约并登记开始执行后，才发送源码与测试。内层给学员会话保留独立的截止时间，并从同一预约中预留正确解恢复及清理时间；不能在性能采样后重新获得时间预算。恢复使用新容器编译固定向量正确解并由控制器比较结果；恢复或清理失败丢弃先前成绩。外层在正常完成后再次核对设备空闲，数据库写入仍受租约与所有权隔离；异常时停止自有服务后进入隔离停用，保留预约供后续恢复。此组件连接不签发正式启动 receipt，也不注册 Web 题型。

每次启动只导入经完整校验的离线镜像，不在任务期间拉取网络制品。私有工作目录绑定设备/任务/预约，重启后的清理只接受该身份；保留未确认清理的预约。适配器本身不签发启动 receipt，也不改变 Web 准入；正式连接还需实际 GPU 故障与性能重放及独立的就绪门槛。

命名空间启动使用固定的环境变量白名单，不继承数据库连接、代理、容器远端连接或 Python 注入配置。RootlessKit 创建独立 user、mount、PID、network、IPC、UTS 和 cgroup 命名空间；内层完全断网，离线制品不需要 slirp/NAT。文件路径 socket 保留在外层私有目录，连接后仍由外层核对真实宿主 UID/PID 与任务 cgroup，不能信任内层报告的 PID。内层控制器只在 `/manager` 中运行，并为 guest 建立受限的 `/workloads` 父组。

任务工作目录位于维护者指定的私有根目录，名称及身份文件绑定当前服务；创建时拒绝已有目录，恢复时重新核对身份、所有者、权限和目录 inode。只有确认匹配服务已停止且 cgroup 无进程后才删除目录；不认识或仍在运行的目录原样保留。这里的文件身份与进程清理不代表 GPU 已恢复，数据库预约仍须等待真实设备空闲及正确解恢复。

先以固定 CPU 进程验证实际跨命名空间连接、大消息、环境清理、断连与独立服务期限，不调用 NVML/CUDA，也不把此检查当作 GPU receipt。命名空间选项依据 [RootlessKit 官方说明](https://github.com/rootless-containers/rootlesskit)，以本机实际进程与 cgroup 检查确认。

运行模块共用固定制品校验：完整 runsc 归档、Python OCI 图及 NVRTC 校验从探针脚本移入 `judge/`，既有探针继续调用同一实现。每次在私有工作目录准备制品、仅导入已验证离线镜像；Podman 使用明确的独立存储、空 hook 目录和指定 CDI 目录，不连接远端服务或继承用户配置。创建后、启动前核对实际镜像、运行时和隔离参数，失败不能回退普通容器。

控制命令也采用有界管道和绝对期限，等待期间处理取消；清理忽略已失效的业务回调，但仍受任务服务的硬期限约束。只有当前工作目录内、身份核对通过的容器可被终止和删除。清理须确认实际退出，再清空自有镜像层和私有挂载；容器 CLI 退出不是清理证明。

异常退出后不重新打开遗留的 Podman 数据库或调用其中记录的 PID。持锁外层先核对并停止原任务服务，确认整个 cgroup 为空；随后使用绑定同一预约、名称独立且有硬期限的回收服务，在新的 RootlessKit 命名空间中删除旧私有存储。创建存储前持久化目录 inode、预约身份摘要和内核 UID/GID 映射，回收时必须逐项匹配，并拒绝残留挂载。只处理固定的 `data/run/tmp` 目录，使用不跟随链接的文件描述符删除；缺失或不匹配的身份保留现场。回收进程没有 GPU、数据库或执行学员任务的入口，不续期任务；失败继续保留设备预约。回收服务也停止且 cgroup 为空后才删除工作目录。这个步骤只恢复文件系统，设备可用仍需外层确认空闲及真实 CUDA 正确解恢复。

worker 启动先采用新的所有权令牌接管设备并置为隔离停用，保留数据库中旧任务/预约。清理范围仅包括该旧预约的任务、文件回收及维护服务，以及每卡固定身份的启动维护服务；固定身份使无学员任务时的维护进程也能在外层崩溃后定位。全部旧服务确认停止后，才进入各自工作目录的恢复。启动正确解使用新的 `maintenance` 服务与无学员数据的 `recover` 消息，单次上限 90 秒；不续期或重跑旧学员任务。维护期间持续核对主机锁、数据库所有权和原预约，遇到变化立即停止自有服务。物理恢复成功也不直接发布 ready：设备及原预约保持隔离停用，完整启动检查和凭证验证须另行通过后才能确认可用。所有控制器副本及升级须保持同一个私有目录根和设备锁目录，不能通过改路径避开遗留资源。

### 正式就绪检查

启动检查沿用每卡固定维护身份并串行执行，异常中断后由同一启动恢复流程处理。就绪不能仅依据固定正确解：还须覆盖实际隔离与资源限制、各契约的正确解/错解、设备故障、取消/失联及后续正确解恢复。正式凭证只由完整检查入口在全部成功后写入，绑定制品、策略、硬件、主机启动身份及当前持锁所有者；部分检查和 CPU 基础设施验收不能生成 GPU 凭证。该入口仍须在授权独占卡上实际验收后，才用于正式 worker。

CUDA 部分使用固定 `check-kernel` 维护消息，只接受已审阅的用例名和外层生成的随机挑战，不接受源码、题目或命令。共享目录包含向量/矩阵参考解、针对性错解、编译及入口错误、非空公开 Run、最大尺寸、输出伪造、设备堆、非法访存、32 GiB 模块显存不足、无效 PTX、内核超时、诊断输出超限及编译后取消/附着客户端退出，共十九项。固定 32 GiB 模块针对当前选定的 24 GiB 卡；它不证明更小显存配额，也不能在更大卡上跳过后视为通过。

每项使用正式交互评测与控制器比较，受保护答案不交给 guest；外层再次核对预期 verdict、Run/Submit 区别、正数性能样本与容器清理身份。内核超时、非法访存和编译后中断必须先完成编译，准备失败不算预期故障。取消须由本次固定回调触发；附着客户端退出须由控制器终止该会话持有的进程并观察到相应协议退出，不能接受任意平台异常。两者须确认清理前容器仍在运行，再实际终止。此证据只说明已编译会话被中断，不单凭等待时间声称内核正在执行。每项随后独立创建正确解会话、关闭存储、停止整个维护服务并确认设备空闲；任何一步失败均不返回成功检查。

十九项 CUDA 检查仍只是完整启动门槛的一部分。整控制器退出、控制通道失联、独立服务硬期限及其恢复还须接入同一编排；完整集合与当前所有者验证通过前，不能签发凭证或把设备置为 ready。无 GPU 的协议测试可证明拒绝和顺序，不能证明 CUDA、性能或设备恢复。

整控制器检查使用固定 `check-controller` 请求和新挑战。内层先在仍保持打开的 CUDA 会话中编译并核对正确解，发出匹配的就绪帧，收到明确触发帧后才注入三类固定故障：直接退出控制器、关闭控制通道后停止轮询、保持连接但停止轮询直到服务硬期限。外层只在本次挑战已确认后接受 EOF；控制器退出与硬期限必须在显式停止前观察整个 cgroup 为空，硬期限还须排除过早退出。通道失联须先观察进程仍存活，再由外层实际停止整个服务。其他连接错误、额外输出或提前退出不能作为预期故障通过。

每项维护总预算上限 180 秒，最多前 90 秒用于故障与私有存储回收，其中为回收预留 30 秒；后 90 秒用于新的独立正确解服务。只有旧调用停止且目录已删除，才能用同一固定维护身份创建新的服务调用。数据库所有权回调贯穿两阶段，不延长学员预约；失败继续保留隔离停用及旧预约。硬期限观察窗口只延长到独立服务期限后的清理余量内，不改变服务本身的硬期限。CPU 验收可复用同一握手、故障注入、观察和文件回收逻辑，但必须用固定 CPU guest，结果不生成 GPU 凭证。

完整启动编排先执行既有接管与物理恢复，然后依次执行资源检查、十九项 CUDA 用例及三项整控制器故障检查，共二十四个必需阶段。每段最多 180 秒，整体上限按完整集合计算；中途失败不跳过或恢复到部分进度。保持同一主机锁、数据库所有者和原预约，每次使用相同持久维护身份的新服务调用。报告只在对应方法完成独立恢复、服务/存储清理与设备空闲核对后计入完成集合。

凭证仅由上述完整入口写入私有目录，包含准确有序的阶段集合、运行证据摘要、当前环境指纹、worker、持锁所有者、UID、内核及主机 boot ID。它由可信本机控制器保管，不是对同 UID 管理者的密码学证明；guest 无权读写该目录。文件须为本用户的 0600 单链接普通文件，目录为 0700，拒绝符号链接、路径替换、超大或畸形内容；成功写入并同步后再次读取校验。没有导入外部 JSON、单项报告或 CPU 记录来签发 GPU 凭证的入口。

凭证在本次持锁所有者内最长有效 24 小时，同时检查墙钟与单调时钟，不接受回拨或过期。设备就绪转换前至少留出一整个任务预算；凭证与完整集合校验通过后，短事务再次核对原预约并确认恢复，才允许清理旧任务账目和发布 ready。任一步失败均尝试删除本次凭证并保持隔离停用，不覆盖所有权变化；读取、期限、策略或身份失败不能刷新健康。新 worker 必须执行完整启动流程，不能凭旧文件跳过检查。正式 CLI、队列/健康接入和硬件验收仍须后续完成，测试替身生成的临时文档不能作为实际运行凭证。

空闲心跳同时核对当前设备身份和没有外部进程，再刷新数据库健康；不能只凭未过期的文件维持可用。检查失败隔离停用，不终止未知 GPU 任务。心跳本身不执行恢复，也不能释放未处理的旧预约。

资源检查通过同一受监管的适配器、私有控制器和 `PrivateRuntime` 执行。固定 `check-resources` 消息不接受源码或可执行程序；只接收外层新建的回环监听端口与随机挑战。控制器在新容器中运行审阅过的基础设施程序，核对非 root、只读根、宿主私有文件与回环网络隔离、环境清理、设备可见性、真实 CPU 节流、内存/PID/临时存储边界，以及输出、超时、取消和附着客户端退出后的清理。内核资源计数来自控制器，不能仅接受 guest 自报超限；每种故障后用新容器重新核对隔离。正式 GPU 检查还须在该资源检查之后完成独立 CUDA 正确解恢复和完整服务清理。

PID 门槛对应宿主 cgroup 的原生任务上限，不把 gVisor 虚拟进程数当作宿主 PID 数。固定可信 PID 探针只在已验证的私有控制器命名空间运行，确认工作负载 cgroup 为空后创建专用叶组并将自己移入，实际触及父组 256 个原生任务的上限，再终止并等待全部自有子进程、移回管理组并删除专用叶组；控制器核对内核拒绝计数增加及剩余任务为零。该探针不接收学员代码或路径，也不在共享宿主 cgroup 中执行。此区分依据 [gVisor 资源模型](https://gvisor.dev/docs/architecture_guide/resources/)，实际结果仍须由固定版本验收证明。

CPU 开发验收直接重放同一个资源检查模块，明确要求未准备 GPU，不加载 NVIDIA/CUDA；结果只覆盖 CPU 基础设施，不能作为正式 GPU 就绪记录。检查逻辑使用显式失败而非可能被 Python 优化关闭的 `assert`。资源检查回复必须包含准确完整的检查集合和清理记录，不能通过缺少条目或仅返回 `passed: true` 获得成功。

独立的 CPU 验收仅在固定 Python 镜像中运行平台审阅过的基础设施夹具，不加载 NVRTC、不启用 nvproxy、不映射 GPU，也不接受学员源码。它复用同一制品、隔离、管道与回收路径，检验文件/网络/设备边界和取消、输出超限后的恢复。正式 CUDA 会话必须显式配置单卡和编译器，不能沿此 CPU 检查路径执行或生成 GPU 成绩。容器参数依据 [Podman 创建文档](https://docs.podman.io/en/latest/markdown/podman-create.1.html)，仍以实际边界检查为准。

## 常驻 worker 生命周期

独立 `gpu_worker` 命令显式配置完整设备 UUID、固定离线制品和持久私有目录，沿用 `JUDGE_ENABLED` 总开关。每次进程启动都运行完整检查，不接受跳过检查、复用旧所有者凭证或导入报告。空闲心跳和领取在同一设备身份行锁下完成；正式执行回调及结果结算再次检查当前凭证、停止请求和数据库身份。

凭证临近到期时先关闭就绪，再重跑全部启动阶段。损坏、时钟回拨、代码或主机身份变化属于故障，退出并等待修正，不能当作正常续期。取消、删除或租约丢失后，只有原服务实例已确认停止，才允许独立维护恢复；恢复后在行锁下核对同一预约和仍有效的完整启动凭证，再释放该预约。清理身份异常不能通过重建服务对象继续运行。

SIGINT/SIGTERM 处理器只设置停止标志；正常控制回调负责中止执行，沿原服务实例清理。退出撤销当前所有者凭证并停用设备，最后释放主机锁；中断任务的预约保留到下次完整启动恢复，不能因退出或数据库失败直接释放。`--once` 同样完整启动、最多领取一个任务，并在退出时停用，不提供独立“签发后退出”的就绪入口。命令日志只记录固定阶段、任务 ID 和错误类别。

该命令接通宿主控制器，不代表 CUDA 全路径已经验收，也不替代后续容器化部署、题型准入与产品验收。当前阶段仅做不占 GPU 的数据库、控制流程和实际信号验证。

## 持久成绩与学习证据

GPU 正式成绩复用 `Submission` 和现有学习、课程、挑战证据入口。验收先核对正式 Submit、结束状态、执行时间顺序、已消耗的独立 GPU 预约，以及完整结果和历史执行环境的摘要；公开 Run、平台故障、未开始执行或不匹配记录不能生成完成证据。已完成记录按其保存的版本化会话配置验证，不要求历史代码摘要等于当前代码；升级必须保留旧配置定义，不能让旧成绩随工作树变化失效。

GPU 正确性用例通过后仍可能在重复性能批次中出错，因此不能套用 CPU 的“全部正确性用例通过即 accepted”关系。只有正式 Submit 的全部正确性及重复批次成功，才有控制器采样和中位数；指标明确为包含通信与同步成本的批次往返墙钟时间。编译初始化单列，不能宣称纯 kernel 时间、算力或相对加速比。不同内容版本、硬件/运行环境或策略摘要的成绩不混排，不能进入原有按用例通过量比较的榜单。

用户可见结果只投影已校验的固定字段与公开用例名；隐藏输入、答案、参考源码、原始日志和任意新增字段均不可随反馈外泄。记录验证只检查可信 worker 已持久化证据的一致性，不接受客户端上传结果作为运行证明。此阶段接通结果消费者，不绕过独占硬件验收、题型发布与提交准入门槛。

## 分批实施与验收

### CUDA 内容与发布补充（2026-10-31）

内容 v1 接受 `cuda-kernel-v1`，但不把它加入 CPU 执行分派表。Schema 约束操作、入口、用例结构及浮点容差，再复用 GPU 契约核对形状、有限数、可信预期值和 UTF-8 源码预算。禁止混入 CPU 专用字段，也不能因此放宽既有 CPU 契约。

首批向量加法、行主序矩阵乘法作为候选扩展保存在 `content/candidates/`，提供独立题意、公开样例、边界及受保护测试、参考实现、针对性错解、来源与待确认授权声明。复用现有向量、矩阵和乘法概念，新增线程索引概念、教程与学习路径。候选不进入默认 `starter.json`。

新增只读 `content_compose`：以一个完整有效内容包为基础，只追加不存在的 ID；任何重复、未解析引用或未知字段均拒绝。输出仍是现有完整 v1 包，不新增发布格式、不写数据库、不覆盖输出文件。这样可在新建验收库中试验候选，同时保留原目录；正式导入的全量撤回及不可变版本规则不变。第三方题库继续使用组织命名空间、精确依赖摘要及独立审核。

内容硬件验收通过正常 API 提交参考解的 Run/Submit、针对性错解和恢复参考解，复用 worker 的完整启动、当前凭证、准入、预算、租约及恢复；不在宿主编译，不增加可跳过检查的专用执行器。验收工具要求显式选定隔离验收站点和测试账号，以版本摘要锁定每题，逐项保存请求键、任务 ID、源码摘要与结果。失败或观察超时保留日志和已有任务，不自动重发、取消未知任务或清理站点。成功报告只记录 API 所返回的可信 worker 证据，不能作为启动凭证导入。

当前维护者要求继续不占 GPU。因此本增量只验证结构、发布事务、API 工具边界与旧题兼容；候选源码的真实编译、正确/错误程序和完整 GPU 队列验收必须等独占硬件条件恢复。不能因静态通过而发布默认题目或宣称硬件成功。

1. 实现有界 CUDA 契约、受保护比较和固定编译/执行驱动，在 GPU 0 实跑参考解、针对性错解与错误分类。
2. 接入独立运行时指纹、GPU 预算、设备预约和队列/租约/取消；验证并发 worker 与旧 CPU 行为。
3. 注册正式题型与真实探针，纳入策略摘要和不可伪造的启动验收；补齐内容、页面、正式结果和可比榜单。
4. 验证显存/CPU/内存/PID/输出/超时、取消/失联、设备回收与故障关闭；进行 PostgreSQL、真实队列、浏览器和部署验收。
5. 提供明确的容器化 GPU worker 部署入口，更新集中部署指南、README、AGENTS、需求追踪及 ADR。所有门槛通过前继续关闭 GPU 提交。

本 RFC 不将阶段性组件测试标为完整交付。正式策略及结果结构必须在上述故障和性能检查后固定。NVRTC 与 Driver API 以固定版本的 [NVIDIA 文档](https://docs.nvidia.com/cuda/archive/13.1.1/nvrtc/index.html)和实际二进制为依据。

2026-10-30：第一步的有界契约、受信 NVRTC/Driver API 驱动及控制器比较已实现；GPU 0 的两类参考解、三类错解、编译错误和缺失入口共 7 组真实检查通过。检查入口和失败修复见 [G1 记录](../acceptance-g1.md)。尚未注册正式评测器或完成资源、恢复、性能与产品接入。

同日，在正式队列接入前补充设备故障实测：输出伪造防护、设备堆超额、非法访存、整卡内存不足、无效 PTX、长运行终止及后续正确解恢复共 9 组检查通过，见 [G2 记录](../acceptance-g2.md)。最终重放在 8 秒期限后约 8.538 秒确认终止。整卡 OOM 不证明任意较小显存配额；后续仍需独立整卡预约、时间预算和失联隔离策略。

G3 实现设备所有权、持久预约、独立账目和租约组件，真实 PostgreSQL 检查确认并发领取、最小权限及锁等待期间的过期拒绝；账号删除不会释放设备。决定见 [ADR-018](../adr/018-gpu-device-ownership.md)，证据与首次失败见 [G3](../acceptance-g3.md)。这些组件尚未被正式 GPU worker 调用，提交入口保持关闭。

G4 已实现交互会话、控制器比较和批次时间采样，并增加复用这些组件的 `--session-probes` 入口。管道及拒绝边界检查通过；首次硬件重放在发现其他账号的计算进程后退出，尚未运行新 GPU 用例。当前继续不占 GPU 的开发，正式执行池和硬件验收仍未完成，见 [G4 记录](../acceptance-g4.md)与 [ADR-019](../adr/019-gpu-session-protocol.md)。

G5 已加入独立任务服务和短事务控制回调；固定 CPU 进程树的硬期限、控制器退出后接管及实际 PostgreSQL 等待超时通过。本机 systemd 252 不支持所选的临时服务作业期限属性，最终使用固定入口的绝对启动门槛配合独立运行期限，详见 [ADR-020](../adr/020-gpu-task-control.md)。[G5 记录](../acceptance-g5.md)保留失败与最终结果；正式 GPU 适配器仍须将这些组件与设备监测、隔离及恢复连接起来。

后续的运行适配器与结算连接见 [G9](../acceptance-g9.md)。[G10](../acceptance-g10.md)实现启动时的旧预约接管、服务/存储清理及独立维护协议；真实 PostgreSQL 与 CPU/runsc 异常回收通过，维护正确解尚无新硬件证据。恢复成功仍保留隔离停用，完整就绪检查、启动凭证和正式 worker 待完成，决定见 [ADR-026](../adr/026-gpu-startup-recovery.md)。

[G11](../acceptance-g11.md)把共用资源检查接入维护协议，九项真实 CPU 检查、十七个容器清理及拒绝边界通过；PID 探针按原生 cgroup 任务数实测，原始失败与修正保留，决定见 [ADR-027](../adr/027-gpu-startup-resource-checks.md)。GPU 模式及完整启动凭证仍须后续验收。

[G12](../acceptance-g12.md)接入十九项固定 CUDA 启动用例及编译后中断；240 项组件检查、实际 CPU 管道和准备前拒绝通过，尚未运行新 CUDA 用例。整控制器失联、完整启动编排与凭证仍待完成，决定见 [ADR-028](../adr/028-gpu-startup-kernel-checks.md)。

[G13](../acceptance-g13.md)接入整控制器退出、通道失联及独立服务期限。三项实际 CPU/runsc 故障、映射存储回收、新调用恢复及 247 项相关回归通过。新的 CUDA 恢复、完整启动编排及凭证仍待完成，决定见 [ADR-029](../adr/029-gpu-controller-lifecycle-checks.md)。
