# RFC-019：共享学习体系中的 CUDA 内核评测

状态：实施中，尚未开放提交。日期：2026-10-30。对应 PRD §2.2 C、§4.2/4.4、§8、R-16 和 AC-04/08。基础环境证据见 [RFC-018](018-gpu-environment-probe.md)。

## 契约与可信结果

新增 `cuda-kernel-v1`，语言为 CUDA C++，首先覆盖 float32 向量加法和行主序矩阵乘法，提供基础实现与优化练习。题意明确内核参数、网格/线程块、数组边界、浮点容差与资源预算。内容仍使用现有不可变题目版本、知识关系、Run/Submit、私有源码和学习进度。

学员只提交设备内核源码。固定 NVRTC 在 gVisor 内将其编译为 PTX，固定 Driver API 驱动加载内核；不链接或运行学员的宿主 C++ 程序。编译选项、入口和驱动代码由平台固定，内容不能提供 checker 或可执行插件。输入允许进入 guest，预期结果和容差比较留在可信控制器。编译、执行和错误变体都必须经过相同隔离，不允许宿主编译学员源码或普通容器回退。

所有值、形状、网格、输出、源码、编译和执行时间都有独立上限。错误区分语法/编译错误、答案错误、运行失败、时间或内存超限以及平台故障。隐藏用例不返回名称、数据、原始编译日志、异常、输出或中间缓冲区。公开 Run 不能生成正式学习证据。

## 性能与可比性

正式性能使用可信控制器测量的固定批次执行墙钟时间；编译和初始化耗时单独报告。采样包括预热、重复批次及中位数，明确它包含控制通信和同步成本，不称为纯 kernel 时间。guest 自报耗时或分数不作为正式证据。

性能记录绑定题目版本、测试/基准版本、样本量与重复次数、硬件型号和设备 UUID、驱动、编译器、编译选项、运行时/制品/策略摘要及资源配置。只在相同可比性键内排序，正确性不通过不获得性能成绩。沿用自愿公开、撤回与账号隐私规则，不并入 CPU 的统一通过数/速度榜。

执行会话采用逐条请求/应答协议。控制器先发送源码并等待固定编译完成帧，再逐个发送输入，答案不进入 guest。单次请求、协议帧、累计输出、编译和整个会话分别受限，等待时持续调用取消/租约检查。客户端进程退出不能代替容器终止；会话清理始终检查自有容器状态，必要时终止并等待实际退出，失败则保持设备停用。

第一版性能配置固定选用正式测试中工作量最大的一个输入（向量元素数或矩阵乘加项数，同量取最先出现者），只在全部正确性检查通过后采样。预热 2 批，测量 5 批，每批在固定输入上重复执行 16 次，控制器从发送批次请求到收齐输出帧计墙钟并取中位数。每次内核调用前重置输出缓冲区，并同步执行；每批仍返回输出供控制器比较。结果明确为含通信、缓冲区分配和同步成本的批次时间，不称为纯内核耗时；编译/初始化单列。固定输入的缓存优化属于此基准条件，不外推为其他输入或规模的速度。

初始会话上限为 Run 60 秒、Submit 120 秒，编译 15 秒、每次请求 5 秒，余下预约用于环境准备与清理；这些值须通过真实设备样例和超限用例验证后才能用于正式 worker。正式会话不启用包含源码或原始日志的诊断环境变量。组件探针复用同一会话实现，继续与正式启动 receipt 和网站准入分开。

## 执行池、预算与回收

保留现有 CPU/WASI worker，GPU 使用独立路由、就绪状态和执行指纹，不能由 CPU worker 领取。初期明确分配 GPU 0，每卡一次一个任务，数据库预约和主机设备锁同时保护重复 worker。GPU 每日时间预算独立于现有 CPU 调用单位，不能混记或在重复幂等请求中重复扣额。

资源预约涵盖编译、正确性检查和性能采样。继承已实测的用户 cgroup 命名空间与可信父 cgroup 限额；固定工作负载预算必须通过实际限额及超限探针。显存预算包括输入、输出、驱动和编译开销；设备代码不得借 CPU 宿主代码访问额外分配 API。还需验证设备端分配、越界、显存耗尽与长运行内核的边界，不能仅凭正常样例推断这些限制成立。

worker 在各阶段续租并检查取消。租约失效只终止自己的任务；任务结束或服务退出必须回收专属容器/cgroup，确认设备无本任务残留，再执行设备恢复检查。未知执行状态、失联或恢复失败将设备隔离停用，预约不得因数据库超时就直接交给下一任务。不能重置共享 GPU 或终止未知进程。

主机文件锁只协调本平台控制器，不能阻止其他账号使用显卡。正式 worker 须在任务前后及运行期间检查设备占用；出现不属于自有工作负载的计算进程时停止自有任务、丢弃性能结果并保持停用。共享主机上的专用设备仍需要维护者协调独占窗口；不能把低利用率或空闲 CUDA 上下文视为无人占用。

资源实现使用同一 `Submission` 的独立 `gpu-slot-seconds-v1` 预约策略，按 Run 90 秒、Submit 180 秒保守预约整卡时段，不能与 CPU 调用单位相加。它是执行上限的预约，不冒充实测 GPU 时间；执行后不因语法错误、取消或用户错误退回额度。具体执行器的编译、运行和清理总上限不得超过预约。

设备表保存 UUID、执行指纹、worker 所有权令牌、当前任务 UUID 和租约令牌，状态分为隔离停用、可用、已预约。当前任务只保存不含用户内容的运行身份，不通过外键随账号删除而释放设备。主机使用私有目录中的每卡 `flock`，所有副本必须共用该目录，锁文件关闭后保留；新控制器取得主机锁后也先进入隔离停用，不能仅凭旧心跳过期恢复可用。数据库内所有设备操作按设备行、任务行的顺序加锁，旧所有权/租约令牌不能续租、写成绩或释放新预约。

Web 对设备表只读，worker 仅有读取、插入和更新权限。部署控制器按实际迁移是否存在授予新表权限，旧发布包保持兼容。调度层只能记录受信控制器已经完成恢复这一事实；正式 worker 必须在真实设备检查后调用恢复转换，不能把调度单元测试当作硬件验收或伪造启动 receipt。

### 任务服务与控制回调

每个正式任务使用独立的临时用户服务承载可信控制器和其整个隔离进程树。服务名与描述绑定设备 UUID、任务 UUID、预约令牌及操作 UID；控制器重启后可以凭保留的预约定位旧服务，但必须核对描述、临时服务属性、cgroup 与调用身份。未知同名服务不能停止或替换。服务使用 `Type=exec`、整 cgroup 终止、禁止自动重启、明确启动/停止期限和运行硬期限；准备、执行、恢复与清理共享同一预约截止时间，不能因重试获得新时段。服务仅启动固定可信入口，学员源码不进入命令行或日志。

运行时限由用户服务管理器执行，不依赖 Python 心跳或数据库回调及时返回。任务结束后检查服务停止及 cgroup 没有剩余进程，不能将启动客户端退出、一次 `stop` 返回或数据库租约到期作为已清理证明。该检查仍不替代设备空闲与真实 CUDA 恢复探针。组件阶段使用固定 CPU 进程树验证超时、父进程退出及重启后的定向清理，不访问 GPU。

GPU 控制回调使用单独、短事务：PostgreSQL 单次语句上限 1 秒、锁等待 250 毫秒；SQLite 连接在事务前临时使用 250 毫秒 busy timeout，并在退出后恢复。每次进入和退出检查设备锁、任务截止时间与租约；等待失败只会中止自有任务，不能续活过期预约。数据库服务端超时不保证网络故障时调用及时返回，因此任务服务硬期限仍是独立必要条件。新回调和服务组件在实际 GPU worker 接入前不打开提交入口。

### 受信运行适配器

外层 worker 保留数据库凭据，持有设备锁、任务预约和服务实例；临时服务中的可信控制器复用固定 RootlessKit/Podman/runsc 环境，在其内运行 guest 编译/驱动。两者通过私有目录中的 Unix socket 传递有界消息，外层用 `SO_PEERCRED` 核对操作 UID 与所属任务 cgroup。只有完整制品身份和环境准备通过后才发送源码与受保护测试；不将这些数据写入命令行、环境变量、日志或任务文件。guest 仍只收到源码和输入，预期答案留在可信控制器。

外层在等待各阶段时持续检查数据库租约和宿主设备占用；占用查询包括计算与图形进程，无法识别 PID 或所属 cgroup 时拒绝继续。服务内所有隔离进程须属于同一任务 cgroup；出现外部进程时仅终止自有服务，不杀未知 PID、不重置 GPU。结果只有在 guest 清理、独立正确解恢复、整个任务服务退出以及宿主设备空闲均确认后才交还 worker 结算。

每次启动只导入经完整校验的离线镜像，不在任务期间拉取网络制品。私有工作目录绑定设备/任务/预约，重启后的清理只接受该身份；保留未确认清理的预约。适配器本身不签发启动 receipt，也不改变 Web 准入；正式连接还需实际 GPU 故障与性能重放及独立的就绪门槛。

命名空间启动使用固定的环境变量白名单，不继承数据库连接、代理、容器远端连接或 Python 注入配置。RootlessKit 创建独立 user、mount、PID、network、IPC、UTS 和 cgroup 命名空间；内层完全断网，离线制品不需要 slirp/NAT。文件路径 socket 保留在外层私有目录，连接后仍由外层核对真实宿主 UID/PID 与任务 cgroup，不能信任内层报告的 PID。内层控制器只在 `/manager` 中运行，并为 guest 建立受限的 `/workloads` 父组。

任务工作目录位于维护者指定的私有根目录，名称及身份文件绑定当前服务；创建时拒绝已有目录，恢复时重新核对身份、所有者、权限和目录 inode。只有确认匹配服务已停止且 cgroup 无进程后才删除目录；不认识或仍在运行的目录原样保留。这里的文件身份与进程清理不代表 GPU 已恢复，数据库预约仍须等待真实设备空闲及正确解恢复。

先以固定 CPU 进程验证实际跨命名空间连接、大消息、环境清理、断连与独立服务期限，不调用 NVML/CUDA，也不把此检查当作 GPU receipt。命名空间选项依据 [RootlessKit 官方说明](https://github.com/rootless-containers/rootlesskit)，以本机实际进程与 cgroup 检查确认。

运行模块共用固定制品校验：完整 runsc 归档、Python OCI 图及 NVRTC 校验从探针脚本移入 `judge/`，既有探针继续调用同一实现。每次在私有工作目录准备制品、仅导入已验证离线镜像；Podman 使用明确的独立存储、空 hook 目录和指定 CDI 目录，不连接远端服务或继承用户配置。创建后、启动前核对实际镜像、运行时和隔离参数，失败不能回退普通容器。

控制命令也采用有界管道和绝对期限，等待期间处理取消；清理忽略已失效的业务回调，但仍受任务服务的硬期限约束。只有当前工作目录内、身份核对通过的容器可被终止和删除。清理须确认实际退出，再清空自有镜像层和私有挂载；容器 CLI 退出不是清理证明。

独立的 CPU 验收仅在固定 Python 镜像中运行平台审阅过的基础设施夹具，不加载 NVRTC、不启用 nvproxy、不映射 GPU，也不接受学员源码。它复用同一制品、隔离、管道与回收路径，检验文件/网络/设备边界和取消、输出超限后的恢复。正式 CUDA 会话必须显式配置单卡和编译器，不能沿此 CPU 检查路径执行或生成 GPU 成绩。容器参数依据 [Podman 创建文档](https://docs.podman.io/en/latest/markdown/podman-create.1.html)，仍以实际边界检查为准。

## 分批实施与验收

1. 实现有界 CUDA 契约、受保护比较和固定编译/执行驱动，在 GPU 0 实跑参考解、针对性错解与错误分类。
2. 接入独立运行时指纹、GPU 预算、设备预约和队列/租约/取消；验证并发 worker 与旧 CPU 行为。
3. 注册正式题型与真实探针，纳入策略摘要和不可伪造的启动验收；补齐内容、页面、正式结果和可比榜单。
4. 验证显存/CPU/内存/PID/输出/超时、取消/失联、设备回收与故障关闭；进行 PostgreSQL、真实队列、浏览器和部署验收。
5. 提供明确的容器化 GPU worker 部署入口，更新集中部署指南、README、AGENTS、需求追踪及 ADR。所有门槛通过前继续关闭 GPU 提交。

本 RFC 不将阶段性组件测试标为完整交付。正式策略及结果结构必须在上述故障和性能检查后固定。NVRTC 与 Driver API 以固定版本的 [NVIDIA 文档](https://docs.nvidia.com/cuda/archive/13.1.1/nvrtc/index.html)和实际二进制为依据。

2026-10-30：第一步的有界契约、受信 NVRTC/Driver API 驱动及控制器比较已实现；GPU 0 的两类参考解、三类错解、编译错误和缺失入口共 7 组真实检查通过。检查入口和失败修复见 [G1 记录](../acceptance-g1.md)。尚未注册正式评测器或完成资源、恢复、性能与产品接入。

同日，在正式队列接入前补充设备故障实测：输出伪造防护、设备堆超额、非法访存、整卡内存不足、无效 PTX、长运行终止及后续正确解恢复共 9 组检查通过，见 [G2 记录](../acceptance-g2.md)。最终重放在 8 秒期限后约 8.538 秒确认终止。整卡 OOM 不证明任意较小显存配额；后续仍需独立整卡预约、时间预算和失联隔离策略。

G3 实现设备所有权、持久预约、独立账目和租约组件，真实 PostgreSQL 检查确认并发领取、最小权限及锁等待期间的过期拒绝；账号删除不会释放设备。决定见 [ADR-018](../adr/018-gpu-device-ownership.md)，证据与首次失败见 [G3](../acceptance-g3.md)。这些组件尚未被正式 GPU worker 调用，提交入口保持关闭。

G4 已实现交互会话、控制器比较和批次时间采样，并增加复用这些组件的 `--session-probes` 入口。管道及拒绝边界检查通过；首次硬件重放在发现其他账号的计算进程后退出，尚未运行新 GPU 用例。当前继续不占 GPU 的开发，正式执行池和硬件验收仍未完成，见 [G4 记录](../acceptance-g4.md)与 [ADR-019](../adr/019-gpu-session-protocol.md)。

G5 已加入独立任务服务和短事务控制回调；固定 CPU 进程树的硬期限、控制器退出后接管及实际 PostgreSQL 等待超时通过。本机 systemd 252 不支持所选的临时服务作业期限属性，最终使用固定入口的绝对启动门槛配合独立运行期限，详见 [ADR-020](../adr/020-gpu-task-control.md)。[G5 记录](../acceptance-g5.md)保留失败与最终结果；正式 GPU 适配器仍须将这些组件与设备监测、隔离及恢复连接起来。
