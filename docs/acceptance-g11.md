# G11：启动资源检查

日期：2026-10-31。设计见 [RFC-019](rfcs/019-gpu-kernel-evaluation.md#正式就绪检查)和 [ADR-027](adr/027-gpu-startup-resource-checks.md)。本轮继续不占 GPU；只验证共用 CPU 资源流程和协议边界，未签发 GPU 凭证或开放提交。

## 已实现

新增 `judge/gpu_isolation.py`，将已有实际 CPU 资源检查从脚本移入生产控制器共用模块，并补齐内存和宿主 PID 限额探针。适配器的 `check-resources` 维护请求只包含随机挑战和外层回环监听端口，不接收学员源码。GPU 模式要求准确设备集合、资源检查后独立 CUDA 正确解恢复、存储及整服务清理和最终设备空闲；这条 GPU 路径本轮仅做协议测试。

CPU 重放显式要求运行时未准备 GPU，不能作为 GPU 模式的替代。报告必须包含完整九项检查、十七个不同容器的清理及本次挑战。拒绝缺项、重复容器、失配设备、未停止、错误布尔值和夹带成绩；检查不依赖 Python `assert`。

| --- | --- |
| 身份与隔离 | UID 65534、无 capabilities、根目录只读、控制器私有文件不可见、宿主回环监听不可达、无 GPU 设备和私密环境变量、挑战匹配 |
| 输出、超时、取消、客户端退出 | 分别触发输出限制、请求期限、取消回调及附着客户端死亡；遗留容器由控制器清理 |
| CPU | 约 3.002 秒墙钟消耗 1.492 秒 CPU，发生 20 次节流，符合 0.5 核额度 |
| 内存 | 固定程序超过 512 MiB 边界后，由控制器核对 cgroup OOM 计数增长并得到内存超限结果 |
| 临时存储 | 32 MiB 写入后触发 ENOSPC，测试文件清理 |
| 宿主 PID | 专用叶组中探针自身及 255 个子进程占满父组 256 个任务额度，再创建被内核拒绝；全部子进程等待结束，剩余为零 |

每个场景后都新建隔离容器，重新验证身份与边界；共十七个容器均已停止。私有存储、服务 cgroup、工作目录和临时根目录均清理成功。叶组修正后的首次成功记录 `px-gpu-runtime-c2ec5f51bcd0/result.json` 也保留；随后增加原生探针的 UID 保护，再得到上述最终记录。

`test-results/g11-protocol-final.xml` 为 **104 passed，无 skipped**，覆盖 CPU/GPU 模式不可互换、报告完整性、设备/挑战失配、泄露拒绝、回环监听生命周期、失败清理、资源检查后的独立恢复顺序及原生探针在错误命名空间中拒绝启动。通道、GPU 运行时与报告值在这些单元检查中是替身，不证明 CUDA 成功。

`test-results/px-gpu-controller-3a9412d68b56/result.json` 为最终控制器的实际命名空间加载与准备前拒绝检查：可信入口和新增模块加载成功，身份核对、错误顺序拒绝、EOF、整服务停止及工作目录清理通过；没有准备 GPU。此前同类检查 `px-gpu-controller-1c9e9c825b3b/` 也通过。

## 失败与修正

三次原始失败记录均保留，且其自有资源都已清理：

1. `px-gpu-runtime-669dd2e18680/result.json`：PID 场景保留大量 Python guest 子进程，先触发内存上限；其余八项通过，不能据此认定 PID 场景通过。
2. `px-gpu-runtime-44cb0aa3da04/result.json`：改为镜像内固定休眠程序后，runsc 控制连接在压力下不可用，单容器停止命令失败；最终私有存储与整个服务仍成功清理。该场景仍不能证明所需的宿主 PID 边界。
3. `px-gpu-runtime-675bac4a0b0e/result.json`：固定原生探针尝试进入已启用子控制器的内部 cgroup，内核返回 EBUSY。改为创建独有叶组并继承原父组额度后通过；未放宽任何限额。

最终区分了 guest 虚拟任务和宿主原生任务。PID 门槛在正确层级实际测试，并核对内核拒绝与零剩余；资源模型和 cgroup 约束的官方依据见 ADR。原生探针只执行仓库中的固定可信程序，不接收学员输入，也不在共享主机 cgroup 中运行。
