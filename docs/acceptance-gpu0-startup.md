## 失败、诊断与修复

两次原镜像调用均在 `resources` 阶段失败，正常 `recover-gpu` 之后没有活动任务记录，完整 SMI 列表为空。原任务日志按生产契约关闭，不能从通用错误推断具体原因。

独立诊断源码从提交 `6a0eaf0` 导出，只记录固定基础检查的位置和身份字段；重新构建相应控制/任务镜像，并重新计算全部源码契约。第一轮因原任务先退出而未取到内部信息；第二轮在原绝对期限内、guest 清理后短暂保留失败控制进程供读取。两轮均保持失败并按原状态恢复，不作为正式启动证据。

第二轮记录确认：宿主选择是 UVM `507:0`，guest 实际为 `254:0`，其余设备身份与隔离字段全部匹配。固定 gVisor 的 VFS 会转换此设备号，原代码却直接使用宿主预期。修复新增 `guest_nodes()`，绑定已审阅的 runsc 二进制摘要；宿主、Docker/OCI 输入和历史 journal 仍保留实际注册号。未知 runsc、错误 guest major、卡 minor、额外节点继续拒绝。

新增回归在修复前得到 **3 failed / 4 passed**，同时复现错误拒绝正确 guest 和错误接受宿主编号。修复后七个相关模块 **281 passed / 0 skipped**，Ruff 与格式检查通过。组件结果不替代当前进行中的单卡节点和完整启动检查。
