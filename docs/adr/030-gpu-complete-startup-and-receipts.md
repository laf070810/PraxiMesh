# ADR-030：完整 GPU 启动、私有凭证与就绪事务

状态：接受组件设计，2026-10-31。依据 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md#正式就绪检查)。正式 GPU worker 和硬件验收仍待完成。

## 决定

`core/gpu_readiness.py` 调用既有启动接管与物理恢复，然后串行执行资源检查、十九项 CUDA 用例和三项整控制器故障，共二十四个必需阶段。每段最多 180 秒，整体上限 4320 秒；所有阶段保持同一主机锁、数据库所有者及原预约，使用每卡固定维护身份的新服务调用。没有跳过阶段、恢复部分进度或导入外部报告的入口。

编排层复用报告校验器，再次检查完整资源集合、GPU 模式、容器清理、CUDA 预期判定以及控制器故障后的恢复。报告结构校验不替代适配器对本次随机挑战的核对，两层必须同时成功。旧任务保持原预约和账目，直到全部检查及就绪事务成功。

`judge/gpu_receipt.py` 将凭证限制在本用户 0700 目录内的 0600 单链接普通文件。先同步私有临时文件，再以不覆盖现有文件的方式原子发布，移除临时链接后再次读取校验；拒绝链接、FIFO、权限变化、目录/文件替换、超大或畸形 JSON。文件绑定完整有序阶段集、证据摘要、当前代码/运行时/硬件环境、worker、持锁所有者、UID、内核和 boot ID。它是可信控制器的私有记录，不是针对同 UID 管理者的密码学证明。

有效期最多 24 小时，同时检查墙钟和单调时钟，回拨或过期关闭就绪。转换和心跳至少保留一个完整任务预算。新进程必须重跑完整启动；旧所有者的文件不能用于新锁令牌。测试替身产生的临时序列化文档不是运行凭证。

文件验证成功后，在有界短事务中再次锁定设备、核对所有者、worker、指纹和原预约，才确认恢复并发布 ready。凭证发布与数据库提交之间发生冲突时，删除本次凭证并保持隔离停用；不能释放旧预约或改写替代所有者。空闲心跳还要核对实际设备身份及没有外部进程，并在同一设备行锁下校验身份与刷新健康。失联、过期、身份变化或外部占用均关闭健康，不终止未知进程。

## 验证边界

本次检查的范围与失败修复见 [G14](../acceptance-g14.md)：文件和协议边界、实际 PostgreSQL 事务竞争，以及 CPU/runsc 依赖检查。GPU 方法在数据库测试中明确替换为测试替身，相关临时文档不能作为硬件成功证据。

该入口尚未被正式 worker 或 Web 准入调用。二十四阶段 CUDA 全路径、运行总预算、正式队列、产品题型、性能和部署仍须继续实施与独占硬件验收；现有 Compose 的可用题型保持七种 CPU/WASI。
