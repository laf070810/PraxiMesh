# ADR-065：在原数据库上恢复原 GPU worker

日期：2026-11-01。状态：采纳；文件、协调器进程与状态模型验证，实际 Docker/PostgreSQL 和完整 GPU 部署待验收。延续 [RFC-022](../rfcs/022-gpu-release-coordination.md)、[ADR-063](063-durable-gpu-worker-lifecycle.md) 和 [ADR-064](064-gpu-release-readiness-observation.md)，结果见 [G49](../acceptance-g49.md)。

候选代失败后，其任务记录和物理预约仍属于候选数据库。若先切回旧库，再启动 worker 恢复，会丢失原预约的归属。单独的容器停止、一次旧预检或持久的 ready 阶段都不能证明恢复完成。

内部 `Deployment.recover_gpu_worker()` 由 `scripts/deploy_gpu_recovery.py` 编排。输入须匹配当前私有配置、已记录发布代和完整冻结制品；要求原维护路由、部署/数据库操作锁及原暂停 token。曝光意图存在时，只接受已曝光的当前代。它不切换配置、不冻结或复制数据库、不改变代理，也不删除任务 journal 或物理预约。

协调器先持久保存原容器 ID、运行契约、配置摘要、操作归属及尝试记录，再依次停止原 worker、重跑固定预检、启动同一容器并等待完整就绪。预检与 worker 仍分别使用已有生命周期记录；已登记对象缺失或同名替代均拒绝，不自动重建。每次新 worker 启动须有本次操作的成功预检，且预检开始不早于上一 worker 的实际退出时间。

六个持久阶段为 stopping、resetting_check、checking、starting、waiting、ready。中断后只继续原操作和原实例，已退出的预检无需再发停止命令。仍在运行的启动实例继续等待原期限；已确认退出的本次启动，只能在下一次恢复调用中建立新尝试。预检失败修复后也沿同一容器重试并保留失败启动时间；每份记录最多保留十六次 worker 尝试，每次最多十六个失败预检，达到边界时保留现场并停止自动处理。

若 Docker 已启动容器并退出，而协调器尚未保存启动确认，先由原生命周期记录确认该次失败；本次调用不重复启动，后续调用才建立新尝试。不能因为持久记录仍是 start_requested 而永久拒绝原实例，也不能借此接受其他操作的启动。

ready 只记录流程进度，重复调用仍读取当前就绪。最终确认前再次核对原运行实例，不能把刚退出的 worker 标记为恢复成功。配置发布须先确认恢复记录完整且结束，再核对已停止的原容器、任务 journal 和两库暂停/预约门槛；不能以直接发布配置跳过待完成恢复。

完整 GPU 发布尚未接通，因此公共 CPU apply/recover/restore/expose 路径必须在任何变更前拒绝已有 GPU 配置、容器或恢复状态，包括 GPU→CPU 的情况。绑定了节点但尚未创建 GPU 配置/容器的 CPU 站点保持原行为。此组件不解除真实队列、升级、回滚和曝光后恢复的验收门槛。
