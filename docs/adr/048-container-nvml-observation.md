# ADR-048：容器内 NVIDIA 管理观察

日期：2026-10-31。状态：接受；十七项真实管理/CPU/兼容场景及 422 项相关组件检查通过，见 [G32](../acceptance-g32.md)。背景见 [RFC-021](../rfcs/021-gpu-container-supervision.md)。

G31 能在可信控制容器中核对宿主 PID 和原任务归属，但不能提供 NVIDIA 进程来源。采用独立 NVML 管理库快照与固定查询子进程，直接调用计算、图形和 MPS 三个 v3 进程 API，不依赖私有 `/proc` 中的进程名称或 `nvidia-smi` 的展示格式。接口绑定不包含 CUDA 初始化、计算、设备设置或进程终止。

显式挂载契约 v3 在 v2 的宿主 procfs 身份之外绑定所选 UUID、型号、驱动、计算能力、设备 minor 和管理库清单。GPU 的宿主枚举 index 不替代字符设备 minor。只映射所选 `/dev/nvidiaN` 与 `/dev/nvidiactl`；不映射 UVM、其他 GPU 或宿主 capability 目录。v1/v2 的行为与任务 journal、总预算版本保持原义。

库来自不可由普通用户改写的系统目录，构建时静态检查 ELF/SONAME 和内核版本，固定大小、SHA-256 与独立 profile；镜像构建后再次核对原库。控制端启动和观察前后重新检查库、当前内核、设备节点和原挂载。普通 CPU 控制镜像默认不携带 NVML，原 CUDA/PTX 任务镜像也不能作为这个管理制品使用。

NVML 590 会在自身 `/dev` 中创建空的 `nvidia-caps`。实际失败确认后，契约仅允许与私有 `/dev` 同文件系统、属于当前用户、不可由其他用户写入且非链接的空目录；任何额外项仍拒绝。没有增加容器能力、允许 mknod 或映射其他设备。

固定子进程仅接收完整 UUID，使用空白受限环境、独立三秒期限与 256 KiB 输出上限；只返回身份和分类 PID，不输出进程名称、环境、命令行或显存样本。所有查询类别都必须成功，任何错误不回退为空列表。任务监测保存同一个原 `OwnedProcesses` 对象，空列表也重新核对原 journal/实例/PID 1；不能重新建观察对象认领重启或新任务。

管理设备句柄本身并非只读权限边界，因此只属于已有专用 rootless Docker 控制权的可信执行平面。此接口的只读性来自固定代码；它不证明学员 GPU 隔离，不签发 receipt、不释放预约，也不改变网站准入。没有实际外部 GPU 进程时不能宣称验证其 PID 来源；真实 CUDA 归属与恢复须另行独占验收。操作集中在 [GPU 指南](../deployment/gpu.md#container-device-observer)。

三类 NVML 上下文列表也不是全部资源占用的穷尽证明。[NVIDIA 查询文档](https://docs.nvidia.com/deploy/nvidia-smi/index.html)另列出 `O` 类及无需上下文的资源分配；本接口尚未证明覆盖它们。正式容器准入前必须补齐该来源或建立经过真实验证的等价限制，不能仅凭本接口返回空列表发布空闲/就绪状态。
