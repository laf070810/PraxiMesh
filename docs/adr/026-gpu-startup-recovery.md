# ADR-026：GPU 启动接管与维护恢复

状态：接受组件设计，2026-10-31。依据 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md#受信运行适配器)，证据与限制见 [G10](../acceptance-g10.md)。

## 决定

启动恢复由 `core/gpu_startup.py` 协调。控制器持有真实设备锁，接管数据库设备行后先隔离停用，保留原任务 UUID 和预约令牌；租约到期、账号删除或进程重启都不能自动释放这个预约。

旧预约可定位任务、文件回收和维护服务。每卡另有固定的启动维护身份，由设备 UUID 派生，不依赖本次所有权令牌；因此即使没有学员任务，也能在外层进程退出后找回遗留维护服务。停止操作继续核对服务描述、cgroup 和调用身份，不能终止同名但身份不符的服务。

取得旧预约后，先尝试停止所有已知旧服务，再访问数据库或清理目录。某一个停止失败仍尝试停止其余已知服务，随后退出恢复；不能在任何旧服务尚未确认停止时清理文件或启动新 GPU 工作。文件回收服务的目录先处理，避免占用后续映射文件回收所需的固定身份。未知目录不在清理范围内。

维护使用独立 `maintenance` 服务和严格的 `recover` 消息，不携带学员源码、题目或成绩。它复用已验证身份的准备流程，在新容器中编译固定正确解，执行并由控制器比较结果，再关闭运行环境。宿主仍须确认整服务停止、目录清理和设备空闲。维护回复不能夹带成绩，任务服务和维护服务不能互换。

启动阶段总预算最多 180 秒，单次维护最多 90 秒，且受总阶段剩余时间限制；这些是组件中的边界，尚待真实硬件时序验收。维护使用自己的预算，不续期、重跑或消费旧学员任务。过程中持续核对主机锁、数据库所有权、原预约及截止时间。全部恢复完成后仍保持隔离停用，既不结算旧任务，也不签发启动凭证或发布 ready。

所有控制器副本及升级须共用同一私有工作根和设备锁目录。固定身份只能定位该目录与同一用户服务管理器中的已知资源；变更服务账号或目录需要另行设计迁移，不能直接绕过旧资源启动。

## 验证与后续

真实 PostgreSQL 检查覆盖新锁所有者接管、旧预约保留、账号删除、所有权或槽位变化、维护失败及拒绝领取新任务。维护适配器在这批测试中是替身；实际 CPU/runsc 检查覆盖任务和维护控制器的异常退出及映射存储回收。两者均不证明 CUDA 恢复成功。

完整隔离与故障检查、启动凭证、正式 worker 及健康发布尚未实现。后续只有在真实 GPU 恢复、完整检查与当前制品/策略凭证全部通过后，才能确认旧预约已恢复并开放新工作。
