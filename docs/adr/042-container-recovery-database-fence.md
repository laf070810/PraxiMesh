# ADR-042：容器恢复与数据库预约绑定

日期：2026-10-31。状态：接受；完整容器 GPU 执行和部署仍待交付。背景见 [RFC-021](../rfcs/021-gpu-container-supervision.md)，操作集中在 [GPU 指南](../deployment/gpu.md)。

将已有持久容器清理接入宿主 worker 的启动、完整凭证续检与取消恢复。`gpu_worker` 可显式接收成对的 `--container-journal` 和 `--docker-socket`，目录必须已初始化并与当前设备锁、私有 daemon 的安装身份一致。默认不连接 Docker。新增 `BoundContainerRecovery` 供后续容器 worker 复用；当前能力是预约与清理流程集成，不表示容器后端已经能领取并评测 CUDA 作业。

停止与归档分开。`ContainerJournal.stop()` 只核对并停止原实例，保留活动记录；创建成功但 ID 未落盘时，先持久保存找回的完整 ID，再停止。数据库接管失败时也尝试这项独立停止；不删除记录，不清空预约，不以不同名称或实例替代已保存对象。未知/替换对象继续拒绝操作。

正常启动先在短事务内接管并隔离设备，保留原预约。停止全部已知宿主服务及原容器后，归档前核对同一数据库拥有者、隔离状态与预约。记录只能匹配原任务/预约，或由每卡固定函数生成的启动维护身份；调用方不能自行传入一组“维护”UUID 来放行其他记录。账号删除后仍使用设备行保留的任务 UUID，不依赖提交外键。

匹配后按原记录移除并归档，再次核对数据库身份。错配、行锁超时、记录替换或归档失败不产生就绪或成绩，预约和额度继续保留；若清理已完成但最后一次数据库核对失败，保留归档及新数据库状态，仍不返回成功。停止不依赖数据库查询；SQL 锁/语句超时不等于网络超时，原任务的独立绝对期限继续生效。

容器清理报告始终 `ready: false`。只有既有独立 GPU 正确性恢复、完整启动检查和就绪事务全部成功，worker 才能领取任务。启动报告增加容器记录清理校验，正式执行策略摘要包含新核心模块和容器身份实现，因此旧 GPU receipt 不能直接沿用；不改变 CPU/WASI 策略或旧学习成绩。

验证使用一次性 PostgreSQL、合成的隔离预约和固定 CPU guest；测试不把设备标记为硬件已通过，不编译学员源码，也不生成 GPU receipt。原有宿主 GPU 生命周期采用明确的运行时替身做事务/参数验证，真实 CUDA、设备占用监测和最终 Compose 仍需独立验收。
