# ADR-053：容器内固定内核启动检查

日期：2026-10-31。状态：已实现并通过非 GPU 验证；完整启动及硬件路径待验收。背景见 [RFC-021](../rfcs/021-gpu-container-supervision.md)，结果见 [G37](../acceptance-g37.md)。

容器维护请求复用十九项 CUDA 检查目录，仅接受固定名称与随机挑战。`ContainerGPUAdapter.check_kernel` 经原 `KernelTask` 发起，可信任务端选择源码与保护答案，内层 guest 只处理既有内核协议。普通任务目的不能调用维护检查；检查不会产生学员成绩。

`judge/container_kernel_checks.py` 定义独立的 `container-kernel-check-v1` 报告，使用原 runsc guest 的固定标签与清理证据。`ContainerRuntime.stop_container` 在原状态、附着进程及进程树清理成功后保存首次观察，重复清理不覆盖。报告固定包含原状态、实际附着返回码、停止和移除确认。宿主 Podman 报告继续要求完整容器 ID，两类清理身份各自验证，只共享预期判定、编译完成、实际计时和故障分类规则。

检查执行从原总期限中预留独立正确恢复和清理时间。命名检查成功后仍须运行新正确 guest、完成内层清理、核对报告挑战、恢复外层原记录并重新观察空闲，才向调用者返回。取消/附着退出在触发前观察原 guest 与附着进程均活跃，触发后独立核对清理；实测中 runsc 在客户端关闭后可能已经停止 guest，不能把事后状态代替触发前观察。宿主路径继续要求其清理前活跃状态，容器路径要求独立的 `interruption_observation`。模块显存分配失败必须保留驱动退出码 4，不能用整任务 OOM 代替。

选择独立报告格式而非伪造 64 位宿主 ID，避免把私有 runsc 标签误当成跨环境身份。完整外层实例身份继续由 journal、控制器与执行环境固定。无设备 CPU 夹具复用真实流程验证协议和清理，收到的源码仅作数据；这些报告不能证明 CUDA、性能、显存边界或设备恢复成功。

现有 receipt、网页准入和 worker 命令保持原门槛。容器资源检查、整控制器故障、完整启动编排和部署尚待接通，十九项 CUDA 仍需独占硬件实测。
