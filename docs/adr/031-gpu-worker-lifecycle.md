# ADR-031：GPU worker 生命周期与当前凭证

状态：接受组件设计，2026-10-31。依据 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md#常驻-worker-生命周期)。完整硬件与容器部署验收仍待完成。

独立宿主命令 `gpu_worker` 使用显式设备 UUID、固定离线制品、普通用户服务和持久私有目录，持有设备锁直到退出清理完成。每次启动都调用完整启动编排；`--once` 只限制领取次数，不提供跳过检查或留下可复用凭证的路径。CPU worker 健康与队列不受此命令修改。

领取在同一个有界数据库事务内锁定设备身份、复核凭证、刷新空闲健康和预约任务。执行回调及结算同样在自身短事务内核对当前凭证和 worker 身份，写入后再核对停止标志、时限和身份；验证失败回滚该次状态变更。策略摘要覆盖循环与命令源码，不能让已加载进程沿用磁盘上新代码的身份。

凭证明确区分正常到期与文件/时钟/身份错误：空闲时正常到期触发完整续检；其余故障退出。执行中凭证失效会沿同一服务对象停止执行并丢弃结果。取消、删除或丢失租约后先确认原服务停止，再进入独立恢复；恢复开始前在行锁下核对原预约，完成后再次核对原预约、身份与完整启动凭证，才释放设备。清理失败不能被误当作可恢复的取消，也不能重建服务对象绕过调用身份检查。

SIGINT/SIGTERM 处理器只赋值无锁标志，空闲轮询最多每 100 ms 检查一次，控制回调负责正常清理。实际子进程复现了 `threading.Event.set()` 重入条件锁的死锁，因此信号入口拒绝带锁的 Event；这也符合 [Python 信号处理说明](https://docs.python.org/3/library/signal.html#signals-and-threads)。退出尝试撤销当前所有者的文件与数据库就绪，即使其中一步失败仍尝试另一步；不能静默报告清理成功。中断且尚未独立恢复的任务保留预约，由下次完整启动处理。数据库网络等待不构成实时保证，任务服务的独立硬期限仍然必要。

验证范围见 [G15](../acceptance-g15.md)：实际数据库、信号与 CPU 控制链，加上明确运行时替身的流程测试。本决定没有验证 CUDA 整套启动、性能与总时限，没有开放网站 GPU 提交；容器化 worker、内容与正式证据仍须继续实现和验收。
