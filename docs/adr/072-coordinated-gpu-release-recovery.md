# ADR-072：按持久曝光决定协调整站 GPU 发布与恢复

日期：2026-11-02。状态：采用，内部实现；公共 GPU 发布仍待真实环境验收。延续 [RFC-022](../rfcs/022-gpu-release-coordination.md) 和 [ADR-070](070-durable-gpu-exposure-decision.md)、[ADR-071](071-durable-gpu-configuration-retirement.md)。

单独完成配置、worker、准备和曝光组件仍不足以安全升级。候选数据库可能只完成部分迁移，候选检查可能失败，代理响应也可能在新库已接受写入后丢失。恢复不能从“当前命令失败”推断应当恢复旧快照，也不能要求失败的候选先通过同一产品检查才允许回退。

采用 `scripts/deploy_gpu_release.py` 的内部编排。每个操作保存完整前代/候选代、规范归档路径和独立恢复尝试，复用原组件完成排空、维护、冻结、复制或初始化、迁移、最小权限、准备及持久曝光。升级不重新导入内容。GPU→CPU 先退出原配置；初次安装失败保留数据库和日志，不认领缺少原所有权标记的库。

曝光前恢复前代，先在实际配置所指向的原库处理工作、清理原验证轮次，再冻结并退出或切换配置。能确认原 worker 从未启动时不为退出配置启动 GPU 任务，原排空和冻结保护仍执行。曝光后只恢复已决定的当前库；保存恢复阶段，重新验证原实例并保留全部轮次和曝光历史。配置已经完整发布时只读核对原配置，仍拒绝未完成退出。

恢复曝光的响应丢失不重启仍在运行的原 worker；确认同一实例退出后才重新进入维护与原库恢复。CPU 目标也在开放前保存数据库决定，重试只接受维护路由或已决定的原端口，不接管未知路由。数据库所有权查询只区分确实不存在与原 owner/marker 一致；存在但不匹配时拒绝，不删除或重新初始化。

当前公开 `apply/recover` 仍拒绝 GPU 状态及新的整站记录。文件、锁、CPU 进程中断和服务模型验证与实际 Docker、PostgreSQL、CUDA 验收分别记录；模型不解除激活门槛。统一检查入口及未完成项见[整站发布与恢复](../deployment/container-gpu-worker.md#whole-site-release)。
