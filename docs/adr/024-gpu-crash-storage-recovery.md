# ADR-024：异常退出后的私有存储回收

状态：接受组件设计，2026-10-31。依据 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md#受信运行适配器)，验证见 [G8](../acceptance-g8.md)。本决定不开放 GPU 提交。

## 问题与决定

任务控制器被强制终止时，正常的容器清理无法执行。整个任务 cgroup 停止后，私有 Podman 存储仍可能包含映射 UID 的目录；操作账号无法直接删除这些文件。保留目录和设备预约是必要的，但还需要可验证的恢复路径。

运行模块在创建这些文件前，持久化工作目录设备号/inode、预约身份摘要和内核 UID/GID 映射。记录不含学员源码、答案、日志或容器 PID；文件私有且不可覆盖。普通目录清理部分失败时，保留预约和运行时身份文件供接管。

`recover_workspace` 要求调用者已经持锁并停止原服务，重新核对服务身份和整个 cgroup；它不修改数据库预约。回收使用绑定相同设备/任务/预约的独立 `recovery` 服务，在最多 60 秒的调用预算及独立服务硬期限内运行固定入口。旧回收进程也必须先停止，其环境目录回收后才能重新启动。

新的完全断网 RootlessKit 命名空间必须具有与原任务相同的 UID/GID 映射。外层验证 socket 对端属于此次回收服务后，才发送目录身份；内层核对 inode、私有身份文件及映射，拒绝残留挂载、链接形式的存储根或任何身份不符。只删除固定 `data/run/tmp` 子目录，使用基于文件描述符、不跟随嵌套符号链接的删除。没有打开旧 Podman 数据库、执行旧工作目录中的程序或根据旧 PID 发信号的路径。

回收成功并且回收服务停止、cgroup 为空后，外层才删除剩余工作目录。回收中断时可凭保留的预约和映射记录重试；无法核对的旧记录保留现场，不提供忽略身份的强制选项。文件系统回收不代表 GPU 空闲或正确性恢复，正式 worker 仍须完成这两项检查后才能结算、释放预约。

命名空间与 ID 映射机制参考 [RootlessKit 官方说明](https://github.com/rootless-containers/rootlesskit)。实际边界通过本机 CPU 容器验证，未用其推断 CUDA 清理成功。

## 验证

实际 runsc CPU guest 运行期间，分别触发可信控制器立即退出、整服务终止和独立硬期限。替代控制器只依靠持久预约重新打开目录，成功回收映射文件；活动任务的回收被拒绝。独立回收入口在收到删除请求前被终止后，下一次接管也成功。更细的部分删除重试、权限/链接/挂载/身份不符及期限检查由定向测试覆盖。

该入口不访问 GPU、不继承数据库凭据、不执行学员任务，也不生成启动 receipt。正常容器回收路径同时重放，详细范围见 G8。
