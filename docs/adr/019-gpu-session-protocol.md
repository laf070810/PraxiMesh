# ADR-019：CUDA 会话协议与控制器批次时间

状态：接受组件设计，2026-10-30；参数和运行路径尚未通过本轮 GPU 验收。正式准入仍关闭。背景见 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md)。

## 决定

受信控制器与固定 GPU guest 驱动通过逐条 JSON 请求/应答通信：先编译源码并核对设备架构，再发送输入。预期结果、用例可见性和名称不发送到 guest；不接受其自报 verdict、耗时或分数。驱动保留独立协议文件描述符，设备 `printf` 只能写入受限 stderr。

控制器与驱动统一限制每帧 256 KiB，覆盖两个最大输入数组的小数序列化；累计 stdout 2 MiB 和 stderr 32 KiB。编译限 15 秒，每次执行请求限 5 秒，会话 Run 60 秒、Submit 120 秒。等待时检查租约/取消，回调返回后重新核对截止时间；正式 worker 还须限制数据库回调等待，并设置每任务服务硬期限，不能只靠同步回调周围的轮询提供硬停止保证。

只在全部正确性检查通过后，对工作量最大的正式测试输入进行 2 批预热、5 批采样，每批 16 次调用。每次调用前清空输出并同步执行，每批比较结果。控制器测量请求到响应的墙钟中位数，编译/初始化单列；这些时间包含通信、缓冲区分配和同步开销，不能写成纯 kernel 时间。任何正确性、采样或资源检查失败均不保留性能成绩。Run 不生成性能成绩。

会话关闭始终执行自有容器清理并确认终止；不能用附着客户端退出证明容器已停止。未知退出归为平台故障；内存超限必须来自驱动的已知退出码，或受信容器/cgroup OOM 观察，不能仅由 SIGKILL 推断。清理失败优先作为平台故障，设备继续停用。

会话逻辑由 `judge/gpu_session.py` 提供，比较和采样由 `judge/gpu.py` 提供，当前 `--session-probes` 通过私有 gVisor 环境调用。执行摘要包含会话、驱动、比较、隔离配置、资源与依赖源码。它只是版本身份，不是启动 receipt，也不授权开放网站提交。

## 验证边界

[G4 记录](../acceptance-g4.md)中的真实管道检查只验证协议与控制流程，不执行 CUDA。首次 GPU 重放因其他账号的计算进程占用目标卡而在启动前退出。最大输入、固定批次成本、实际输出超限、取消/异常退出和设备恢复均须在独占卡上补验，之后才能接入正式评测池。
