# ADR-064：冻结发布环境与原 worker 的就绪观察

日期：2026-11-01。状态：采纳；组件与归档读取验证，真实数据库、容器和 GPU 部署待验收。延续 [RFC-022](../rfcs/022-gpu-release-coordination.md) 与 [ADR-063](063-durable-gpu-worker-lifecycle.md)，结果见 [G48](../acceptance-g48.md)。

容器处于 running 状态，不能证明完整 GPU 启动已经通过。数据库中的旧心跳也可能属于同名 worker 的上一次启动。发布控制器必须把实际运行实例、原配置、完整环境和当前数据库状态一起核对，不能只检查一个布尔标记。

内部 `Deployment.gpu_worker_ready()` 由 `scripts/deploy_gpu_readiness.py` 实现。它完整核验原发布归档，随后再次逐文件验证源码字节；运行时源码范围、runsc、NVRTC、Docker CLI 的固定声明只通过 AST 字面量读取，不导入或执行归档 Python，也不借当前工作树计算旧包身份。任务/控制器源码契约、镜像、驱动和管理清单来自同一冻结清单。现有版本化环境验证器继续检查资源、设备与会话字段。

原维护路由、部署/数据库操作锁、同 token 暂停、完整私有配置和本代容器运行契约必须成立。每次数据库快照用一个只读 SQL 同时观察队列暂停、目标设备、全部未完成任务及所有设备的物理预约；没有任务行的预约仍会阻止通过。不持设备或队列行锁等待 worker，连接在观察后关闭。

目标设备须属于本代 worker、ready 且无任务/预约。心跳须有时区、不早于原容器启动、不晚于数据库观察时间，并把控制器读取耗时计入新鲜度。完整环境须匹配冻结制品、原节点和同一实际 daemon。环境核验后再次确认原容器与心跳，再取得最终数据库快照；设备所有者或环境发生变化时拒绝，出现新任务、预约或隔离状态时继续等待。

等待预算覆盖完整 GPU 启动并从原容器启动时间计算；协调器重新执行不会续期。超时保留原容器、任务及预约，不重启、不清理、不写就绪。成功只返回本次观察的非敏感摘要，不持久缓存为曝光凭据；每次重新调用都必须重新读取，后续曝光仍须再次核验。

该入口只用于开发中的发布协调，不签发或读取私有 receipt，不修改正式成绩，也没有接通 GPU `apply`。真实 worker 仍负责完整启动、凭证、设备清理与健康发布；实际 Docker/PostgreSQL 和完整队列、回滚、曝光恢复需分别验收。
