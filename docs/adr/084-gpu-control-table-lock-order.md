# ADR-084：GPU 控制事务先取得更新表锁

日期：2026-11-15。状态：采纳；真实 PostgreSQL 检查通过，原站点恢复与新版本硬件验收继续。设计见 [RFC-030](../rfcs/030-gpu-database-lock-order.md)。

控制事务在原局部超时生效后、读取设备行之前取得 `ROW EXCLUSIVE` 表锁。这样部署检查的 `SHARE ROW EXCLUSIVE` 必须等待该短事务结束，不能插在设备行锁与心跳 UPDATE 的表锁升级之间。设备行仍先于任务行加锁；250 ms 锁等待、1 s 单语句限制和失败保留物理预约的规则不变。沿用原 GPU 表权限，不增加授权。

真实 PostgreSQL 已复现原心跳 UPDATE 的锁超时。修复后的 36 项并发、设备/任务和最小权限检查通过；额外三项确认旧清理的较短事务等待及新锁顺序。它们不执行 GPU，也不生成 ready。

历史清理只识别已审阅的原 `core/gpu_control.py` 与候选 CLI 源码摘要对，使用原 CLI 已有的 `--database-timeout 0.2`。正常检查的预算不变，新版本仍用默认清理等待。旧清理在竞争时先回滚，保留同一轮次、原任务及已确认的结果；不自动重试、不延长原验证期限，也不替代新启动就绪。未匹配的旧源码不获此兼容能力。

兼容核验只读取并校验归档字节，不执行归档代码或借当前工作树声明旧能力。原恢复仍操作原库、原 worker 和当前实际启动实例；调用进程中断后继续原恢复记录，不重建 GPU 对象。
