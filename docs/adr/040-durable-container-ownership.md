# ADR-040：持久容器身份与仅清理旧调用的恢复

日期：2026-10-31。状态：接受开发路径；完整 GPU 容器 worker 尚未交付。背景见 [RFC-021](../rfcs/021-gpu-container-supervision.md)，结果见 [G24](../acceptance-g24.md)。

新增 `ContainerJournal` 和 `PersistentRuntimeService`，保留原开发服务行为。持久服务名称由私有安装 UUID、固定 Docker daemon 身份、设备锁目录 inode、设备 UUID、任务 UUID、预约及用途确定，不依赖进程 UID。当前命名空间中的文件拥有者和 0700/0600 权限仍必须成立；不同锁目录或 daemon 不能接管此记录。实际 worker 容器的 UID 映射与部署挂载仍需单独验证。

每个设备同时只有一份活动记录。先持锁写入固定启动意图，再创建容器；完整容器 ID 在启动前落盘，原启动实例在确认就绪后记录。保存原镜像 ID、完整参数与 nonce、镜像环境、标签及 seccomp 配置，不保存任务源码或应用密钥。写入先同步私有临时文件，在共用的私有元数据锁内核对目标是否允许创建，再原子重命名并同步目录；已存在的活动记录不能被新调用覆盖。元数据锁 inode 保留，初次安装的不同设备控制器也必须共用；同一对象的线程另行串行化。

首轮真实检查发现本机项目目录为 NFS，`RENAME_NOREPLACE` 返回 EINVAL，尚未创建任务容器。该扩展依赖文件系统支持，见 [rename(2)](https://man7.org/linux/man-pages/man2/rename.2.html)。因此采用上述文件锁与普通原子重命名组合，继续保持完整记录和独占发布，不使用复制或截断原文件作为回退。文件锁、原子重命名或同步失败仍保留活动记录并停止。

恢复只支持已知 v1 监督契约。`RecoveryContainer` 使用原记录核对实际对象，允许当前源码摘要已变化或旧镜像无法再用于新执行；不运行旧镜像中的入口，也不续接旧通信。随机 nonce 和完整参数保护创建成功但 ID 未落盘的窗口；找回后先保存容器 ID，再停止。已有 ID 或启动实例被替换、配置变化、记录损坏或缺失时拒绝操作，保留待恢复状态。

确认容器移除后，将记录标为 removed 并归档，再移除活动记录。归档中断可重复恢复；归档内容冲突不能直接删除活动记录。普通任务完成仍需调用 journal 的恢复/归档路径，不能只删除 Docker 对象而丢弃持久记录。新任务必须等待前一个活动记录处理完成。

此结果只证明原可信容器已清理，返回值始终 `ready: false`。不释放数据库预约，不证明 GPU 无残留，不代替独立正确解和完整启动凭证；这些动作仍由后续 worker 集成负责。操作集中在 [GPU 指南](../deployment/gpu.md#container-journal)。
