# ADR-027：共用启动资源检查

状态：接受组件设计，2026-10-31。依据 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md#正式就绪检查)，证据见 [G11](../acceptance-g11.md)。本决定只覆盖完整启动门槛中的资源部分，不签发 GPU 凭证。

## 决定

`GPUExecutionAdapter.check_resources` 只能使用已持锁的维护服务。外层新建回环监听端口和随机挑战，通过私有通道发送固定 `check-resources` 请求，不接收源码、程序或路径。控制器验证消息与运行时身份后，调用 `judge/gpu_isolation.py`，为后续独立 CUDA 正确解恢复和存储清理保留时间。资源检查、恢复、整服务停止及设备空闲全部成功后才返回报告。

资源模块同时供生产控制器与显式 CPU 基础设施验收调用。两种模式必须与运行时是否已准备 GPU 完全一致；CPU 结果不能满足 GPU 检查。固定 guest 验证非 root、只读根、宿主私有文件与回环网络隔离、环境清理，以及准确设备集合。输出、超时、取消、附着客户端退出、CPU 节流、内存 OOM 和临时存储限制都实际触发，并在随后新建的容器中重新验证隔离。

内存限制必须由可信控制器观察到 cgroup OOM 计数增长。CPU 使用实际内核计数证明节流，临时存储触发 ENOSPC。宿主 PID 额度用固定原生探针测试，不能用 guest 自报 PID 数替代：gVisor 虚拟进程与宿主进程并非一一对应，见其[资源模型](https://gvisor.dev/docs/architecture_guide/resources/)。

原生探针只在私有控制器的 UID 0 和管理 cgroup 下启动，先确认工作负载组为空且上限为 256，再创建自己的叶组。探针及 255 个固定休眠子进程实际占满父组额度；随后尝试创建失败，终止、等待全部自有子进程，移回管理组并删除叶组。控制器确认拒绝计数增加且剩余任务为零。子组结构遵循 [cgroup v2 的内部进程约束](https://docs.kernel.org/admin-guide/cgroup-v2.html#no-internal-process-constraint)，不更改父组限额或共享主机配置。固定探针没有学员输入；服务硬期限仍覆盖异常中断。

报告必须包含准确有序的九项检查和十七个不同容器的清理记录，并匹配本次挑战与设备身份。拒绝缺项、重复容器、失配挑战、错误布尔类型、未停止容器或夹带成绩。检查使用显式异常，不能依赖可被 Python 优化关闭的 `assert`。

## 验证边界

实际 CPU 重放证明上述共用资源流程及清理；正式 GPU 模式的设备可见性、CUDA 恢复、完整时限仍需独占硬件验收。启动 CUDA 正确解/错解/故障、失联恢复、凭证、worker 和产品准入还须继续完成，不能将本模块单独作为 ready 条件。
