# ADR-054：容器资源与隔离启动检查

日期：2026-10-31。状态：已实现并通过非 GPU 资源及调用链验收；GPU 与完整启动发布仍待验收。背景见 [RFC-021](../rfcs/021-gpu-container-supervision.md)，实际结果见 [G38](../acceptance-g38.md)。

`ContainerGPUAdapter.check_resources` 通过原维护任务发送随机挑战。可信任务端创建回环监听器和私有 canary，固定镜像中的 `container_isolation_guest.py` 只接受审阅过的身份、输出、等待、CPU、内存和临时存储操作。客户端不能替换路径、命令、端口或预算；学员源码不进入此检查。

`container-resource-check-v1` 保留独立语义：guest 的 UID 为私有沙箱内的 0，能力集为空、禁止提权、根目录只读，不可见外层 canary，也无法连接外层任务的回环监听器。它不把任务回环描述成宿主全局回环。GPU 身份检查要求 CUDA 仅枚举一张卡，UUID、型号、架构与原目标一致；设备节点按原选择的物理 minor 和 UVM major 核对，不把 CUDA 逻辑序号 0 当成物理 minor。驱动精确版本继续由外层固定驱动制品及运行时核对，CUDA API 的版本号不冒充 NVIDIA 驱动版本。无设备 CPU 入口不调用 CUDA 或加载驱动库。

九项检查覆盖身份、输出超限、超时、取消、附着退出、CPU 节流、临时存储、内存 OOM 与进程上限。每项均要求新的身份 guest 成功，按顺序保留十七个原 guest 的首次清理证据。取消和附着退出先确认原 guest 与原附着进程活跃，之后确认实际停止、移除和进程树清空。报告严格验证实际 CPU 用量/节流、有限存储大小、本任务 OOM 计数、进程上限与恢复原任务数，拒绝缺项、重复、非有限数和布尔值冒充测量值。

OOM 主动监测发现原附着进程仍活跃时，先终止并等待该进程，再调用原运行时清理。这与正常会话关闭顺序一致，避免在仍活跃的附着进程上直接等待清理；独立停止/移除和整个原进程树确认仍为必需。无法确认 CLI 退出、清理命令失败或监督器被杀都不能转成成功报告。

限额维持 `container-workload-v1`：整任务 0.5 CPU、512 MiB、无 swap、256 个宿主任务，包含监督器与 runsc 开销。内层 PID 是虚拟化视图，进程上限因此复用自有私有任务 cgroup 内的固定可信 fork 探针，不执行任意宿主源码。CPU 或内存限额不代表 GPU 显存预算。

九项通过后仍须在原绝对期限中运行新的正确内核恢复并完成清理；共预留 35 秒恢复、10 秒清理、5 秒完成通信。报告由原 `KernelTask` 再次按原目标/设备校验，外层 journal 清理和空闲观察成功后才返回。外层 OOM、通道中断或恢复失败均不能返回成功报告。现有 receipt 和网页准入继续拒绝尚未完成完整启动的容器路径，整控制器故障、启动发布、worker 与 Compose 继续接通。
