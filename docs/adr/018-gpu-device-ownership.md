# ADR-018：GPU 所有权与恢复后释放预约

状态：接受，2026-10-30。范围为调度组件；正式 GPU 执行器、启动探针与性能成绩仍按 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md)实施。

## 决定

同一张 GPU 每次只预约给一个任务。持锁控制器同时拥有主机私有目录中的每卡 `flock` 和数据库 `GPUDevice` 的所有权令牌。所有副本必须共用锁目录；关闭文件描述符释放锁，锁文件本身不删除，避免不同 inode 同时被两个控制器持有。新控制器取得锁后将设备置为隔离停用，保留旧任务身份，执行真实清理和恢复后才允许领取任务。

设备状态为隔离停用、可用、已预约。数据库保存任务 UUID 和租约令牌快照，不将设备预约做成随账号删除级联释放的外键。任务过期、结算或账号删除均不直接释放卡；只有持锁控制器验证自有工作负载已终止、目标卡无残留并通过恢复检查，才调用 `confirm_recovered`。发现未知占用或无法确认的执行状态时保持停用。

数据库内先锁设备、再锁任务；只给任务表加写锁，不锁只读题目版本。拿到锁后重新检查租约期限，避免 SQL 查询开始时有效的租约在锁等待后被复活。旧所有权、任务身份或租约令牌不能更新下一任务。Web 对设备表只读；worker 只有 SELECT、INSERT、UPDATE，不得删除设备行或修改题目。

复用 `Submission` 记录 `gpu-slot-seconds-v1`，Run 90 秒、Submit 180 秒，CPU 调用单位与 GPU 整卡时段分别统计。只有首次实际调用前的执行标记将预约转为已消耗；执行前的平台失败可释放账目额度，执行后的失败不退回。账目额度释放与物理设备释放是两项独立动作。账号导出提供本人 GPU 账目，删除账号后不保留源码或用户外键，只暂存恢复所需运行身份。

迁移追加 `core/0004_gpu_resources`，保留旧迁移与历史 CPU 预约。部署授权根据实际记录的迁移和存在的表确定；新控制器可处理没有 GPU 表的旧数据库。恢复数据库时，GPU 健康状态失效并进入隔离停用，不能从备份继承硬件就绪状态。

## 结果与边界

[G3 验收](../acceptance-g3.md)包含真实进程文件锁、PostgreSQL 并发/权限/迁移和等锁跨越期限的检查。调度组件不执行 GPU 代码、不签发 receipt；测试中的恢复转换只证明数据库状态转换。正式 worker 还必须把真实设备清理、恢复、取消和预算上限接入这些接口，之后才能开放 GPU 提交。
