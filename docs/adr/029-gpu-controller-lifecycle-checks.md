# ADR-029：整控制器故障与独立恢复检查

状态：接受组件设计，2026-10-31。依据 [RFC-019](../rfcs/019-gpu-kernel-evaluation.md#正式就绪检查)。正式 CUDA 路径仍待独占硬件验收。

## 决定

`GPUExecutionAdapter.check_controller` 只接受维护服务和三个固定用例名：控制器退出、控制通道失联、独立服务硬期限。每次由外层生成新挑战，通过已有私有控制连接交换；维护协议不能传入程序、源码或目标 PID。

内层先在仍打开的 CUDA 会话中编译并验证固定正确解，再发 `fault-armed`。只有本次 `fault-trigger` 匹配后，才执行直接退出、关闭通道后停止轮询、保持连接但停止轮询之一。测试不把持有 CUDA 上下文等同于正在执行长运行内核；后者另由超时和会话中断用例检查。

外层核对就绪挑战及服务仍存活后触发故障，不接受普通异常或任意 EOF。退出及硬期限场景必须在显式停止前确认整个 cgroup 为空；硬期限还需排除提前断开。失联场景须观察到断开后仍存活的服务，再通过原 `OwnedJobService` 实例核对并停止。所有路径保留服务调用身份及主机锁，不能以新建对象绕过原调用核对。

每项总预算不超过 180 秒：前段最多 90 秒，预留其中 30 秒处理映射存储；正确解恢复另有最多 90 秒，且受原总期限约束。硬期限观察可等到服务期限后的余量内，但不延长 systemd 运行期限。只有旧服务停止、cgroup 为空、工作目录已移除及设备空闲后，才用同一持久维护身份创建新的服务调用来运行正确解。失败继续保持停用和原预约。

共享故障模块 `judge/gpu_lifecycle.py` 同时供实际 CPU/runsc 验收使用。CPU 路径只运行固定基础设施程序，经过同一故障握手、终止观察和映射存储回收，再以新服务、新容器执行固定 CPU 检查。其结果不得进入 GPU 凭证。

## 验证边界

组件测试核对挑战、状态顺序、提前退出、额外输出、期限、清理失败和恢复预算。实际 CPU 入口及本次结果见 [G13](../acceptance-g13.md)。这些结果不证明 CUDA 恢复、GPU 完整时间预算或性能。

完整启动编排、绑定当前所有者的凭证、健康准入、正式 worker 与产品题型仍须继续实施和验收；本组件不改变设备就绪状态。
