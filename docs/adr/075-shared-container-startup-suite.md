# ADR-075：复用完整容器启动检查

日期：2026-11-02。状态：采纳；完整本地执行命令与 GPU 硬件验收仍待完成。对应 [RFC-024](../rfcs/024-local-cuda-practice.md)。

## 问题

本地 CUDA 公开样例执行需要和服务端相同的完整启动检查。原编排位于 `core/gpu_readiness.py`，同时管理数据库预约与凭证发布；直接从本地工具调用会引入学习数据库依赖，复制编排则容易遗漏检查或恢复条件。

## 决定

将容器检查编排整理到 `judge/container_startup_suite.py`。该模块可在未安装或初始化 Django 的进程中导入，不访问应用数据库。它接受原适配器、由可信调用者刚完成的初始恢复报告、维护任务身份、总期限及所有权/取消回调。

流程核对初始恢复报告、原锁、控制器、环境和空 journal，随后依序执行资源、十九项内核及三项控制器故障检查。每阶段仍使用原维护任务、独立清理和既有报告校验；单阶段最多 180 秒，总预算不超过 4320 秒。仅在全部二十四阶段和最终原身份/清理检查通过后返回完整证据。进度通知不表示就绪，失败或取消不返回部分成功结果。

服务端调用共用流程，继续负责实际初始恢复、旧预约保留、凭证撤销/发布、最后的数据库行锁核对和 ready 事务。宿主后端保持原流程。本地调用者后续须自行实现共享物理锁、持久任务身份和真实初始恢复；共用函数不提供报告导入、receipt 发布或跳过阶段的外部入口。

新模块纳入有序 GPU 执行源码契约，并随控制器、worker 和源码发布包交付。契约变化时须重建匹配镜像，不能借用旧凭证或只替换单个文件。

## 验证边界

无数据库组件验证使用真实私有锁/journal 文件与明确的 GPU 执行模型；独立子进程检查不加载 Django。服务端回归继续验证旧预约、凭证失败和替代拥有者，真实 PostgreSQL 检查验证发布时行锁竞争。这些结果不证明 CUDA、设备隔离、完整硬件启动或本地 GPU 工具已经交付。

实际无设备 worker 镜像/Compose 预检、匹配编译镜像和默认 Compose 回归均按集中部署指南重放，结果见 [G65](../acceptance-g65.md)；它们不执行 GPU 工作负载，也不能签发 GPU 就绪凭证。
