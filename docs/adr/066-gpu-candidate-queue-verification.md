# ADR-066：固定 CUDA 候选检查与原提交保留

日期：2026-11-02。状态：采纳；实际临时数据库、私有文件和协调器进程验证，GPU 执行、Docker 和 PostgreSQL 验收待完成。延续 [RFC-022](../rfcs/022-gpu-release-coordination.md) 和 [ADR-065](065-original-database-gpu-worker-recovery.md)，结果见 [G50](../acceptance-g50.md)。

设备 ready 只能证明启动门槛，不能证明候选代的正常队列会产生成绩。因此在完整发布接通前，增加 `core/deployment_gpu_check.py` 与 `deployment_gpu_check` 管理命令，经原 `enqueue` 提交固定向量加法和减法错解，检查两条正式 Submit。程序只交给既有 GPU worker，Web/管理命令不编译或执行源码，不提供模拟或跳过检查的生产选项。

操作绑定本次暂停 token、本代 CPU/GPU worker、所选单卡、原启动时间、设备 owner 和完整环境指纹。无密码账号、临时题目版本及两个提交使用稳定的本操作标识；准备在同一队列锁事务中暂时恢复准入、提交、重新暂停并还原暂停时间，外部提交者不能观察开放窗口。GPU 表锁和行锁只在短事务中核对，等待执行时全部释放。

识别原记录须匹配完整题目数据/摘要、固定源码/摘要、账号属性、模式、指纹和预算，不得出现其他关联数据。重试继续同一批提交，不取消、不重复入队、不刷新以最早提交时间计算的 480 秒观察期限。过期后即使后来出现结果，也不将其计作本次验证成功。

通过要求现有 `verified_evidence` 接受完整 CUDA 结果，正确/错误 verdict、用例通过数、性能契约、预算、时间和完整环境均一致。检查命令返回通过后仍保留测试记录；协调器先持久保存验证响应，再调用独立 `cleanup`，最后持久保存清理响应。这样确认丢失只会重读原成绩，清理响应丢失只会重试清理，不产生新提交。

清理仅在全部任务终态、全部设备没有物理预约且原设备新鲜 ready 时删除自有测试记录。未知任务状态不算终态。失败后也可显式调用同一清理流程；它不要求成绩正确，不报告验证成功，也不能删除真实用户或未恢复的预约。

`scripts/deploy_gpu_check.py` 先校验冻结制品包含协议声明和对应 worker 源码，再持久保存原代/实例/配置/环境身份；调用固定管理命令后核对完整有界响应，并重新观察原实例和就绪。五个阶段为 checking、checked、cleaning、verified、cleaned，checked 表示成绩已持久确认、尚待清理；清理观察仍须绑定原容器、配置和环境。成功记录只属于原启动，重复读取仍重查就绪；原 worker 重启后只能按新鲜身份清理原测试记录，不能将旧结果转为新启动的验证证据。未完成检查阻止配置发布和 CPU 恢复入口绕过。

Web 与管理容器仅获得所绑定设备的准入名单，不获得设备、socket 或 receipt。CPU worker 保持原环境。两份新增应用源码自动进入 GPU worker 的冻结源码契约，使用时须重建匹配制品；旧归档仍可只读校验，但不授予新检查能力。

本轮组件不解除公共 `apply` 的 GPU 拒绝。完整发布、候选检查调用顺序、升级回滚和曝光流程仍需连接并真实验收；数据库中的合成环境和结果仅验证事务/证据边界，不是 CUDA 正确性、计时或设备恢复证据。
