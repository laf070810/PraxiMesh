# ADR-055：容器控制器故障与新实例恢复

日期：2026-10-31。状态：已实现，非 GPU 故障、相关回归与清理核对通过；GPU 与完整启动发布仍待验收。背景见 [RFC-021](../rfcs/021-gpu-container-supervision.md)，结果见 [G39](../acceptance-g39.md)。

共用 `controller_faults.py` 的固定退出、断连、独立期限三种握手。宿主与容器保留各自的实例身份和监督语义；请求只接受固定名称及随机挑战。容器可信任务先编译并比较固定正确内核，再确认原 guest 和附着进程活跃，才发送包含挑战的故障准备消息。收到匹配触发后才退出或停止轮询，普通提交不能调用此维护分支。

故障对象是任务容器内的可信执行控制器，PID-1 监督器独立承担期限和子进程退出处理。持有 Docker socket 的控制容器及其持久记录接管继续使用原控制端契约；两种角色不能混为同一个进程或同一项验证。

`container-controller-check-v1` 绑定外层原 ID、启动 nonce、实际硬期限、断连时刻和明确状态。控制器退出要求监督器状态 70、独立期限要求状态 124，两者都要求 PID 为 0；提前断连、OOM、对象丢失或替换均不通过。通信断开则必须留下同一运行实例，之后按原 journal 清理。观察器不调用 stop 来证明独立退出；实际 CPU 验收在任何主动清理前另核对原进程树已消失。

已握手的固定故障可在原硬期限后的停止余量内观察 EOF 和状态。观察期间仍核对原锁、socket、容器 ID、命令参数、租约回调及原记录；实际 PID-1 期限没有改变，普通连接的存活和超时要求也不放宽。运行中的 GPU 任务继续做原占用观察，停止后沿原记录清理，再重新观察空闲。

`ContainerGPUAdapter.check_controller` 在最多 180 秒中保留最多 90 秒故障与 90 秒独立恢复。故障实例完全移除后，才在同一锁、任务 ID 和预约下创建新维护对象。它必须使用不同的容器 ID 与 nonce，运行固定正确恢复并完成自己的清理；环境变化、原归档不匹配、恢复失败或实例复用都扣留报告。该报告不产生学员成绩或 GPU receipt。

2026-11-12 的确定性分数时钟检查发现，构造的合法期限相减后可能略大于原预算。故障、完整启动及维护入口统一按原绝对期限比较，保留严格的最小预算、类型/有限值检查及原 90/180/4320 秒上限，并拒绝紧邻上界的下一个浮点值；不添加容差或重置期限。设计见 [RFC-021](../rfcs/021-gpu-container-supervision.md#监督契约)。源码摘要随修复更新，匹配镜像及无设备回归的范围见[托管失败复现](../acceptance-hosted-ci.md#fractional-clock)，不使用旧凭证或 CPU 模型开放 GPU。

固定无设备夹具使用同一可信执行流程和故障观察器，源码只作协议数据。五组真实场景覆盖三个故障、准备正确性失败和后续恢复失败，各组再验证新的正确调用；它们不证明 CUDA、实际显存、设备恢复、完整启动发布或容器 worker 已可用。
