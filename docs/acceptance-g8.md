# G8：异常退出后的私有存储回收

日期：2026-10-31。实现见 [RFC-019](rfcs/019-gpu-kernel-evaluation.md#受信运行适配器)、[ADR-024](adr/024-gpu-crash-storage-recovery.md)。操作统一在 [GPU 部署指南的 CPU 异常恢复入口](deployment/gpu.md#不占-gpu-的异常恢复检查)。本批只运行固定 CPU 基础设施程序，未访问 GPU、加载 CUDA、释放设备预约或开放提交。

## 实现与实际检查

`judge/gpu_recovery.py` 在创建映射文件前保存私有运行时身份；替代控制器核对预约、旧服务及其全部进程后，通过独立、有硬期限的 RootlessKit 服务删除固定私有存储。新命名空间核对原 UID/GID 映射、目录 inode 和两份身份摘要；不打开旧 Podman 数据库、不根据旧 PID 发信号、不执行遗留目录中的程序。缺失身份、挂载、映射不符或清理中断保留现场，回收服务也确认停止后才删除原工作目录。

首次实际检查 `test-results/px-gpu-recovery-86865d692d98/result.json` 的三项场景通过。每个场景在固定 runsc CPU guest 确认运行后触发异常，原任务停下后仅凭持久预约重新打开工作目录；宿主无法读取的映射目录 UID 为 1541789，替代命名空间成功回收它以及真实容器存储。

| 场景 | 检查范围 |
| --- | --- |
| 控制器退出 | 内层可信控制器直接退出，跳过正常清理；外层确认整个任务 cgroup 已空后接管目录 |
| 整服务终止 | 容器仍运行时终止本次独有任务服务；停止回收入口、留下其目录，再由新回收实例接管 |
| 独立硬期限 | 控制器停止轮询并等待，用户服务管理器终止整个进程树；随后回收映射文件 |

三项均拒绝对活动任务执行回收。回收中断的真实场景发生在对端已认证、尚未发送删除请求时；部分目录已删除后的重试另由定向测试覆盖，不把两者混为同一次实测。

## 失败与修复

`test-results/px-gpu-recovery-157dd08c4f8d/result.json` 保留后续重放的失败：前两项通过，第三项的回收进程结束后，`systemctl stop` 返回非零。随后自有服务和 cgroup 检查确认已退出，失败后的再次回收成功，测试目录最终移除。该整体结果仍为失败，不计作通过。

服务停止逻辑原先在命令非零时立即报错，未处理临时服务自然退出、自动收集与停止命令之间的竞态。修正为重新核对服务身份、调用身份和整个 cgroup；仅在已停止且无进程时接受清理完成。服务仍运行、cgroup 有残留或同名服务调用身份改变时继续拒绝。五项定向状态检查覆盖这组边界。

修正后的最终重放为 `test-results/px-gpu-recovery-e5e3dee5dfa8/result.json`，三项全部通过，原服务与回收服务的 cgroup 均空，工作目录及临时根目录移除。最终源码摘要与该记录逐项一致。既有服务控制入口也重放通过，`test-results/px-gpu-control-d0bc10206242/result.json` 的四项场景覆盖硬期限、主进程退出、控制器接管及外来服务拒绝。
