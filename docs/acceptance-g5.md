# G5：不占 GPU 的任务控制链验证

日期：2026-10-30。维护者要求先继续不占 GPU 的开发。本轮没有访问显卡、执行 CUDA、终止其他账号进程或改动已有主机服务。**本轮通过的是任务控制组件，正式 GPU worker 和 GPU 提交仍未交付。** 操作集中在 [GPU 指南](deployment/gpu.md#不占-gpu-的控制链检查)，决定见 [ADR-020](adr/020-gpu-task-control.md)。

## 新增组件

`judge/gpu_service.py` 绑定任务与预约身份，监督独立临时服务，核对实际 cgroup 限额并确认整进程树终止。固定启动入口拒绝排队过久的服务；运行时限由服务管理器独立执行。`core/gpu_control.py` 将短事务、锁/语句等待限制、剩余预约时段和现有 GPU 租约接口连接起来；结果结算与设备释放仍要求可信运行端先完成真实恢复。

## 实际服务结果

首次 `g5-service-first.log` 失败；诊断 `g5-service-diagnostic.log` 发现本机 systemd 252 拒绝临时服务的 `JobTimeoutUSec` 属性。两个失败目录均记录没有残留自有 cgroup。改为固定入口检查绝对启动期限后，首次修复重放通过；进一步加入零 swap、实际父 cgroup 核对及微小剩余时段的零定时器拒绝后，最终记录为 `test-results/px-gpu-control-983663ee831f/result.json`，`passed: true`。

| 场景 | 实际结果 |
| --- | --- |
| 独立运行期限 | 固定父/子进程均忽略 SIGTERM，子进程另建会话；服务时限约 3.989 秒，约 4.212 秒确认两者停止且 cgroup 空。期间没有发送手动 stop |
| 主进程退出 | 父进程正常退出后，残留子进程由服务管理器终止；确认 cgroup 空 |
| 控制器退出与接管 | 首个控制器进程退出后服务仍在运行；新持锁控制器按同一预约身份确认调用 ID，再定向停止整个服务 |
| 身份不符 | 故意创建的不同描述测试服务被拒绝停止，仍保持 active；随后由该测试服务的创建者清理 |
| 实际父限制 | `cpu.max=200000 100000`、内存 2147483648 字节、swap 0、PID 512；这是实际限制读取，未在本轮重新做 CPU 节流负载测试 |

四个测试服务均确认停止、cgroup 空；原始结果、合成进程标记和锁文件保留在忽略目录。固定夹具只休眠和创建子进程，不读取传入源码、不创建 GPU 上下文。该结果不证明 gVisor/CUDA 进程树、设备释放或恢复成功。

## 数据库与组件回归

- `test-results/g5-postgres.xml`：**33 passed**，真实设备行/任务行锁争用在限定等待内报错，语句超时生效且设置恢复；既有最小 worker 授权足够。预约不会因超时、删除账号或控制器失锁而直接释放。自有 PostgreSQL 容器和卷已清理。
- `test-results/g5-components.xml` 为 152 passed、12 skipped；加入零定时器边界回归后的 `g5-components-commit.xml` 为 **153 passed、12 skipped**，覆盖 GPU 契约、会话、制品、主机锁、资源预约及新控制组件。12 项跳过均为 PostgreSQL 专属场景，已包含于上述实际 PostgreSQL 重放。
- Ruff、格式、差异、文档链接和源码打包范围检查通过。当前 CPU 执行策略未变化；本轮未重复已有 WASI 硬件无关但较重的整套沙箱验收。

测试中显式调用恢复后的数据库方法只检验事务边界，不构造或签发硬件 receipt。下一步仍需完整 GPU 运行适配器、占用监测、实际恢复和准入/产品接入；独占条件恢复后重放 G4/G5 组合的真实 GPU 路径。
