# G21 可信容器监督基础的 CPU 验证

日期：2026-10-31。实现前基线：`main` 的 `3cbeaa5`。设计见 [RFC-021](rfcs/021-gpu-container-supervision.md)和 [ADR-037](adr/037-trusted-container-supervision.md)，执行入口集中在 [GPU 部署指南](deployment/gpu.md#container-supervision)。本批遵循维护者“不占 GPU”的要求，只执行固定可信 CPU 程序。

## 已实现与验证的范围

新增 `container-supervisor` 构建目标，沿用锁定的 Python 基础镜像，仅包含监督器、契约与固定探针。它是可信基础设施容器，不是学员执行器，也没有挂载 GPU、宿主目录、Docker socket 或数据库配置。

控制端只连接显式、私有且属于当前用户的 rootless Docker socket。每次操作使用空白客户端配置和最小环境；固定本机镜像 ID、入口、用户与 runc，核对无网络、只读根、无能力、私有命名空间、有限 tmpfs 和资源参数。任务标识来自持有的设备锁与预约 UUID；实际观察到容器后，继续绑定完整 ID 和启动实例时间。错配、替换、daemon 状态不明或无法确认停止时拒绝清理。

容器 PID 1 在执行可信子进程前核对实际身份、cgroup 和启动窗口，之后独立维护绝对终止期限。调用者退出或重新接管不会延长期限。子进程只能继承五项固定环境变量，输出丢弃，Docker 日志关闭；就绪状态有界且包含随机挑战及监督源码摘要。

七项真实场景分别为：

1. `deadline-busy`：CPU 负载下到达独立期限，退出码 124，随后核对进程树消失。
2. `parent-exit`：可信子控制器自行退出，监督器及其脱离进程组的后代一起结束。
3. `owner-exit`：创建容器的宿主进程已退出，容器仍按原期限自行结束。
4. `takeover`：新的持锁对象找回相同预约容器，并停止、确认和移除。
5. `replacement`：旧对象拒绝停止同名的新容器；新容器仍运行，由新对象清理。
6. `foreign-label`：自建的标签错配夹具被拒绝启动和停止；测试工具显式启动该固定夹具后再次确认拒绝，最后只清理本次已知容器。
7. `late-start`：人为延迟超过启动窗口，监督器拒绝启动可信子进程，退出码 70。

进程树检查使用 Docker 的实际主机 PID、命名空间 PID 1 和 `/proc` 启动时间，避免仅凭 PID 消失判断。限额中 CPU 有实际节流检查；本批没有新增内存或进程数量的耗尽探针，读取上限不等同于实测所有资源故障。
