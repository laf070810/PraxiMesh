# G29 容器内编译控制与故障恢复

日期：2026-10-31。实现前基线为 `main` 的 `77177b3`。设计见 [RFC-021](rfcs/021-gpu-container-supervision.md)和 [ADR-045](adr/045-containerized-compilation-control.md)，操作集中在 [GPU 指南](deployment/gpu.md#container-compilation-control)。本批不占 GPU，不修改主机服务或现有站点。

可信控制镜像现在包含计算编译契约所需的完整源码，由镜像内验证固定编译镜像。新的一次性编译调用复用原 journal、实际总预算和受信连接：先验证请求，开始回调及原记录核对成功后才发送源码；正常返回必须完成 guest、任务容器和 journal 清理。取消、平台故障、清理失败和学员语法错误保持区别。返回内容只有编译状态、有限 PTX 元数据和镜像/预算身份，不生成正式成绩或就绪。

## 已复现的缺口

G28 控制镜像的原构建源码副本能导入编译服务，但调用 `compiler_digest()` 时因缺少 `judge/gpu_runtime.py` 失败，记录在 `test-results/g29-controller-snapshot-diagnostic.json`。这是可信摘要计算的隔离源码复现，没有执行学员程序。最初尝试使用上一轮镜像 ID 时，该测试镜像已按原验收清理，创建命令未生成容器；该尝试不计为实际容器复现。

修复控制镜像清单后，新增测试将其全部源码复制到独立目录，在隔离 Python 中同时导入新调用并计算编译/控制契约，结果须与当前仓库一致，不能借用原工作目录的模块。

## 实际容器编译与恢复

`test-results/px-controller-compiler-7a4d4a05566a/result.json` 的总结果和十四项场景均为 `passed: true`，原输出为 `g29-controller-compiler-initial.log`。所有调用使用同一个私有安装、设备锁与 journal，每次更换任务/预约身份；控制端镜像内的 UID/GID 0 实际映射到原非 root 操作者。

| 真实场景 | 观察结果 |
| --- | --- |
| 向量加法、矩阵乘法参考解 | 控制镜像内验证固定编译身份，经独立任务容器的 gVisor/NVRTC 生成 PTX 元数据 |
| 语法错误、不可用架构 | 分别返回 `syntax_error` 与 `platform_error`，原任务清理后才返回 |

| 发送源码前取消 | 任务已准备，开始回调抛出取消；源码未发送，原任务清理；后续新调用编译通过 |
| 编译后取消 | 已生成 PTX 后取消，没有成功结果；原任务清理，新调用编译通过 |
| 控制器退出、整控制容器终止 | 分别观察退出码 17 和 137，宿主重新取得同一锁并按原 v2 记录回收；随后新控制容器编译通过 |

## 剩余范围

无设备 NVRTC 编译不证明 CUDA 入口可加载、内核运行正确性、设备恢复或性能。新的编译制品身份不充当正式 GPU 执行环境；设备注入/持续监测、容器后端完整启动/领取/结算、GPU Compose 与发布升级仍待完成。本批没有运行 GPU、重放完整 WASI/数据库/浏览器/Compose 或重建已有服务，完整目标继续保留在[需求追踪](requirements.md)。
